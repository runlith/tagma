# Performance investigation

Investigate the reported symptom with the running system's evidence, distinguish work from waiting, and report only what the measurements support. Choose the smallest reading that can separate plausible causes; this is a decision guide, not a checklist to execute in full.

## Establish the question

- Name the observable operation and its completion: a server response, a first transcript frame, content visible to the reader, a tool ending, or a finished run. An HTTP duration measures only its own boundary.
- Establish the incident's time window, timezone, process instance and running build. A checkout, a test rig and an installed process are separate measurement targets. Keep evidence from different builds and restarts distinct.
- Distinguish explanation from authorized changes. Reading retained evidence does not authorize captures, load generation, settings changes, cleanup, browser interaction or a server restart. Follow the governing permission for each act.
- State the acceptance criterion from the request. A hypothesis needs an observation that could disprove it; stop pursuing a cause when the evidence does.

## Select the evidence

The current tool schema is the parameter authority. Reveal a deferred tool through the catalog before concluding that it is missing. Use read_performance for process telemetry; select only the row below that answers the question.

| Question | Reading | What it answers |
| --- | --- | --- |
| What did one act cost, including its reactive producers? | ledger | Process-local roots with disjoint own/producer statements, units, writer hold/wait, logical SQLite payload bytes and opened spans; select rootId or continue with the returned `{ledgerId,sequence}` cursor. |
| Which operation names can I ask about? | names | Separate cursor-paged span and metric name lists. |
| How does a known operation behave over time? | metrics | Per-name hourly distributions, counts, failures and histogram-derived p50/p99. |
| What was slow in this interval, across operations? | overview | Per-name histogram totals over explicit [since, until), paged by (name, boundaryKey); samplesRead, partial and stoppedAtBudget state the coverage. |
| Which occurrences of that operation were slow? | slow | Retained occurrences ranked by duration; choose a concrete span to explain. |
| Where did one occurrence spend its elapsed time? | breakdown | Direct children ranked by covered time, plus uncovered selfMs. Descend into the expensive child. |
| How are events related across a trace? | trace | A paged forest, optionally under a spanId; use it for structure rather than dumping a run to explain one span. |
| Did the event loop pause? | vitals, stalls, then stall | Interval CPU/memory/loop-delay samples; an explained stall and the spans overlapping it. |
| Where was CPU spent? | profiles, then profile | Saved sampled CPU frames. A long span alone is not a CPU profile. With raw, a thread gets the inspector artifact as a .cpuprofile file in its scratch, named in the answer. |
| What occupies memory, or what grew? | memory; captures, growth | A deliberate live census; or two retained censuses. The live census itself does work. |
| Which objects hold the memory, and through what? | capture_heap_snapshot | A V8 `.heapsnapshot` file of the main isolate with every object's size and retainers; two taken apart show what grew and what holds it. It pauses the process. |
| Is telemetry keeping up? | losses with source: "live"; relevant vitals | Current pressure and loss counters without a worker wait; omit source to page retained loss windows. |
| Which subprocess work cost resources? | commands | Retained command costs by class over the returned page, with unmeasured costs explicit. |

For current machine saturation, read_machine_load({limit: 20}) returns the native CPU account and the busiest processes from one round; pid narrows the process details. Its total, measured and shown counts describe different populations. Unattributed means no connection to the installation was established, and the signed difference between machine and process counters is unallocated work, not another application's CPU. Known executions lead to their command and thread; inspection grants no authority to stop them. This is a live reading, not a retained incident census.

The execution host is a separate process with its own ring: ask it the same questions through read_host_performance. It keeps a profile for a stall and for a standing window the process spent mostly on CPU, at most one busy window a minute, so a busy but responsive host is attributed through profiles whose requestedBy is "busy". Its memory and losses are measured inside the host; read its store pressure from its vitals.

Process spans and a thread's execution record answer different questions. For a model/tool/delivery incident, select threads with list_threads, query read_thread, then expand the addressed evidence with read_thread_record. Its runs, steps, measurements, entries and activity have different populations: immutable record revisions are not separate billable attempts. The activity source keeps the last day by default (setting activity.keepHours): each row is one model call, tool call, compaction, report or other act with its parent, actor, trigger, outcome and usage, and a step or measurement names its model call in its activity field; read_thread_record expands one row with its notes and bodies, and a body past retention or the body budget reads as unreadable while its row stands. A performance traceId names process spans; a thread or run id is not interchangeable with it.

Read settings with read_settings(section: "telemetry") when budgets or sampling matter. Use the reported effective value and source scope, not a remembered default.

## Keep reads small and relevant

1. Derive since from the incident clock in epoch milliseconds, and until beside it for overview. Time pages run oldest-first; omitting since starts at the oldest retained evidence, not at now. Reuse the same lower bound across related readings, and state the actual interval covered by their results.
2. Start with a small limit and continue only while the next page answers the question. A limit bounds returned rows, not necessarily query cost; slow and overview enforce their carrier-derived ceilings in the query schema. Their total is the population count when the first page exhausted it, otherwise null means uncounted, never zero. Names has separate span/metric cursors; pass the returned cursor unchanged.
3. Ask metrics for frequency and distribution, slow for examples, and breakdown for one example's elapsed time. A collection of longest samples does not establish the population's percentiles.
4. Filter identities actually carried by a result. Match instanceId before comparing monotonic clocks; do not subtract clocks from different processes or combine time windows silently.
5. Reuse evidence already read. Follow an expensive child or a concrete missing interval instead of widening every query or scanning every name.

Example sequence: let T be the incident's measured lower bound, N a name returned by names, and S a span id returned by slow. Ten rows here is a small discovery page, not a performance target:

    read_performance({type: "names", since: T, limit: 10})
    read_performance({type: "metrics", name: N, since: T, limit: 1})
    read_performance({type: "slow", name: N, since: T, limit: 5})
    read_performance({type: "breakdown", id: S, limit: 10})

These are alternatives as evidence warrants, not four compulsory calls. T, N and S are values obtained in this investigation, never literal placeholders to send.

## Interpret the evidence honestly

- **Coverage.** retainedRange gives outer bounds, not proof of completeness between them. Retention, sampling, a pending suffix and unfinished spans can all leave holes. Spans are kept by unit, not by trace. A span its producer declares a judged unit — every agent model step, tool call and other agent.* span below the run, and every Tagma operation's own span, named by its operation id and opened by the invocation layer around its execute, so its admission and prepare sit outside it — is kept with its whole subtree when it failed or ran past its own name's p99. A unit that passed 256 KB before it had failed keeps only its head, and only when the head ends failed or slow. A loop stall keeps only the spans that ran across it, with their ancestors up to their unit's head, never the rest of that unit: stall answers what overlapped the freeze, while the work around it is complete only where something else kept it. The p99 is the process's own since it started, so the first hundred endings of a unit's name are never slow, and a root's first hundred are slow only past 250 ms; after that a root, too, is slow only past its own name's p99, so a root name that always runs long keeps its outliers and its hash share, not every trace. Every tool call shares one name, so a tool call is slow against all tools, while the operation span inside it is judged against its own operation. A trace root's own spans are judged in windows of about two seconds, and a root's slowness keeps only a trace that ended within its first window. A hash-chosen share of traces is kept whole. So a unit stored for its own failure or slowness is complete while its parents may be absent, and a unit whose head survived only by crossing a stall holds just what crossed it: a trace reading shows it as a root, and a slow operation is read with slow on its operation id (a slow tool call on agent.tool-call) and breakdown on the span it returns, never by paging the run's trace. An absent span left nothing, whatever it did. An empty page is not proof that nothing happened; unavailable, query-failed and read-timed-out are not empty success.
- **Histograms.** metrics counts span completions even when individual successful spans fall below the storage floor. Each new span name carries a zero origin at its isolated registry's start, so its first snapshot does not consume its first completions as a baseline. Its percentile is a bucket bound, not an exact observation; preserve partial and aboveMs. Per-name metrics combine routes sharing a name; a route attribute on a stored span does not turn that aggregate into route-specific latency. A name with no hours at all may be work that ran without the tracer — a loop forked while a layer outside it was built — so an empty histogram is not proof the work is idle; a CPU profile settles it.
- **Overviews.** overview totals the same per-name histograms over an explicit [since, until) interval. Its page walks names in (name, boundaryKey) order, never a global slowest ranking; limit bounds returned series, not the samples the fold decodes. samplesRead counts decoded sample reads including edge probes, observed bounds cover every decoded in-window sample, and reasons discriminate missing baselines, resets, boundary changes and clipped edges per series; a sample landing exactly on since is that chain's own baseline, so its series is not clipped there, and only a successor-proven quiet right edge stays clean. stoppedAtBudget true means the fold ran out of decoded samples before the interval ended: the series it returned are still whole, everything from next on was never read, and the answer is a narrower interval rather than another page — a null next beside it means not even the first name fitted. Zero-count series carry no percentiles; compatible endpoints span missing ticks without losing counts. On an empty first page, coverageReason `no-snapshots-in-interval` means no histogram tick landed inside that interval; later ticks cannot fill an earlier window. Widen the interval to include its snapshot boundaries when a cumulative count is needed.
- **Profiles.** A stall carries a profile only while the standing sampler runs: the `telemetry.cpuSampler` setting, off by default. Off, a stall still records its delay, cpu and the spans across it; to find a frame, turn the setting on and catch the problem again, or take a manual capture, which runs the sampler for its window alone. Bun's sampler takes no sample while the loop thread is idle, and takes them a few times less often than asked. A profile report weighs each sample by at most the profile's typical sampling period (its lower-quartile delta), so its selfMs estimates busy time where the window holds runs of consecutive samples; a window of a few scattered samples has no period to read and is read by sample counts. A raw `.cpuprofile` still hands each idle gap to the first sample after it, so read it by sample counts, not by timeDeltas. A stall whose cpu and loopCpu are both near zero had nothing running — the process was not scheduled or its timer woke late under machine contention — and has no frame to find. A stall's `sampling` gives the samples inside it and the busy time they saw — the gaps between neighbouring samples inside the stall, idle gaps excluded — and names a frame only when that covers at least half the stall; a stall with fewer is work the sampler could not see, so read its loop thread cpu beside the process cpu (the process figure counts every thread — workers, GC helpers) before blaming the loop, and treat the spans overlapping it as candidates until something shows one is its cause. A stop-the-world collection is one such cause; macOS `sample` against Bun's `-profile` build of the same revision names native thread frames across the gap. Keep collection timing's scope separate from the loop delay it may explain.
- **Allocation and collections.** Heap growth and post-GC retained bytes measure occupancy, not allocation. In the checked Bun API, `getHeapStatistics().total_allocated_bytes` is heap capacity; `heapStats().mimalloc.malloc_requested` is process-wide allocator-request traffic, including native and other-VM work, with delayed/non-atomic aggregation. Compare its deltas only across matching bench compositions, label them allocator-requested bytes, and sample at window boundaries because `heapStats()` performs a census. `GCProfiler` reports per-VM collection-cycle durations, not mutator pauses; its native event list grows until stop and window boundaries can omit cycles. `BUN_JSC_logGC` `p=` describes collector stop phases; heap-address/`all` tags need a proved serving-VM mapping. Keep such figures diagnostic unless their timing and population match the gate. Loop-delay distributions are a bounded responsiveness measure, not proof of a collection's cause.
- **Elapsed time.** A slow span can be waiting on a permit, I/O, a child process or scheduling. breakdown selfMs is elapsed time outside the retained direct children's interval union, not CPU and not proof that missing children did no work. Never sum overlapping spans as sequential cost. On sql.execute, db.query.fingerprint groups normalized statements and db.query.summary names their shape; db.queue.ms measures dispatch-to-child delay, db.exec.ms the child engine, and the rest includes acquisition, transport and scheduling.
- **Tool events.** Trace-bundle record.at is the emission instant at millisecond resolution; queueMs is the separate monotonic wait before writing, including any earlier bundle-opening or payload work on the same lane. Subtract tool-call-started, tool-call-executing and tool-call-ended instants only for bundles produced by a build with emission timestamps. Earlier bundles timestamped the asynchronous drain, so those differences cannot establish execution phases. Tool durationMs includes the awaited afterTool rules.
- **Command costs.** commands carries the reaped child's CPU microseconds and peak RSS bytes where the host measured them; unmeasured stays explicit. Peak RSS is a high-water mark, not memory held now, and these costs do not establish complete descendant-tree accounting.
- **Causal costs.** `ledger` counts execution independently of span retention. A root's total is its own bucket plus disjoint producer buckets; a nested producer selects a bucket rather than repeating the count. Compare snapshots only within the same `ledgerId`: `endedAt` ends the root body, while queued work can still add to it. Pass the returned `next` cursor as `after`; a cursor from another ledger restarts at the fresh retained suffix with `reset:true`, even on an empty page. Do not subtract counters across that reset. The ledger retains a bounded suffix; `evicted` means omitted roots, not zero cost, and it is not durable history. Request/response bytes describe logical SQLite text, values and keys; they exclude transport framing. The execution host ring cannot answer this process-local query.
- **Causality.** A span covering a stall is a candidate, not its proven cause. Use the queue/permit owner's measurements or an experiment that separates waiting from execution. A fast health endpoint alongside a slow database read narrows a hypothesis only for the intervals actually observed.
- **Loss.** Distinguish pending overflow, stored retention, worker failure and intentional omission. Subtract comparable counters within the same process and interval; a lifetime drop total is not a current rate, and persisted retention drops are not automatically failed admission. State the denominator of any loss percentage.
- **Stored age.** Retention first selects the oldest eligible UTC hour, then prefers spans within it. The hour is an eviction ordering window, not an hour of guaranteed history. Inspect actual loss ranges: fast indexed selection and a bounded file do not prove that the incident's detail survived.
- **Comparisons.** Report sample count, window, load, dataset, cache state and build for each arm. Tiny or empty fixtures do not predict large-store tail latency. A throughput estimate from one batch's time is a model, not a measured end-to-end rate. An old archive's size or a thread's creation day does not date when its bytes arrived.
- **The server log.** One serve.log spans several days and every restart, and during a restart the leaving and the arriving server write into it at once. Each line opens with its instant, date and offset included, and the pid of the process that wrote it: take a window by the instant and one run by the pid. Lines written by a server older than that stamp carry only a time of day; for those, cut at the "=== tagma serve started <instant>" lines and count within one process, because a window chosen by the clock alone sums every day the file holds.
- **Scope.** Server responsiveness does not establish browser paint latency. A rig proves its controlled scenario, not the running deployment. A peer's result keeps its source and conditions until independently confirmed.

## Follow the symptom

**Intermittent slow opening or request.** Compare typical and slow instances of the same operation. Follow the measured path from admission through waits, execution and response. Where client evidence is available, include receipt and display; otherwise state that part as unmeasured. Test a queue hypothesis against a comparable read and the resource holder rather than blaming every function inside a long request.

**Slow transcript opening.** The transcript opens over live thread.subscribe; HTTP list timings are adjacent evidence, never the complete open. Server preparation is the short ThreadFeeds.open span (thread.id/project attrs), independent of the long-lived RPC subscription; client User Timing tagma.thread-open runs select to the post-snapshot frame opportunity, host ordinal in detail.host, never click-to-paint.

**Slow commit or rule check.** The gate's wait is enforcement.judgement; under it each rule is an enforcement.rule span (enforcement.rule and inspection.builtin attrs). Under a rule, inspection.ask is one request to an inspection worker: its queue.ms is the wait for that worker's lane behind other requests, its inspection.worker child the time the worker held it, and the inspecting.* spans below are the worker's own phases — listing, blob reads, parsing, calibration, inspecting.compute for the synchronous judgement — mirrored live into the same trace. Elapsed time of inspection.worker outside its phases is worker boot and messaging. A worker that is busy cannot answer the lane's state question; the lane then logs the phase it was last told about, so serve.log names a long phase while it is still running.

**Widespread freezing or high CPU.** Align loop-delay vitals and stalls with the incident. A CPU profile can identify computation; an otherwise responsive loop suggests asynchronous waiting remains possible. If the relevant profile is absent, describe the capture needed and its cost before taking it under the authorized scope. A capture holds the window it asked for; a stall inside it keeps its freeze as a profile of its own, which the capture's answer names, so the capture itself then covers less than it asked — requested is the ask, the monotonic bounds are what the record covers.

**Memory or storage growth.** Compare the same process and workload stage. Separate RSS, heap, external buffers, pending telemetry and retained disk data. Distinguish live database pages, reusable free pages and WAL. Growth, a high-water mark and a leak are different claims; use dated observations rather than an assumed steady state. A leak is the heap left after full collections rising across the process's life: censuses taken with `collect`, or the lowest heapUsed of each window of vitals. A census counts objects by type and names no holder: once growth is established, two heap snapshots taken apart name what grew and what retains it.

**The instrument is slow.** Start with read_performance({type: "losses", source: "live", limit: 1}): this reads process counters and pressure without taking the report gate or waiting for the worker. Its process-memory evidence leaves retained loss windows unread, not empty. Relate incoming work, persisted work, queue growth and losses; omit source only when you need a retained loss page, and use vitals for historical pressure. Stop widening requests into a slow instrument. A read-timed-out answer says the question did not finish, never that the store stopped: the worker and its queue go on, so ask a narrower interval instead of retrying the same one or reading it as an outage. Its queue, worker queries, retention and report projection are separate possible owners; raising a budget does not prove any of them faster.

**Verifying an optimization.** Preserve a baseline and repeat the same owned workload against the changed code. Prove the behavioral contract as well as latency, distinguish cold from warm, and check competing work. For a fix, earn red/green in a copy containing your own changes rather than disturbing a shared checkout. Stop when the agreed behavior and applicable checks are satisfied.

## When evidence is insufficient

Read the available operation catalog first. A missing report, unusable refusal or unexpectedly expensive diagnostic belongs to the instrument's owner: retain the exact command, expected answer, actual answer and its cost. File Tagma tool friction through file_reflection in the turn you meet it; it writes Tagma's own graph, so a read-only investigation files it too.

Use existing public reads and maintained measurement paths. A missing operation is not permission to build a scratch driver, query a foreign project's database, or bypass a refusal. Work on Tagma's own storage can inspect its implementation under that commission; ordinary users of Tagma should not need its source to read their evidence. Name the precise missing fact and the smallest additional authorized measurement that would settle it.

Once data identifies a responsible product operation, read_owners routes the code investigation. Repair the producer of the cost or wrong value, not a retry or cache at the first consumer that felt it. Do not read the whole performance package merely to use its tools.

## Report the result

Lead with the outcome. Keep the handoff short:

- **Measured:** symptom boundary, interval, process/build, workload and sample count.
- **Established:** conclusion and the span/report/experiment that supports it; distinguish observations, hypotheses and estimates.
- **Unmeasured:** missing coverage, failed reads and conditions the comparison did not exercise.
- **Next:** the justified next reading or repair; if work was authorized, its checks and delivery state separately.

A disproved bottleneck hypothesis is a useful result. Name it and change nothing on its behalf.

## Keep this skill current

This contract is maintained in .agents/skills/performance/SKILL.md of the Tagma repository; it is a skill of Tagma's own development and ships with no installation. The loaded tool schema and actual report settle what the running version supports.

- When authorized work changes performance queries, cursors, ordering, units, aggregation, retention, loss accounting or capture behavior, update the affected recipe here in the same change. Keep examples compatible with the public protocol rather than adding a second schema in prose.
- At the end of an investigation, ask whether a repeatable choice or misleading interpretation had to be rediscovered. Correct the relevant section when writing is authorized; otherwise report the proposed correction and its evidence. Correct your own misuse before calling it an instrument defect.
- Keep the general lesson, not this incident's ids, machine sizes, thresholds, logs or implementation plan. Replace stale guidance instead of appending a chronology. Hypotheses remain hypotheses until measured.
- Maintain the shipment source, not installed copies. Recheck catalog/load behavior and the affected public contract after a skill change; evaluate wording through investigative decisions, not substring assertions about the prompt.

For a specific contract needing more depth, use `read_owners` on the report's implementation under `packages/performance/src` or `apps/tagma/server/src/performance`, then read that owner. These are optional drill-ins, not a required orientation tour.
