# Rules

A project's rules have one surface in three parts:

- **`#rule` blocks** in the project's graph — the law's text, delivered to agents.
- **`tagma.config.ts`** at the repository root — what each check judges, under `inspections` by key, and the `format` commands that format the commits Tagma lands (the `format` reference). Each judgement reads the file from the version it judges.
- **`@runlith/tagma/rules`** and **`@runlith/tagma/rules/effect`** — the functions that describe inspections and format commands in that file. Tagma carries the package; the project installs nothing.

An enforced rule joins them: its enforcement document names a key of `tagma.config.ts`, a strictness, its triggers and its debt.

## A rule, or an order for now

The operator correcting how agents work beyond this task — what they would want from any agent tomorrow — is a rule: write it in that turn and name it in the answer. Priorities, plans and orders for now are not rules; in doubt, offer one in a line. A wish about the product's behaviour is a spec or a task, not a rule.

## Writing a `#rule`

The `#rule` tag prompt governs its form: one norm, the title states the obligation, the body only what the title cannot work without. What else decides how it works:

- **Sources** draw its reach: the code it is about, the code its check measures. A rule without sources measures the whole project within the inspection's base. An empty path in a reach means "the whole base"; an empty list reaches nothing. Anchor a symbol to the file declaring it.
- **`delivery`** decides where its text reaches agents. `prompt`: every thread's startup instructions — a norm across the project or wider than the code it was born in. `code`: when an agent reads or writes code its sources name — a norm about that code. Unset, a rule with sources is `code`, one without `prompt`. `set_rule_delivery` switches it and keeps the sources; its answer names how each thread's startup cost moved. Choosing `code` without sources succeeds with a warning: its text reaches no agent, while any check still measures the whole project; add sources with anchor_block or choose `prompt`. Delivery never changes the reach.
- **`set_rule_enabled`** false: the rule is not delivered, its check judges nothing and a new enforce_rule refuses `rule-disabled`; switch it on with set_rule_enabled `enabled: true` before enforcing it. Its document and debt stay. It is for correct law that should not bind now; a wrong rule is rewritten or replaced.
- Write the switch and delivery through set_rule_enabled and set_rule_delivery; these fields belong to their operations, so create_block and update_block direct their caller there.
- Tree position decides nothing: a nested rule overrides no ancestor.
- A rule in the global graph rides every project as `prompt` text and is never enforced: checks judge only the project's own rules.

## A measurable norm gets a check offered

A norm is measurable when the files alone decide each violation: an import crossing a boundary, a runtime load, a forbidden call or form, a file's size, a name, a linter rule. When you record such a rule, or meet one followed only as text, offer in a line to make it a check, naming what would judge it. Build and measure a check on the operator's word; enforce only what he agrees to after seeing the measurement.

Prefer few rules that hold to many that are ignored; a small project may rightly get none, and saying so is a complete answer. Law should not grow with the code: units found by pattern and placed by category take their place at birth, so a new feature needs no rule edit.

## From a rule to a check

1. **Read what stands.** `read_enforcement` — every rule, an enforced one with its key, strictness, triggers, debt and newest refusal; with `rule`, its engine and `revision`. `read_config` — the keys and format commands at HEAD and what judges each. `read_inspections` — one line per function this project's HEAD can use.
2. **Choose the judge**, in this order: a builtin; a linter the project already runs; the project's own program (`own-inspections`). Describe no builtin from memory: `read_inspections` with a function `name` answers the call signature and referenced types from the SDK declarations — the arguments `tagma.config.ts` passes; a builtin id answers its params schema with defaults and field descriptions. Both include the fingerprint unit, reach, languages and the ways out of refusals; `limitations: true` adds what it cannot see; `key` answers what a key resolves to at HEAD and the rules naming it; `map: true` answers the module map the `#module` cards draw. A builtin is neutral: every convention is a parameter, the opinion is the rule's. A builtin of a pack this HEAD does not use refuses `pack-unused`. A language no builtin reads is said plainly, with an interim judge — the language's linter or a program — and what that judge cannot see.
3. **Write the key** into `tagma.config.ts`. check_rules with `inspection: <key>` over the change runs it from this session's version, uncommitted config included: the config must evaluate, and it answers every violation in the reach of the version this change would land — what still stands once it lands, the residue of a migration in progress.
4. **Measure the reach.** Land `tagma.config.ts` with submit_work — a key no enforced rule names judges nothing — then check_rules with `over: "all"`, `inspection: <key>` and `blockId: <rule>`, or the module the rule will hang under: every violation in the reach at HEAD, as enforce_rule will measure it. Adjust the parameters and measure again until what it finds is what the rule means. Every figure you quote comes from a call in this thread; where check_rules is not offered, say that nothing can be measured here and propose nothing.
5. **Propose**, one line per rule: the rule (standing, or the one to write and where it hangs), the function and its key parameters, the triggers, the strictness, the violations found now, and the owner you suggest for each debt entry. Then your recommendation and its main tradeoff.
6. **On the operator's word**, write what was agreed — the rule, the tasks owning its debt — and run enforce_rule exactly as proposed. It reads the key at HEAD: a key not yet landed refuses `inspection-unknown`.

## `tagma.config.ts`

```ts
import { defineConfig, Files, Imports, Linters } from '@runlith/tagma/rules';

const eslint = Linters.eslint();

export default defineConfig({
  inspections: {
    modules: Imports.modules(),
    size: Files.maxLines(650, { files: { exclude: [...Files.tests] } }),
    'no-console': eslint.rule('no-console'),
  },
});
```

- The default export is `defineConfig({ inspections, format })`. A key is lowercase letters, digits and `-`, starting with a letter.
- `Files.tests` supplies the shared test-file globs, including e2e, benchmark and `.fixture` files; `Imports.modules` takes the corresponding filename infixes in `tests`.
- The file is plain synchronous data: it imports only `@runlith/tagma/*` and relative files of the same version, without the clock, randomness, the network, the environment or the file system. A function, a class instance or a promise in the value refuses. A config that does not build or evaluate refuses `config-invalid` with its file, line and reason.
- Every judgement reads the config of the version it judges: a landing its own commit's, enforce_rule and the re-measure HEAD's, check_rules over the change HEAD's with this session's lines. Editing the file is a change the gate judges, and a branch changes its checks with its code.
- Before landing an enforced key's changed description, run check_rules over `change` with `rules` naming its rule, or the default `all`: it measures that rule's whole reach in the session's built version, `owed` marking debt. Standing findings caused by the description alone do not set `refuses`; new crossings in the changed code still do. submit_work reports findings outside debt under `rechecked`, then re-measurement records those still standing as escapes, tracing new crossings to this commit. Absorb intended debt by its previewed fingerprints before landing. A version whose config lacks a rule's key, or does not evaluate, leaves the rule unable to run — `inspection-failed` at gate, a `watched` entry at watch.
- A builtin with no public function (`names`, `platforms`) is written as `{ builtin: '<id>', params }`, typed `Builtin<'<id>', Params>`; `read_inspections` with its id answers the params.
- For a tsconfig extending a generated file absent from the judged tree, `Loading.forbid`, `Imports.modules` and `platforms` accept `built`: exact `output` and tracked `source` paths relative to `base`, with `why`. The tracked copy supplies the generated config's aliases. A config inside `node_modules`, inside a git submodule the tree's `.gitmodules` declares, or outside the checkout — a package `extends` such as `@tsconfig/node22/tsconfig.json`, a shared company config, a package linked from a sibling folder or from a submodule — needs no `built`: `Loading.forbid`, `Imports.modules` and `platforms` read it from what the judging checkout holds, following links as TypeScript does, the same file for both sides, and a reinstall or a submodule update is judged by what the checkout holds now. One not installed names itself until the checkout's dependencies are installed, one in a submodule not checked out until `git submodule update --init`: `Imports.modules` and `Loading.forbid` fail `inspection-failed`, `platforms` reports each file resolving through it unresolved.
- `Imports.modules` with `reads: runtime` or `every` judges literal dynamic imports and literal `import.meta.glob` patterns, eager and lazy, with `!` exclusions: a source-relative pattern from its file, a `/`-leading one from the deepest of `roots` holding the file. `roots` names the directory the bundler resolves such a pattern from, a Vite project's `root`: the tree alone does not fix it. A glob's changed match set rejudges its importer when files appear or disappear. A load whose target is known only at run time — a nonliteral `import()` or `require()`, a glob with options other than `eager` and `import`, a `/`-leading pattern no root holds — is no module relation: it is named in `unjudged` and never refused. `unresolved` judges only a literal import that lands on no file; read the builtin's limitations for the supported forms.

## Enforcing: enforce_rule

- **Strictness.** `note` — the rule is delivered and runs only through check_rules. `watch` — it runs at its triggers and names what it finds; a landing lands and names it under `watched`. `gate` — it refuses at a `before` trigger, and acts as watch at an `after` one. `off` removes the enforcement; the journal keeps the document.
- **Triggers**, `on: [{ op, phase }]`. submit_work and merge_worktree judge the tree they land against its base, a merge against each parent; a submit_work trigger also judges a thread's commit_checkout (the operator's lands unjudged, its crossings recorded as escapes held by the operator, or without a holder by a rule whose inspection failed over it) and every `git commit` in a checkout of this project, through the commit gate hooks Tagma installs. edit and write, `after` only, judge the written file against HEAD and tell its writer. An operation that changes nothing judges HEAD. Any other refuses `trigger-unknown`; with none the rule runs only through check_rules. A rule that must hold the branch takes gate before submit_work and merge_worktree.
- **First enforcement** names `inspection` and makes every violation found debt, each owned by `owners[fingerprint]` or else `owner`: a standing task or spec that removes it.
- **Later writes** keep what a field left out says. `base` is the engine's `revision` from read_enforcement — null for a rule with none — and a write on another refuses `enforcement-stale`: read again and rebuild the input. It also refuses when HEAD moved what the measurement stood on since prepare.
- `checkout` selects a registered root; absent, an explicitly aimed cwd or branch, otherwise the only checkout holding this session's lines in the rule's project, or its main checkout when none does. Several held checkouts require an explicit choice. If the rule is absent from that checkout's graph copy, enforce_rule refuses `not-found`. `prepare` measures its HEAD, absorb searches this session's change there, and the write changes its graph copy; worktree debt travels with that graph on merge. The confirmation names the debt, what is absorbed and retired, and the duration. Under review the operator is asked when debt grows or an entry has no standing owner.
- Absorbing debt, lowering strictness, dropping triggers and `off` loosen the law: only on the operator's word, except absorbing the violation a gate refused, as "When a rule refuses work" says. Under review enforce_rule asks the operator whenever debt grows.
- `set_module` with `preview: true` measures the proposed map at HEAD and returns debt changes and escaped fingerprints without writing cards or enforcement. Without preview it measures again and writes both together, with the same `absorb`, `owners` and `owner`; its text starts with every re-measured rule's escaped count and first fingerprints. The preview's full `rules[].escaped` is available with `json: true`; after a write, read_enforcement with the rule pages the stored escapes.
- A test file importing a module its own has no relation to needs `importsTests` (the card's `imports-tests`), which opens that module to its test code alone; `imports` would open it to all its code. `cycles: refuse` judges only the relations open to all code: a test-only relation closes no cycle, so a lower module may be tested through one above it.

## Debt and escapes

- **Debt** is what a rule found standing when it was enforced, or what was later absorbed into it: each entry a standing violation, never an exception, keyed by its fingerprint and owned by the task or spec that removes it. read_inspections names each function's fingerprint unit. A count measures inspection units, not the sites displayed for a unit. A violation inside the debt passes every gate. Where the graph is stored in the tree, merge_worktree delivers its pending graph through graph.commit before choosing the source tip, including debt just accepted by enforce_rule; an undeliverable graph refuses with recovery, and graph.commit off refuses while graph files remain uncommitted. It carries ordinary debt only for violations still standing at that tip, up to each entry's count; a stale entry cannot excuse a violation the merge brings back.
- **Debt history** belongs to each graph copy's journal. When a changed debt count arrives from the graph tree, including merge_worktree, the mirror records its before and after entries at import time; existing history points keep their counts.
- **Debt only shrinks by itself.** For a rule at watch or gate with triggers, re-measurement follows landings and HEAD movement of open graph copies, including commits without hooks, pull, reset and rebase. The background startup sweep measures enforcing projects' main checkouts and journaled landings; opening a copy starts its own measurement independently of that sweep. enforce_rule re-measures its own copy and the main checkout. Closing a copy ends its HEAD observation and cancels its pending and running passes, preserving unmeasured journaled landings for replay; reopening compares HEAD with the confirmed measurement in its git directory. submit_work, merge_worktree and check_rules over a change wait for that copy's opening re-measurement to write each rule's debt, so retired debt cannot excuse a new crossing with the same fingerprint. The origins of new escapes are traced afterwards in a lane of their own, so tracing one rule holds neither another rule's re-measurement nor any landing; a tracing failure is reported and retried like a failed re-measurement, and escape notices to holders go out with the debt. Other operations do not wait. HEAD observation uses checkout events; it selects rules whose reach or declaration changed since their last confirmed measurement, and the driver measures changed paths where the inspection supports them. It retires each entry whose violation is gone; a note rule, or one without triggers, sheds debt only through a later enforce_rule. The re-measure adds no entry: debt grows only through enforce_rule or set_module — growing debt is a loosening done in the open. An entry's `count` only falls; occurrences beyond it are outside the debt like a new fingerprint.
- **Absorb.** A later enforce_rule with `absorb` — fingerprints, or `all` — and `owners` or `owner` makes what stands outside the debt debt, escapes included. A fingerprint absent at HEAD is looked for in this session's uncommitted change, judged as check_rules over the change judges it: found there, it becomes debt held for that change, stands until a landing carries it, and retires once its file lands changed without it or disappears from the working checkout, including before its first commit. Partial re-measurements include held files; cached starts confirm they still await landing before skipping inspection.
- **Owners.** Create a worktree's debt owner with create_block `checkout` naming the same root as enforce_rule, so the task stands in the graph that carries the debt. `owners` on a later enforce_rule re-owns standing entries too. An entry whose owner ended or was replaced shows as needing a new one and moves to nobody by itself. close_block, finish_block and supersede_block report the remaining entries per enforced rule and how to reassign them with enforce_rule `owners`, without blocking the act. With `commit`, finish_block inspects only this owner's debt at that version through the same debt evaluation as re-measurement, without waiting for its background pass or tracing escapes; an unavailable inspection is reported separately, never as remaining debt; enforce_rule records an entry without a standing owner as escaped instead. Whoever takes a debt task first finds how far its cause reaches, one file or a whole area; work over an area takes over the debt of every file it covers.
- **Moving a rule to another project.** update_block with a parent in another project's graph carries the rule's enforcement document, debt and escapes as they stand. Before writing it refuses `inspection-unknown` when the rule runs (watch or gate) on a key the new project's `tagma.config.ts` does not declare at HEAD; `relocation-shape` when the rule and a live owner of its debt would stand in different graphs — move them in one subtree or re-own the entries; `module-map-invalid` when either project's module map would stop holding together. The move runs no inspection: the new project's re-measurement takes the debt over as it does for a rule a graph merge brings.
- **Escapes** are violations outside the debt that stand at HEAD: left unabsorbed by enforce_rule, carried by a landing on a live peer's lines, or brought by an observed HEAD movement. A holder comes only from recorded authorship, never from the session that happened to discover the crossing; without that evidence the escape has no holder. A late carried hint must belong to the current history after the confirmed checkpoint, or name the same origin as an escape still standing there; it cannot claim a crossing that disappeared at that checkpoint and appeared again. A holder thread receives `rule-escaped` naming where it stands and what removes it. A new escape without a carried commit is traced to the first version where its fingerprint exceeded debt since the last confirmed measurement, using each version's inspection config; a config tightening can be that version. When the check itself changed since that measurement — Tagma's inspection code, the rule's reach, its module map or its debt — a violation the changed check finds standing at the measured version is recorded at that version with `changed: check`: the change let it in, and no older version is measured. A version without `tagma.config.ts` or without the rule's key carries no crossing of it, so the version declaring the key can be the origin. After reset or rebase removes the old boundary, tracing follows the current reachable history. Unreadable history or inspection leaves origin unproved: the escape is not recorded and the re-measurement reports the failure rather than inventing a commit, while the debt it measured stands written. So does a version the search reads whose inspection left unjudged a source that may hide the violation: any source for `loads` and programs, one in the violation's own file for the file-local builtins, none for `modules`, whose unjudged loads never become findings. An escape stands until its violation is gone; it never becomes debt by itself.
- check_rules `over: "all"` reads the whole reach at HEAD with `owed` marking the debt; read_enforcement with `rule` pages `debt` by owner, `escaped`, and `refusals` by place: each fingerprint's newest refusal with how often it was refused (`times`) since `first`, the most recently refused place first, and the list's `times` counting every refusal kept. A refusal recorded before its check said why has `said` null and keeps only the import it `reached`.

## How a violation reads

Every surface shows a violation the same way — submit_work's `watched`, `carriedViolations` and `rechecked`, a gate refusal, merge_worktree, commit_checkout, check_rules, read_enforcement's escapes and refusals, the Rules screen and the `git commit` hook:
- the norm: the rule, its title and strictness, once over its violations;
- the place and what the check says there, `packages/domain/src/summary.ts:1 loads @example/ui`, with `via a → b` when the chain has more than one link;
- `fix`: the check's own way to remove this violation, from its data — the door `allows` names, the allowance to declare. A violation whose check names none carries no `fix`; the general way out of its function (`generalFix` on a crossing, the engine's `generalFix` in read_enforcement) is said once under the norm — `fix:` when no violation has its own, `fix where a place names none:` when some do, each own fix then under its place.

The fingerprint is the debt handle, not part of what the text shows: check_rules lists `fingerprints`, and a gate refusal names them in the way that absorbs the crossing as debt.

## When a rule refuses work

- **`rule-violated`** from submit_work: a gate rule found a new violation on this session's lines or an automatically carried peer dependency; no approval mode or caller waives it. Code of another subject moves to its owner. Code that belongs where it stands, in a place shaped wrong, lands with its violation as debt owned by a new task naming the area and what was seen — absorb it with that task as `owner`. The worker that met the gate neither redesigns the area nor declares the rule wrong: that view goes into the task. A rule wrong for a class of code changes for that class in its inspection in `tagma.config.ts`, on the operator's word.
- Where `format` commands ran, the rules judged their result: the refusal writes that form into the working files and names them, so its lines and counts read there; fix the code in that form.
- A live peer outside `taking`, carried by explicit `whole` or a program-written file, keeps its violation in `carriedViolations`; it becomes their escape. Holders selected by `taking` are judged as this delivery.
- **`module-map-invalid`**: the module cards do not form a map the rule can judge, for example when their relations close a cycle the inspection refuses. Correct the cards through set_module; a refused set_module writes nothing, so resend it with the proposed map corrected. enforce_rule and gated landings report the same condition for an invalid standing map.
- **`inspection-failed`**: the check could not run, and the landing is refused, never passed through. Read its reason: a tool missing or exiting outside its codes, a file the adapter could not read, a program's reach holding a binary file because its description lacks `files`. Execution failures with cause `program` or `host` name the checker's checkout environment; their gate refusals give setup recovery in `unblock`. For a missing tool or dependency, run the repository's setup command in that checkout now; set the same command with write_setting, key `worktrees.setupRun`, for future worktrees. Changing the setting does not prepare an existing checkout.
- Program and linter timings include preparation and the checker run, even on failure. Rules sharing a checker show its full shared time; a merge sums its runs against the parents. check_rules, landing run reports and saved measurements use those timings. A program or linter re-measure with no changed or carried paths keeps the last actual measurement, including its duration and timestamp.
- Before landing, check_rules over the change answers `refuses`: whether submit_work would refuse. `whole` names files or directories to carry intact within the selected change, as in submit_work. Failed inspections leave the report incomplete; successful findings remain visible. `over: "staged"` judges an index like `git commit`; `tagma check` does the same, `tagma check --all` reads the HEAD reach. check_rules records nothing. A refusal is recorded among the rule's `refusals` for each crossing of a refused submit_work, merge_worktree, commit_checkout or `git commit`: the hooks' `tagma check --gate` (gate_commit) judges the same way and records, as op `git_commit`, an agent's commit it stops, or the operator's not let through with `TAGMA_ALLOW=1`.

## The Rules screen

The operator reads rules there; use its words when you explain.

- Strictness is a word everywhere: "Blocks" (gate), "Warns" (watch), "Text" / "Text only" (note, or no check).
- The list groups rules by the concern their check judges: "Who imports whom", "What loads where", "How code is written", "Size", "External linters"; a program sits under the concern its `defineInspection` declares. Rules without a check stand under "Followed as text", ones whose enforcement cannot resolve under "Cannot run", switched-off ones dimmed. A row shows the strictness, the key, the known violations (debt) with an arrow when they grew or fell, how many "slipped through" (escapes), and a recent rejection; the header counts rules, rules checked on every commit, slipped through and known violations.
- A project with no rule shows "Ask Tagma" — a thread asked to read the project and propose rules — "Write one yourself", and starter norms that each open such a thread.
- A rule's page puts the strictness switch first, then only the lists that have rows: "Slipped through", with "Ask an agent to fix" and "Keep as known…"; "Known violations" — debt by owner, its heading saying how far the debt grew or fell at its last change; "Commits blocked" by place, its twenty most recently refused places first and the rest on request. With nothing slipped through and nothing known, one line says the code has no violations, or that this checkout is not measured yet; a check that cannot run says so in its place, whatever the lists hold. Every list is one table, a row per place: when it was last met, `file:line` — a long path fades from the left and keeps the file name — what the check said, and how often; a refusal recorded before its check said why shows the place alone. A row opens to the whole phrase, its fix — the rule's general way out where the check gave none of its own — who and where (the act — landing, merge, commit or git commit — the agent or "you", the branch, the commit judged against), and "Open file". "What it checks" stays folded below the lists, its line naming the reach; open, it shows what the check holds, the checker, key and function, the landings it runs before or after, and timings.
- The operator acts there: the switch writes enforce_rule with the rule's revision, adding `submit_work` before when Warns or Blocks would otherwise run on no landing. Choosing Blocks while escapes stand, or "Keep as known…", asks one decision for all of them — keep them as known (a new task under the rule owns them, enforce_rule with `absorb: all`), fix them first (a thread draft is prepared; nothing changes), or block anyway (they stay escaped). A rule without a check shows "Text only"; Warns or Blocks there offers a key of `tagma.config.ts` — tried with check_rules over the reach, what it finds made debt of a new task — or a thread draft asking an agent to find one. The threads these buttons open stand in the checkout the screen shows, with the question drafted for the operator to send. What a check judges changes only through `tagma.config.ts`.
