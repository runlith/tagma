`ThreadEntryReader` applies steps to every decoded record with no mark check. By contract a step never changes a record in the current shape, so the reader always yields the current shape, and the mark decides whether to cast the whole thread. Maintenance decodes picked records with the same reader and never waits for the whole-thread mark; a current shape it wrote passes a repeated step unchanged by the fixed-point contract. Steps run one by one: a step shapes a whole event — payload, entry and messages inside — before the next one reads it.

A worker decodes with the same reader. Steps are functions and cannot be posted, so a reader carries `worker`, the start of a worker entry that binds that same reader to the native-harness fold server (`transcript/foldServer.ts`): `composition/rested.worker.ts` imports the composed `entryKinds` literally, and a test reader brings its own entry (`native-harness/testing/readers.ts`). The start is a literal `new Worker(new URL(...))` declared once beside its builder, so the platforms inspection judges the entry as a start, the production bundle emits it beside the server, and every reader built by that builder shares one worker. So the `.entries` transcript, the folded history and the guidance of an offloaded thread come out in the current shape before its queued cast lands. A reader without a worker fails the fold rather than folding unshaped, and a refused step fails the whole fold.

A cast's pass over the file — parse, step, rewrite, hash and compress every line (`rolloutStaging.ts`) — runs in that same worker, reached through the native part's `stage` port and handed the pending steps by name, never on the server's loop: the pass grows with the journal, and on the loop a burst of casts freezes every request the server serves. Queued casts (`formRested`) drain through one queue one thread at a time, because each commit takes the writer and a burst of reads over lagging offloaded threads would otherwise queue hundreds of commits ahead of foreground writes. A thread's return and its import from a rollout plan their store rows in the same worker too (`rolloutCarry.ts` through the port's `carry`): it scans the file, decodes every event with its own reader, folds the native history and transcript and cuts the rows into bounded units it keeps and answers one per ask, so the loop only writes one unit at a time and never holds the whole journal; the plan is dropped when its last unit is taken, or told to drop when the return fails.

A thread is born with mark `step = last` in the same record as its journal row (`insertRow`): its rows and file are written by current code, nothing to cast. Without this mark every new thread counted as lagging, and the first read after its first run unloaded and returned it whole — right under the run settlement whose out-of-lane reads then failed.

Nothing walks lagging threads: a thread whose mark is null or behind is cast only when accessed, and an unaccessed one keeps its old mark and bytes. A null mark — a row from before the `step` column — counts as lagging, so that thread takes every step on its next access, which the fixed-point contract makes safe. A read of an unloaded thread never shapes its file: `RolloutForms.readable` only refuses an unformable or older-than-base file, settles a publication a crash left behind and opens a compressed file; shaping is queued (`formRested`) and never awaited, while decoding applies the steps. The queued cast stages the shaped file beside the lane (`stagedRollout`, under `.staging`), writing nothing but a settle its unit re-checks, so readers neither wait on the lane nor on `uses.rest` while it streams; only the commit — store record, rename, settle — runs in the lane under `uses.rest`. A cast that rewrites the file moves the cursor offset the `.entries` transcript is keyed by, so it also transcribes the staged file beside the lane and renames that transcript in with the file: the next frame finds a transcript matching the new key and never folds the whole thread. A new entry step needs no transcript rebuild, since transcript entries are decoded through the reader when read; a payload step that changed what the fold places would reach a standing transcript only when that thread's cast publishes its own. The commit first compares what staging stood on (form row, cursor and refusal offsets, rest stamp, file size and mtime) and answers `moved` without writing when anything changed: a record appended meanwhile is never lost or reshaped by a stale stage. A commit refused because the thread is in use, or moved, stays owed and runs again when the thread's last use ends.

`formRollout` applies steps to the file of an unloaded thread or to a file with no thread row in the store; it sets the mark only for a standing row and never touches the mark on `last`. A step spans the meta of the header and tail records: a moved rollout home may be the only recovery source a SQL migration never reaches. The journal copy in SQL is collapsed and rewritten by maintenance independently of the file, so a shaped file says nothing about store rows. A SQL-lying thread is cast whole only in one journal-lane pass: catch the cursor up, unload without transcript, shape the file, return. While a run is going or the file lags, cast waits for the next access. The return rebuilds `thread_log`: `historyThrough` and `entriesThrough` are set from the rebuilt rows, while `strippedThrough`, `footprintsThrough` and `boundedThrough` start from nothing and the three maintenances walk the thread once more. That is correct, not a loss to carry over: the file holds whole facts (projection refuses a folded one), so the return writes back the tool facts stripping had folded, the measurement footprints folding had cut and the oversized tool bodies bounding had moved out of SQL, and each cursor's claim "everything through here is rewritten" is false for the returned rows. Every return does this — a rest and return of a rested thread as much as a whole cast — and the re-walk is idempotent: bounding writes its output files by content. Exception — lagging only by steps with no `payload`, `entry` or `message`: SQL event rows never change through them, so `formRollout` shapes such a thread's file in place, parsing no event rows, and `reading` in SQL in the same record, with no unload or return.

A step refusal — on a file row, in `stream_tail`, `context_reading` or `pending_interaction` — refuses the whole act and is recorded in the mark refusal. Paths SQL reads over many threads are declared in `store/fields.ts`. Instruction-snapshot selection inside one thread applies the runtimeState key filter only after the shape mark; before it, it reads that thread's messages and shapes them before the key search. A step that changed such a path refuses: that is a history-table schema change.
