`ThreadHosting` hands a flow whose agent loop runs outside Tagma (a Claude or Cursor runner) a native agent's run without its loop: `RunAssembly.hosted` prepares it with the same `ThreadAgent.prepare` as a native run (admitted runtime sources, output scope with call holding, profile, `modeOf` by the thread's law, prompt freeze and applying the deferred prompt at the run boundary), and holds the preparation together with the handle: every turn opening orients by its context; a catalog-revision change before a step re-resolves the tools with the same preparation, without rebuilding the whole run, and `AgentRunner.host` is the same door as `run` (agent rules plus the deferred-tool rule and `AgentCalls`). No tool, rule, or policy exists in a second copy.

- **A step instead of a loop.** What the native loop achieves at `beforeStep`, hosting does at turn opening and after every call: it evaluates the rules over the thread history, writes guides as a `runtime-guidance` event (by it `project-instructions` and other rules see what is already delivered), and hands them over as text, while `exclude`/`restrict` narrow the step-available catalog. A transport with `toolCatalog: 'turn'` receives all admitted schemas ahead: the model can name a tool after a skill unblocks it without an SDK catalog change, but the native door still refuses a call the step rule excludes. A transport with `toolCatalog: 'dispatch'` (a CLI that lists tools once) keeps deferral and receives every admitted direct tool whatever the step, never a deferred one; its `tool_search` answers carry each revealed tool's definition, and its runner calls a revealed tool through `call_tool`, which the bridge hands to this door under the tool's own name. Thus law, `$skill`, delegation, refused MCP servers, and skill gating reach Claude by the same road as a native agent. A keep-warm run assembles no new turn context; tool calls, `ask_user` included, close with the same refusal as a native one-text ping, without execution.
- **Place change at a step.** A thread's move to another worktree reaches a hosted run through the same context boundary as a native loop (`makeRunBoundary` → `contextBoundary` → `door.admit`; at hosted — `AgentHostedRun.place`). A hosted-run step passes the boundary only while the run holds no open call (`Hosted.open`). A call stands in `open` under the same thread lock under which the step decides whether to pass the boundary. Otherwise a publication after one outcome would shift the door generation under a neighboring call already prepared and awaiting confirmation, and the door would refuse it as a call with someone else's preparation. So calls begun before the move complete in the earlier place, and the first call after the last of them executes in the new one. A call of the same message arriving over MCP after the boundary executes in the new place. Run assembly passes the boundary at once and restores the admitted generation, and `ThreadAgent.prepare` opens — on native and hosted alike — the generation the run already admitted (`RunAssembly` reads it from `ThreadRunContexts`), not the zero one: a run reassembled after a server restart does not open the place the thread already left, and does not fall when that worktree is gone.
- **The vendor session's place.** A profile whose agent Tagma serves (`hosts`) launches the process and opens the vendor session in the thread's current place (`SessionPlace`): `ProtocolLauncher` at every launch, including resuming the same session, `ProtocolAlignment.cwd` at every session opening. The session's saved cwd decides nothing for them. Tagma executes the tools, so the vendor cwd is only its storage key. After a move and deleting the earlier worktree, a restart would otherwise never stand up in a nonexistent folder. A vendor session opened in the earlier place is not found in the new one: the driver opens a new session from Tagma's journal, as after any `notFound`. A CLI with its own agent (`hosts: null`: terminal transport, Devin) works in the launch folder: while its turn runs, `move_thread` refuses `harness-pinned`, and its idling session is finished by the move.
- **The request's composition.** The run's first turn opening writes a `composition` entry (turn prompt, context, catalog) with the same function as a native run: without it the hosted thread's context breakdown would show the system prompt and tools as zeros.
- **History instead of memory.** Every call is written into the thread history as messages naming their run in the record's `runId` (the call with the transport's assistant message, the outcome by hosting), so rewind, branch and restore cut them with their turn, and `discoveredToolNames`, `tool_search`, and `load_skill` see the same as in a native run, and open deferred tools survive the process. The hosting commit publishes the written deltas into the live feed: the external loop does not call the step's native publisher, and without that publication a subscriber would learn of the write only at the next facet change or run end.
- **Binding to the run.** Hosting holds one assembly per active thread run (built once under the semaphore) and releases it on the run's settlement event: stopping the assembly's `RunStop` (`Hosted.halt`), which `AgentRunner.host` bound to `AgentCalls`, stops the door: every open foreground call of the run is first declared stopped, then its fibers are interrupted, open `ask_user` questions are written removed, the output scope closes after the last held call. The door writes `tool-call` with the same combinator as the native loop, with an explicit `{run}` parent: the HTTP input carries no turn fiber, and someone else's current activity does not become a tool's parent. The separate `ask_user` path also opens `tool-call`; repeating an already-answered call returns history and creates no new activity.
- **Permissions.** An `ask` verdict of a hosted call is set by the door itself inside the call: hosting hands it to `door.settle` with `confirming`, and the call life asks through the `CallHooks.asking` port, which the run assembly fills with `callConfirmation` over `Questions`. That is the same `thread.tool.confirm` confirmation the native run sets (`toolQuestionOf` assembles the entry from the call preparation), to the same addressee; "Allow" executes the call, "cancel" and the expired term answer with a refusal without execution. While the call stands in front, the question stands in the run; a call taken into the background removes it from the run and sets the same question to the thread (the `approvals:<thread>` approval area), where the answer is awaited with no turn. Term — `reader.withinMs` from the call preparation: while no answer, the question is written removed when the term expires, and an answer recorded past the term does not permit the call. The question runs the shared `Questions` core (`thread/run/Questions.ts`), not hosting: it finds it by `toolCallId` among the active run's entries, so a call repeated after a server restart finds the open or already-answered question and uses the answer once. The term is counted by the shared `QuestionDeadlines` machine, the same as native parking; an expired question receives the `lapsed` status, and a late answer does not permit the call. `ThreadModes` makes the bypass-mode change: it walks around `Questions.open` and answers every open confirmation of both roads with the same `bypassAnswers`; a call that stood on `ask` before the mode change but sets its question after it sets no question — `ask` reads the live mode (`modeOf`). The operator's answer goes through `Questions.holds`/`answer`; the run end closes its questions through `Questions.close`.
- **Waiting.** Hosting does not write the run's `awaiting-question` stage: when any question of the run opens or closes (by the run entries), it reports to the `HostedAwaiting` port, and the ACP driver, which holds the turn's live flow, owns the stage: it seals the unfinished message before publication and reopens the flow after. `RunStatus.openQuestions` reads the same run entries (`openQuestionsOf`) as `Questions.open`, so it sees both roads' questions. Question closings at hosting release are reported too, and the stage write (`HostedRuns.waiting`) checks that the run still stands. Thus the thread and agent lists see the hosted thread's wait; it does not enter `facet.question`, and no `envelope:ask` goes to the parent.
- **Once, and only in its own run.** A call answers only the run this server holds (`ownerId`); until the run is taken by `adopt`, hosting waits for ownership up to `takeoverAfterMs`, then refuses `ThreadRunNotHeldError` (`run-not-held`), and the runner repeats the call. Past `reached`, hosting reads the call entry by id: an answered call replays its recorded result, `queued` executes, and `started` or an entry without `execution` means the call ran in the server's earlier life, so hosting writes `output-unknown` without executing. Repeated requests join the same in-flight fiber; its completion releases the fiber and transient start metadata even if the requesting HTTP call went away. A tool's work starts only after the `started` entry commits (the door's `onExecution` callback at `admit` moment); `ask_user` writes it before the question: that holds both dedup and `cancelled` at `queued`/`gated` at the run end. A call taken into the background before execution does not write `started`: its entry is already closed by the receipt, and the outcome reaches the thread as a notification. Every call entry checks in decide that the run still runs and is ours, so a late outcome after the run end is not written.
- **Order and waits as at native.** `placeSealed` (`hostedOrder.ts`) puts the sealed message's calls into the door's `CallOrder` with their claims, in message order, so a call that arrived over MCP before its predecessor stands `queued` with `after` and prepares in its own turn. An early call the vendor closed before MCP (a closed entry without `started` at a call that never reached hosting) is declined in the door and holds nothing; the door's receipt proves a call reached it even after its hosting fiber ended, so a background receipt never triggers that decline. A background call releases reads and the barrier when it starts executing, and holds the final `write` claims until the work ends. When a blocking call awaits confirmation, a later call behind it receives the same-batch refusal as at native. Words arrive at `AgentRunner.host` through `HostedWords`: words the transport already handed to the running agent and it has not read yet (`TransportRuns.handed`; the transport decides what counts as handed — at ACP it is the frame the host accepted); they are re-read by `ThreadChanges`, and the transport's `handed` report publishes the change after the handoff commits. Waiting yields only to such a word, and a call's answer names all such words (`words`), and the runner hands the outcome to the vendor loop only after each of them stands in that loop's queue. Thus the "outcome first, then unread words" order stands by construction, as at a native step, not by an HTTP call-answer versus word-delivery race. A confirmation question races `door.callStops`: a call's Stop removes the question. `display(threadId, name, input)` returns the input's display from the already-built assembly, without a semaphore, for the projection's initial entry.
- **History for a new session.** `ThreadHosting.history` yields the thread history paired for the provider and with hydrated attachments, and the `read_hosted_history` operation (`hostedHistory.ts`) translates it into its wire's messages: text, calls, and outcomes, no reasoning. The runner assembles the vendor session from it when the thread arrived from another road or the history slice mismatches the session prefix.
- **Which agent.** Hosting operations take the agent from the thread facet (`hosts`, recorded at birth from the harness profile), not from the caller; a thread without one refuses `not-hosted`. The thread-definition reads — the `read_agent_skills` skill catalog, its instructions, and `read_thread_agent` — take the same agent through `agentOf` (`packages/agent/src/thread/rows.ts`): a hosted thread's `agentId` is always `harness`, which has no capabilities, and by it an ACP thread would receive neither skills nor its agent's law.
- **`ask_user`.** A question is written into the transcript open and awaits the answer arriving through the harness's `answer` (`holds` tells its own questions apart — both `ask_user` and confirmations). The transcript entry is the truth, not memory: after a server restart `holds` recognizes the active run's open question, the answer is recorded, and a repeated call with the same id (the runner repeats a call while the server is unreachable) receives the recorded answer instead of a new entry. Confirmations and `ask_user` travel one placement-and-wait road.
