An entry's wire form is a JSON codec (`Schema.toCodecJson`) of its kind's schema on both sides: the wire schema's outer side is `Unknown`, and RPC serialization checks it only with `isJson`, so a memory value with an optional key of `undefined`, handed over as is, drops the whole subscription frame. So the opaque kind fields (`toolInput`, `toolOutput`, a question's `data`) are declared `Schema.Json`: a producer translating someone else's value through `toJson` (`toolInputJson`, `toolConfirmationData`) meets a compile refusal for non-JSON. The wire codec uses the call context's `ThreadEntryKinds`: in the browser, features contribute the server owners' schemas to the `WireEntryKinds` point. `Door` and `Live` hand every request and subscription one reader (`wireEntries`) whose products are a source `makeThreadEntryReader` reads on each decode: it resolves each entry against the point's current items, so a subscription already running decodes a kind that joined after it started. An unreadable entry with kept identity becomes `ThreadEntryUnreadable`, carrying the original `ThreadEntryUndecodable`: it takes the line's place without hiding neighbors or admitting an unknown body. Damaged optional metadata does not block that diagnosis; of it only the read fields survive.

The server reads stored entries the same way: `ThreadEntryReader.stored` and `storedForm` answer such a line instead of a refusal, so one entry neither fails a window, a fold or a feed frame, nor stops the thread running. The line carries the record it stood on and `toJSON` answers that record, its rewind mark included, so a fold, a rollout export or a return into the store writes the original bytes back: the entry reads whole again once a form step or its kind arrives. Only `decode`, `read` and `admitThreadEventPayload` still refuse: they admit a new fact, and a new record no kind reads must never be written. `toJSON` is an own member because folds spread entries, and a function cannot cross `postMessage`, so what leaves a worker goes through `crossingEntry` first. On the wire the line is its diagnosis (`type: entry-unreadable`, identity, `refused`), never its body; the client reads it back as `ThreadEntryUnreadable`, and an older client still reads it as an unreadable line.

Transcript reads decode only what the transcript uses (`transcriptFact`: the entry and the rewind, restore, withdrawal and branch marks), so a model message no build reads does not blank the thread; such an event, or a damaged mark, stands as one line keyed by the event. History folds still decode the whole event and refuse: a model history with a hole would be silently wrong, so such a thread opens and its run fails typed. A tail entry that does not read is dropped when its run closes, since a new fact must be readable, and is told. The fold into `thread_entry` (`project`) keeps refusing event-level damage so no row claims a fact it could not read.

Every such read is told to the operator's error list as a `degraded` note on the thread it read (`ThreadEntryReader.degraded`, witnessed by `threads/journal/readWitness.ts`), so the operator opens that thread from the note; a rollout line names its thread by the `threadId` its writers record. The witness tells each failure of a thread once while its note stands in the list, asking `ActivityFaults.since` where the list's window begins: after Clear or once the note ages out of retention, the next read of a record that still fails tells it again, with no restart. The witness is late-bound because the activity store stands above the reader in the layers; reads before it binds wait in a bounded buffer. A fold in a worker reports its degraded reads with its read notes (`RestedRead.degraded`) and the server tells them. Facts with a safe absence read through `readableRowFact` and are told the same way: a thread row's birth, parked question and context reading, a run row's progress, usage, stream tail, failure, ending, notification, stop request and withdrawn words, and an inbox item, which is passed over so one item stalls neither its thread nor every waiting wake. A thread's birth reads through one `readThreadBornOf` in the thread row, the list summary and `thread-record`'s facts alike, so one damaged birth is one note; `thread-record` stands below every reader's owner, so it tells into its own `degradedReads` hub, the same buffered mechanism the reader uses, which the witness joins through `ThreadRecords.readDegraded`.

A thread's authority, transport and capabilities have no absence: they read as safe values marked `unread`, told the same way, and the readers that act decide by that mark ([[a4a61a64]]).
