## 1. Agent.create / Agent.resume / send

- `makeCursorAgentOptions` gives `model: cursorSdkModelSelection(selection)`, `name: "T3 Code <threadId>"`, `mode: interactionMode === "plan" ? "plan" : "agent"`, an optional API key; `local.cwd` passes only when the runtime cwd is non-null. `local.autoReview` follows policy, `settingSources: ["project","user","team","mdm","plugins"]`, `sandboxOptions: {enabled}`, `enableAgentRetries: true`; `mcpServers` joins when a T3 MCP session exists (`C/adapter.ts:295–334`). The comment explains the explicit settingSources by the SDK loading no CLI settings without that list: rules, skills, hooks, MCP, team/MDM, and account plugins (`C/adapter.ts:295–306`).
- With an explicit approvalPolicy, auto-review is on for any value but `never`; without one — for the `approval-required` or `auto` runtimeMode. Without an explicit sandboxPolicy the sandbox is on outside `full-access`, except Windows with auto-review; with an explicit policy it is off only for `type: "dangerFullAccess"`. The Windows comment explains the SDK has no filesystem sandbox there; the fallback comes with one warning per session (`C/adapter.ts:184–207,2144–2153`). Other sandboxPolicy fields never reach the SDK options here (`C/adapter.ts:188–207,323–330`).
- T3 never gives the working conversation agent `local.store`, `tools`, `disallowedTools`, `systemPrompt`, `local.customTools`, or `agents`: visible in the full options constructor (`C/adapter.ts:308–334`). T3 declares `acceptsSystemContext: false`, `acceptsDeveloperContext: false`, `acceptsSyntheticUserContext: true` (`C/adapter.ts:151–159`); it adds its orchestration instructions to the first user prompt when a T3 MCP exists, runtime instructions to each turn's ordinary prompt, never through systemPrompt (`C/adapter.ts:2195–2206,2242–2248`; `P/orchestrationInstructions.ts:104–119`). That never checks whether a Cursor account could override the system prompt.
- The wrapper opens either `Agent.create(options)` or `Agent.resume(agentId, options)`; ensureThread uses create, resumeThread/startTurn/snapshot use resume. A live agent with the same native id is reused; with a different one it closes (`C/CursorAgentSdk.ts:383–389`; `C/adapter.ts:2117–2169,2261–2268,2458–2465,2488–2504,2581–2591`). Before each open, the driver takes the working API key from the account-specific auth and lays it over the options (`C/driver.ts:174–198`).
- An ordinary `agent.send(message, options)` gets `model: {id,params?}`, `mode: plan|agent`, and `onDelta`; the working caller never passes `idempotencyKey`, `local.force`, per-send `customTools`, or `mcpServers` (`C/adapter.ts:2271–2290`; `C/CursorAgentSdk.ts:454–468`). That the types/journal sanitizer hold these fields never means use: the journal can record `force`, the fact of custom tools, and the idempotencyKey, but the caller never sets them (`C/CursorAgentSdk.ts:127–135,283–301`). The send comment on replacing ambient MCP is about override danger; the test directly checks no per-send mcpServers (`C/adapter.ts:2273`; `C/adapter.test.ts:69–94,196–200`).
- Message is a string or `{text,images:[{data: base64,mimeType}]}`; files travel as paths through a shared attachment prompt, native image bytes are read separately. An empty message with no attachments is rejected. A bare `/compress` with no attachments needs no wrappers or runtime instructions (`C/adapter.ts:2173–2248`).

## 2. The event and turn model of T3

- The working runner never reads `run.stream()` and never registers `onStep`: it uses `onDelta({update})` at `send` and `run.wait()` for completion. Until the run returns, SDK updates buffer; then a sequential promise chain logs the update, calls the Effect handler, and keeps the handler's first error. `wait()` waits for the SDK result and the callback-chain tail both; a callback error becomes the `run.wait` error (`C/CursorAgentSdk.ts:425–465,469–530`). Another buffer in the adapter holds updates until the ActiveCursorTurn and providerTurn id exist (`C/adapter.ts:2271–2340`).
- `text-delta` appends an assistant segment; `thinking-delta` a reasoning segment. A type switch, tool update, `step-completed`, or `turn-ended` closes the current segments; `thinking-completed` closes reasoning. Synthetic native item ids look like `assistant:<sdkRunId>:<segment>` / `reasoning:<sdkRunId>:<segment>` with weak strength (`C/adapter.ts:967–1159,1910–1953`). Assistant gives `node.updated`, `message.updated`, `turn_item.updated`; reasoning gives node and turn item, with text/streaming and started/completed timestamps (`C/adapter.ts:967–1125`). When no streamed assistant segment ever existed, the non-empty `RunResult.result` becomes the final text (`C/adapter.ts:2342–2358`).
- `tool-call-started`, `partial-tool-call`, `tool-call-completed` pass through `handleToolUpdate`; live ordinary calls sit in a map by `callId`, args/toolCall replaced by the latest update, completed removed from the map. Ordinary-update fields trust the SDK `ToolCall` type; there is no universal parser for unstable JSON here (`C/adapter.ts:1349–1370,1844–1896`). `result.status === "error"` means failure; on a successful MCP the check additionally reads `result.value.isError`; the output picks success.value or the error (`C/adapter.ts:387–420`).
- Shell projects to `command_execution` (command, stdout+stderr, exitCode), write/delete/edit/generateImage to `file_change` (path, newStr/diff/counts where present), read to `dynamic_tool/Read`, glob/grep/ls/readLints/semSearch to `file_search`, MCP/others to dynamic_tool. MCP gets `mcp__<providerIdentifier>__<toolName>` and `args.args` as input (`C/adapter.ts:422–460,478–540,1235–1346`). Lint coordinates translate 0-based to 1-based when valid (`C/adapter.ts:512–528`).
- The shell-output update has no reliable link to a specific call in this mapper: the last live shell is picked, rows pulled from `event.text|output|data|stdout|stderr|chunk`. A live chunk goes as `command_output.delta`; the adapter keeps only a 256 KiB tail for fallback and never writes a growing accumulated output on each chunk. The comment names the former quadratic growth of the event store. The full final output is preferred over the streamed tail (`C/adapter.ts:824–826,1235,1898–1908,1954–1979`).
- `createPlan` gives separate plan/node/turn-item with markdown; `updateTodos` a todo list where cancelled drop, inProgress → running, completed → completed, the rest → pending (`C/adapter.ts:543–559,1373–1542,1855–1873`). `task` becomes a provider-native subagent and a synthetic child app thread with no separate providerThread/native thread id. `partial-tool-call` for task is ignored; the model comes from args, may refine on a late update, and stays on late empty args.model. The child's answer gathers from conversationSteps and resultSuffix (`C/adapter.ts:1544–1667,1781–1841,1874–1884`).
- Two forms of a subagent's nested conversationSteps are supported: `{type:"toolCall",message,…}` and a protobuf-like envelope with a `*ToolCall` key. The second parses as unknown records: success/error/permissionDenied; read.path restores from args or result.success, else `<unknown path>`; shell.command from args or permissionDenied, else `<unknown command>`; glob/grep have field fallbacks and nested workspace-result conversion. An unknown `*ToolCall` stays as a generic type/args/result. That is a bounded recovery of that concrete nested shape, never a promise to support any payload (`C/adapter.ts:562–787`).
- `RunResult.status`: finished → completed, cancelled → cancelled, error → failed; an app-set interrupted has priority. The finalizer closes text, remaining tools, and native subagents, updates the provider turn/thread, and issues `turn.terminal`; an unfinished native child on a normal parent end becomes idle, on cancel/error gets a terminal status (`C/adapter.ts:2006–2115`). The `result.error.message` error prints explicitly; a thrown runner error gives transport_error with the cause text/code/HTTP status (`C/adapter.ts:2359–2411`; `C/CursorAgentSdk.ts:39–64`).
- Everything missing from the `InteractionUpdate` switch is ignored: in particular usage/context counters, summary-started/summary-completed, and other summary updates are never projected here. `onStep`, stream events `system/init`, `assistant`, `thinking`, `tool_call`, `usage` are never read on a separate channel; `agent.getUsage()` is never called (`C/adapter.ts:1910–1984`; `C/CursorAgentSdk.ts:454–565`). So SDK-side usage never becomes T3 turnTokenUsage through this adapter. Account-wide spend is read by a separate reader, described below. `compactThread` sends `/compress` as an ordinary startTurn; there is no result summary/compression-boundary event in T3 as a separate event here (`C/adapter.ts:2177–2179,2520–2524`; `C/adapter.test.ts:365–506`).
- The provider-core contract requires runtime events/ensure/resume/start/steer/interrupt/snapshot; compact is optional (`P/ProviderAdapter.ts:550–628`). The manager routes command_output straight to the live hub, other events to the turn subscribers (`O/ProviderSessionManager.ts:1931–2023`). The ingestor translates them into domain events, dedupes unchanged nodes, bounds file-change/tool-image storage, and creates an error turn item on failed terminal (`O/ProviderEventIngestor.ts:558–713`). The SDK run id becomes T3's strong nativeTurnRef, the agent id the strong nativeThreadRef (`C/adapter.ts:248–280,1986–2003,2293–2296`). A successful provider terminal is still not a final completed app run: RunExecutionService first puts run/root into waiting and takes a checkpoint capture; an unsuccessful one keeps the terminal status (`O/RunExecutionService.ts:635–743`).
## 3. Steer, cancel, queue, and recovery

- T3 Cursor capabilities: active steering false, steering via interrupt/restart true, queued messages true, interrupt true, interrupt quality strong; pending runtime requests never survive a restart; no native rollback/fork (`C/adapter.ts:85–110`). `steerTurn` answers typed unsupported: T3 never calls SDK `Run.steer()` (`C/adapter.ts:2525–2531`). By default an input on a live turn with these capabilities prefers queue: CommandPolicy prefers active steering, then queue, then interrupt/restart. Explicit steering/forced restart with interrupt support picks `interrupt_restart` (`O/CommandPolicy.ts:170–199,273–305`).
- The queue belongs to the app, not the SDK queue; the contract itself calls it app-owned queued turns (`O/CommandPolicy.ts:273–281`). On steering restart T3 keeps the same app run but opens a new attempt/root, the old attempt superseded, the root interrupted, reason `steering_restart`; the outbox effect first does `interruptAndAwaitTerminal`, then a new `providerTurnStart.start` (`O/Orchestrator.ts:4391–4409,4622–4683,4782–4800`; `O/EffectWorker.ts:331–377`). That is a new SDK send, not steer in the old run.
- Interrupt checks the concrete providerTurnId, sets interrupted=true, calls `run.cancel()`, and waits for adapter completion up to 10 seconds; when `wait()` never finished it logs a warning and terminalizes interrupted itself. Late updates drop on finalized; an ordinary live run has no "long time with no text → stuck" timer in the Cursor adapter (`C/adapter.ts:1914–1916,2006–2018,2532–2555`). The runner counts an AbortError in the cause chain as the expected cancellation and suppresses it only on cancel; other cancel errors stay errors (`C/CursorAgentSdk.ts:239–252,541–563`).
- The ordinary agent store is not T3's choice: `Agent.create/resume` get a local cwd with no local store (`C/adapter.ts:308–334`; `C/CursorAgentSdk.ts:383–408`). So this store's path/shape is the SDK default, and the exact default path is undetermined from the T3 code as read. On listRuns/cancelRun the runner passes the runtime local, cwd, and store only when the store was explicitly given (`C/CursorAgentSdk.ts:400–408,475–492`). History snapshot reads through `Agent.messages.list(agentId,{runtime:"local",cwd?})`, with no store argument of its own; text restores from several shapes, while attachments/turns/requests never restore into the snapshot (`C/CursorAgentSdk.ts:567–583`; `C/adapter.ts:790–813,2581–2635`).
- After `Agent.resume` the runner allows exactly one abandoned-run recovery attempt. When the first send throws an Error with `already has active run`, it calls `Agent.listRuns(agentId,{runtime:"local",cwd?,store?,limit:1})`, looks for a running status, calls `Agent.cancelRun(id, same options)`, and retries the original send; when no running one is found it returns the original error. Then the recovery flag is off. `force` is never used, and the running record's age/heartbeat is never checked: abandoned here means resume plus that exact conflict plus running in the last result (`C/CursorAgentSdk.ts:235–237,409,469–499`; `C/CursorAgentSdk.test.ts:134–174`).
- The SDK lives in the server process, so its live objects/callbacks never survive that process's death. The shared startup/shutdown recovery cancels unfinished app runs/attempts/provider turns and closes streaming, marks sessions stopped; queued messages hold, while non-resumable pending runtime requests become expired/cancelled (`O/ProviderRuntimeRecoveryService.ts:79–88,239–249,300–456,590–600`). With `continueThreadsAfterServerUpdate` on, a separate continuation effect/run with `Continue where you left off.` may start — never a reconnect to the old JS Run: eligibility needs a strong native thread, a matching live provider turn/session, and no blockers (`O/ProviderRuntimeRecoveryService.ts:624–639`; `O/RestartContinuation.ts:31–34,117–186,189–205`).

## 4. Models

- Discovery calls `Cursor.me({apiKey})` and `Cursor.models.list({apiKey})` in parallel, with no extra models.list arguments. Inside CursorSdkCatalog the model cache keys on apiKey, capacity 32, TTL 30 minutes only for a successful nonempty model list; error/[] get zero TTL, the user rereads each time (`C/CursorSdkCatalog.ts:68–90`). The driver hands that catalog layer straight to checkProvider, so these numbers describe one service instance; cache survival across fresh layer builds is unproven by this reading (`C/driver.ts:217–260`).
- SDKModel.id/displayName become slug/name after trim; empty ids/names and duplicate slugs drop, isCustom=false. Parameters come from `model.parameters`, their defaults from the params of the first isVariant.default; variants never become standalone models (`C/status.ts:90–105,163–183`). T3 pins no separate reasoning-level list, thinking/max-mode, or fast values: any parameter ids/values the backend got become descriptors by the shared algorithm. Display priority is effort/reasoning, context, fast, thinking, the rest; only context→contextWindow and fast→fastMode rename (`C/sdkModel.ts:5–37`; `C/status.ts:96–160`).
- Two boolean values true/false make a boolean descriptor, the rest select; displayName is the label, the default variant sets currentValue/isDefault. Empty parameter ids/values and duplicate descriptor ids drop (`C/status.ts:106–160`; `P/snapshotProbe.ts:178–224`). That the live Cursor catalog has a concrete `max` is unproven here: a generic parameter value when the backend declares it, never a separate T3 policy (`C/status.ts:114–157`; `C/sdkModel.ts:58–70`).
- On send the model travels as `{id,params?:[{id,value:String(value)}]}`, auto → default, contextWindow→context and fastMode→fast. That function never validates values against the catalog and never completes missing default params (`C/sdkModel.ts:58–70`). T3 Cursor's shared default model is auto, the helper text-generation one composer-2 (`packages/contracts/src/model.ts:146–166`).
- Shared aliases: composer→composer-2; composer-1→composer-1.5; composer-1.5 stays itself; opus-4.6 and opus-4.6-thinking→claude-opus-4-6; sonnet-4.6 and sonnet-4.6-thinking→claude-sonnet-4-6; opus-4.5 and opus-4.5-thinking→claude-opus-4-5. That is the shared normalizeModelSlug, while normalizeCustomModelSlug only trims (`packages/contracts/src/model.ts:182–192`; `packages/shared/src/model.ts:350–373`). A thinking-suffix alias alone never enables the thinking parameter: the table changes the slug, not the options (`packages/contracts/src/model.ts:182–192`; `packages/shared/src/model.ts:350–373`).
- The context budget first takes the explicit selection.options.contextWindow (even when the catalog never listed that value), otherwise the picked model's descriptor currentValue; only a positive safe integer in `N[km]` form counts, multipliers 1000/1000000, else undefined (`C/sdkModel.ts:39–56`). The driver keeps the last built-in catalog when the next probe fails; the initial/failure snapshot has only customModels (`C/driver.ts:251–257`; `C/status.ts:31–33,74–78,219–244`). CustomModels may label an existing slug or give a new isCustom=true; that never makes Cursor execute a model the account lacks (`P/snapshotProbe.ts:142–175`; `C/adapter.ts:336–363`).
- The catalog depends on the account through the apiKey in me/models.list and the cache key; SDKUser gives email/apiKeyName for the authenticated label (`C/CursorSdkCatalog.ts:68–89`; `C/status.ts:185–199`). The account-available model list and param combinations are undetermined from the static T3 source.
## 5. Login and accounts

- Priority goes to the trimmed `CURSOR_API_KEY` from that provider instance's environment, then the credential from the SDK store; apiKeyExpiresAtMs≤now counts as expired. readApiKey never rotates or reissues the key. requireApiKey forbids issuance during login/logout/closed, withAccess tracks child scopes of working SDK sessions (`C/auth.ts:53–157`). The driver hands the key to every open and textGeneration, and disables browser setup/logout on a configured key (`C/driver.ts:135–215`).
- The browser flow uses `Cursor.auth.login({openBrowser:false,store:new InMemoryCredentialStore(),signal,apiKeyName:"T3 Code - <displayName>",onLoginUrl})`; the link returns to the client in the waiting state. Before login, old SDK sessions stop; the successful active flow goes through verifying: pendingStore.load → instance store save → snapshot.refresh, which must confirm authenticated. A late result of a cancelled flow never saves, a rejected verification clears the credential. The shared login timeout is 300000 ms (`C/auth.ts:24,159–262`; `C/driver.ts:142–155`). apiKeyTtlMs is never set explicitly, so the default SDK TTL is undetermined by this reading (`C/auth.ts:180–201`).
- The auth flow has a login owner: a repeat of the same owner returns the current flow, another owner can never start a concurrent setup; another owner's subscriber never sees the authorizationUrl/flowId/interaction. Complete refuses: the login must finish in the browser, no redirect URL is needed. Cancel invalidates the active flow before interruption and checks owner+flowId (`C/auth.ts:287–393,447–482`). That is the owner of the browser action, not a multi-user Cursor account identity.
- Logout closes admission, interrupts the login, stops sessions/scopes, and only then clears the credential and refreshes the snapshot; a failed session stop keeps the key. No remote Cursor revoke is called. `/logout` matches on trim-exact match with no attachments (`C/auth.ts:395–445,484–495`).
- Credential schema: version 1, backendUrl, apiKey, createdAtMs, optional apiKeyExpiresAtMs/email. Binding is ProviderHost.credentials("cursor",instanceId), never the global SDK default store. Corrupt content is no credential; saving an unsupported shape is a ProviderSetupError. The old stateDir/provider-auth/encodeURIComponent(instanceId)/cursor.json migrates when the current credential is missing, then the legacy file deletes; migration errors log (`C/credentialStore.ts:10–85`; `C/driver.ts:116–124`).
- T3's actual storage chain: ProviderHostLive → ProviderCredentialStore → ServerSecretStore; name `provider-auth-<SHA256(driver,bindingId)>`, binding owner=t3; file secretsDir/<name>.bin, directory 0700, atomic temp/rename, file 0600. The live implementation as read writes credential bytes with no encryption: the .bin extension never means Keychain/encryption (`apps/server/src/provider/ProviderHostLive.ts:39–48`; `apps/server/src/provider/ProviderCredentialStore.ts:6–22`; `apps/server/src/auth/ServerSecretStore.ts:154–205`).
- Several accounts are separate instances: driver supportsMultipleInstances=true, each with its own SDK credential binding, auth state/session scopes, and logout (`C/driver.ts:62–71,116–156`; `C/credentialStore.ts:24–28`; `C/auth.ts:53–69,395–433`). A separate account-wide usage scan never enumerates those instances: it reads one live CLI login from the host environment; with CURSOR_AUTH_TOKEN/CURSOR_API_KEY or AGENT_CLI_CREDENTIAL_STORE=memory the scan never takes the CLI login, on macOS with store!=file it needs a Keychain opt-in, otherwise it reads auth.json (`C/CursorUsageAccounts.ts:249–300`).
- Status checks a full SDK me+models read with a 15 s timeout: AuthenticationError or CursorSdkError.status=401 → unauthenticated/error, plan_required → a separate paid-plan diagnostic; any other error/timeout → auth unknown/error. A successful empty catalog gives a warning but authenticated. No retry/refresh of its own in the catalog probe (`C/CursorSdkCatalog.ts:17–49,58–90`; `C/status.ts:35,288–355`).

## 6. Failures and spend outside the SDK

- `enableAgentRetries: true` enables retry inside the SDK and in the conversation adapter and textGeneration, but T3 never sets its count/backoff here (`C/adapter.ts:323–330`; `C/textGeneration.ts:108–119`). The runner.send's only own retry is the abandoned-run recovery described above; an ordinary failed/error result closes the current turn and never opens a new automatic send (`C/CursorAgentSdk.ts:469–499`; `C/adapter.ts:2342–2413`).
- The SDK sometimes reports a transport dump as a successful finished assistant result: T3 recognizes an answer consisting entirely of `Error: RetriableError: …` (except `[internal]`), `Error: ConnectError: [unavailable|aborted|deadline_exceeded]…`, or one known server-error phrase, with an optional stack trace. Surrounding text, fenced code, `[unauthenticated]`, and internal agent-loop diagnostics never classify as a transport dump. The check streams with a 4096 line limit; a transport dump turns completed into failed/transport_error (`C/transportFailure.ts:1–50`; `C/transportFailure.test.ts:13–47`; `C/adapter.ts:2359–2380`; `C/adapter.test.ts:365–479`).
- The SDK error text stays with its non-empty specific code and HTTP status; the test's example HTTP 429/resource_exhausted classifies as transport_error, never a special usage_limit (`C/CursorAgentSdk.ts:39–64`; `C/adapter.test.ts:224–257`). The Cursor adapter has no shared rate-limit/auth-to-usage_limit reclassifier: result.error → provider_error, a thrown wait error → transport_error. Shared makeProviderFailure never derives class/resetAt/retryable from arbitrary SDK text; it keeps what it got, retryable null by default (`C/adapter.ts:2366–2401`; `C/failure.ts:203–229`).

The direct Cursor HTTP endpoints outside the SDK found in production provider-cursor and the clone search are the next two. That is a description of T3: no request was ever made; the SDK's private URLs are not included (`C/usageLimits.ts:129–143`; `C/accountUsage.ts:89,186–200`).

1. `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage`. Base override: settings.apiEndpoint, then CURSOR_API_ENDPOINT, then api2.cursor.sh; one trailing slash removed. `Authorization: Bearer <CLI accessToken>`, `connect-protocol-version: 1`, `x-cursor-client-type: cli`, JSON `{}`. Reads optional billingCycleEnd and planUsage.totalPercentUsed/autoPercentUsed/apiPercentUsed (`C/usageLimits.ts:21–33,74–78,129–143`). Token: CURSOR_AUTH_TOKEN; with no explicit CURSOR_API_KEY it immediately answers unsupported, so accounts never mix. Memory store unsupported. macOS/store!=file reads the Keychain only with allowKeychain and the default endpoint, otherwise the file fallback — Windows APPDATA/USERPROFILE AppData/Roaming/Cursor/auth.json, macOS HOME/.cursor/auth.json, Linux XDG_CONFIG_HOME or HOME/.config/cursor/auth.json (`C/usageLimits.ts:79–128`). In the real driver, checkProvider substitutes the SDK API key into CURSOR_API_KEY even on browser login, so without a separate CURSOR_AUTH_TOKEN that chain returns unsupported before Keychain/HTTP; one opt-in never changes that (`C/driver.ts:217–240`; `C/usageLimits.ts:79–83`).
2. `POST https://cursor.com/api/dashboard/get-filtered-usage-events`. Headers `Origin: https://cursor.com`, `Cookie: WorkosCursorSessionToken=<encodeURIComponent(userId+"::"+CLI accessToken)>`, Content-Type application/json; body `{page,pageSize:1000,startDate:String(sinceMs),endDate:String(endDate)}`; redirects forbidden. userId is the last `|` part of the JWT sub, accountKey is the SHA256 of the full sub; the JWT signature/exp are never checked locally. The CLI token comes from auth.json or the injected Keychain reader, never the SDK apiKey (`C/accountUsage.ts:54–64,89–125,146–200`). Response: totalUsageEventsCount/usageEventsDisplay; timestamp/model/conversationId/tokenUsage inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens,totalCents; totalCents/100 → reportedCostUsd, reasoningTokens=0. Null/missing tokenUsage skips, isHeadless and chargedCents never filter spend. That is account-wide history, not only T3 calls (`C/accountUsage.ts:31–36,285–342`; `C/CursorUsageAccounts.ts:229–246`).

- The limits mapper shows the Overall/Cursor Models/Other Models percents directly, clamped 0…100; the comment explains spend/limit ignore bonus usage. The billing cycle end turns from positive milliseconds into an ISO reset; missing buckets are never invented. Probe timeout 10 s, non-2xx/schema/network failure → unavailable/probeFailed, no Retry-After/backoff/auth refresh (`C/usageLimits.ts:35–62,129–154`). That is a snapshot of limits, never an automatic classification of one run's errors.
- The dashboard reader pages from 1, size 1000, reads to a short terminal page; with a known count it allows up to 6 requests ahead, consumes in order; timeout 10 s/page and 60 s total. 401/403 → an explicit "sign in again", other errors/inconsistent count/truncation/bad totals give a shared error with no records. Edge repeats drop only in the count proven by the total count, and by canonical suffix/prefix; identical really billed rows stay through an occurrence id (`C/accountUsage.ts:177–185,205–274,285–368`). No token retry/refresher is implemented here (`C/accountUsage.ts:186–274,354–368`).
- The Keychain reader is `@napi-rs/keyring AsyncEntry("cursor-access-token","cursor-user").getPassword()`: a positive 5 min cache, null never cached; one pending detached read joins concurrent callers, the caller waits up to 30 s, an unfinished native read stays shared so a second macOS prompt never opens (`C/CursorKeychain.ts:17–18,52–106`). That is only the CLI usage credential; the SDK login stores separately.
- The account usage cache: TTL 60 s, refetch overlap 1 h; a retention gap needs a full refetch. File stateDir/usage-cursor-account-cache-v1.json, compact tuples/string table; an accountKey switch drops the old cache and rereads the new account whole. A duplicate refresh joins through Deferred; stale+refreshing is allowed, with cached data the error gives partial. A failed persist leaves dirty for the next atomic serialized persist (`C/accountCache.ts:10–78,85–167,219–246`; `C/CursorUsageAccounts.ts:56–246`). That is no JS session cache and no SDK context-token restore.
## 7. Tools, skills, textGeneration

## 9. Edge cases T3 handles

- A per-process sandbox-capability cache can poison after one unsandboxed run: the comment says only a sandboxed run first reports the cursorsandbox path; after full-access the SDK caches unsupported until restart. Before the first unsandboxed open, the runner once does createAgentPlatform({workspaceRef?}).prewarmLocalWorkspace({apiKey?,local:{cwd?,settingSources:[],sandboxOptions:{enabled:true}}}), release; the rest wait on Deferred. That is best-effort priming, never a check the sandbox is exactly available (`C/CursorAgentSdk.ts:333–367`).
- An SDK shell-spawn failure in dump_zsh_state/dump_bash_state/__CURSOR_SANDBOX_ENV_RESTORE leaves an internal unhandled rejection; the SDK may also write the final frame into an already closed exec stream (`WriteIterableClosedError`). The single process-wide unhandledRejection guard prints those two known cases and keeps the server alive; any other unhandled one exits the process with exit(1) (`C/CursorSdk.ts:8–60,75–86`).
- A synchronous cancel from a tool-call-started callback killed the process with an unhandled AbortError on SDK 1.0.22/1.0.31/1.0.32 per the recorder comment; in the fixture recorder cancel defers 10 ms. That evidences the named versions, never a proven defect in 1.0.35; the production interrupt is a separate operation, with no 10 ms delay (`O/Adapters/CursorAdapterV2.testkit.ts:843–852`; `C/adapter.ts:2532–2555`).
- Updates may arrive before send and the run id return; runner and adapter buffer them, callbacks serialize and wait before terminalization (`C/CursorAgentSdk.ts:425–529`; `C/adapter.ts:2271–2340`).
- A task may send partial before started, give no completed by the parent end, and deliver the model only late; T3 ignores the task partial, never doubles the child, keeps the late model, closes the unfinished task on the parent status. The test directly models the fixed partial-before-started sequence and missing completed (`C/adapter.test.ts:43–49,91–109,196–215`; `C/adapter.ts:1554–1560,1616–1624,1874–1884,2028–2036`).
- A nested failed read may carry no args.path; the fallback keeps it as a failed Read with `<unknown path>` instead of dropping or crashing the error (`C/adapter.ts:666–686`; `C/adapter.test.ts:1243–1263`). Nested protobuf success/error/permissionDenied and grep workspace content differ from ordinary ToolCall and convert separately (`C/adapter.ts:574–787`).
- A completed result may carry a transport error as assistant text with a finished status; the classifier never turns a quote, fenced code, or an internal RetriableError into a transport failure (`C/transportFailure.ts:1–50`; `C/transportFailure.test.ts:13–47`; `C/adapter.test.ts:365–479`).
- Cancel may throw a direct or wrapped AbortError; close and cancel are not the same: agent.close is synchronous, run.cancel async, the expected abort suppresses only in the latter (`C/CursorAgentSdk.ts:239–252,541–563,597–610`; `C/adapter.test.ts:1228–1240`).
- Resume may leave a persistent active-run marker after the process dies; T3 checks the conflict, listRuns(limit:1), cancelRun, and retries send exactly once, with no force (`C/CursorAgentSdk.ts:409,469–499`; `C/CursorAgentSdk.test.ts:134–174`).
- A model unknown to the account is refused with an uncoded ConfigurationError with a `Cannot use this model:` prefix; T3 raises a domain error with a clear message and never relies on the error code (`C/adapter.ts:336–363`; `C/adapter.test.ts:918–1037`).
- `settingSources` omitted never equals CLI defaults per the T3 comment; `sandbox.json` still reads regardless of settings; SQLite handles need a dispose store; a per-send MCP override replaces ambient servers. The matching decisions split across conversation options, textGeneration, and the no-override test (`C/adapter.ts:295–334,2273`; `C/textGeneration.ts:90–107`; `C/adapter.test.ts:196–200`).
