A thread on any transport holds a `native_thread` core row with the `{adapter, profile, agent}` binding, a capabilities snapshot, the model pick (`provider`, `model`, `reasoning`), the account, and switches. `servingProvider` resolves the provider per transport: on `acp` — `AcpProfile.serves`, on terminal — `launch.model.provider`. The driver configures the vendor session from this same row, so there is no second source for the pick. A terminal thread writes to the same place, and its facet's `asked` applies only at birth.

Who reads the pick: everyone — from the core row. `toState` substitutes it into the snapshot's `thread`, `ThreadListReads` into every list summary, evidence into composition; a pending pick (below) stands in place of the row's pick in the snapshot and list rows only, never for a run; the hosted-turn window measurement is recorded into context reading with the same provider, model, and rung that warmth allows the next request on — otherwise the cache forecast would always answer "model changed".

One owner answers which road serves the pick — `HarnessRegistry.seating(pick, catalog)`: the harness whose `serves.provider` matched, with `seat(agent)` building the landing (the `acp/<profile>/<agent>` binding, facet, capabilities snapshot, and the row's pick); `null` for the native road; a `model-unavailable` refusal for a provider with `auth: cli` on which no harness hosts a Tagma agent (Devin has `hosts: null`: its models run only in its own `harness:devin` thread). Decision and landing are split so a model change inside the same harness does not build a needless landing. Three roads go through the owner: operator birth (`threads/birth/acts.ts`), birth via spawn and fork, and model change. Spawn seats the child in the core birth record: `EngineBirths.record` asks `seating` for the child row's pick, and `inheritFacet` writes the facet, the core landing, and `agentId: harness`, while the child type goes into `binding.agent`; the keyed retry, name, place, and fork stay with the core. A child on a host or without a project refuses `harness-host` and `thread-project-missing`.

Who changes it: `set_agent_model` (via the `ThreadModel` filler, with the call key) calls `HarnessMoves.move`; `set_thread_model` (via `ModelPreferences`, without a key) calls `HarnessMoves.pick`, which lands through the same `move` or keeps the pick pending (below). Not the transport name decides, but the capabilities snapshot and the binding:

- **`modelMove: 'pinned'`** (terminal CLI) — a `model-pinned` refusal: the model is set at birth.
- **Inside the same harness** (or on a thread with no `agent` in the binding) — `Harness.move`: validates the pick against the provider catalog and writes it into the core row immediately, including mid-turn. The turn runs to its end on the previous model, the process lives, and the next launch applies `Configure` to the same vendor session from the pick's diff against the protocol row's `configured` ([[4010a731]]). Launch resolves an empty pick to the catalog default, as native. Model switches (the core row's `switches`) go the same road and resolve as on native: a change with no explicit switches (`set_agent_model`) keeps of the standing ones only those declared by the target model (`HarnessMoves.move`); a `harness:*` birth validates the named ones and adds those the operator remembered for the landing model (`BirthModelSelection.switches`); spawn and fork take the child row's decision from the core; a transport change carries the standing ones over; and launch resolves them against the model declaration in the catalog, with the switch default.
- **Account inside the hosted road.** An agent model change without `account` keeps the pick and the process's pinned account. An explicit pick of a different account — different both from the core row's pick and from the account pinned to the process — runs between runs: `HarnessMoves` frees the old process, then `HarnessSessionStore.choose` records the new account and lifts the previous launch pin in one record. `sessionKey` and `protocol_turn` stay for `session/load`; only the vendor's "no such session" answer opens a fresh session from the journal, while an authentication refusal stays a refusal. `null` picks the provider default at the next launch. One owner carries default changes to processes — `carryDefaultMoves` (`native-harness/models/defaultMoves.ts`), subscribed to `DefaultAccounts.defaultAccountMoved`. It has no carry mechanism of its own: every thread from `HarnessMoves.lagging` goes through the same `carryModelMove`, whose turn is `HarnessMoves.follow`.
  - **Whom.** `lagging` selects unarchived threads on `acp` with a Tagma agent that follow the default (the core row's `account` is `null`). From them it takes threads whose standing process is recorded on another account or has not taken an account yet, and threads whose latest run failed on a limit while the process was on another account. Pinned and terminal threads and Devin are not taken. A `null` default moves nobody: Tagma never switches a thread to an account the operator did not pick.
  - **How.** `follow` re-reads the default on every call and frees the process between runs. While a turn is running it answers `thread-running`, and the carry stops the turn at a step boundary and continues it with a new process. A process that has not taken an account yet (`session-starting`) is asked again: otherwise a launch that read the default before the change would pin the old account after it. The release ends the session, so the next launch opens a session with no launch pin and resolves the default; the vendor conversation continues via `session/load` by `sessionKey`. The `follow` answer names the account the thread left.
  - **One queue per thread.** A change arriving while the thread is still being carried is not lost: it marks it for retry, and the thread checks against the latest default until the marks run out.
  - **Owning a stopped turn.** A run that ended `aborted` with reason `model` and was continued by nothing is taken out of the run journal by every attempt and handed to the carry as stopped. So a turn that stopped after the boundary-wait window, or a turn whose continuation was refused by someone else's admission hold, is continued by the next attempt rather than lost. Attempts repeat until the boundary arrives, the process takes an account, or its end is known.
  - **Auto-continuation after a limit.** A run that failed on a limit (`threadRunLimited`) continues only if the thread really left the account and that run is still the latest. A turn started and stopped by the operator after that is not continued.
- **Between roads** (native provider ↔ harness, or one harness ↔ another) — a handover in one machine record: the standing facet is removed (the process is freed, then the protocol row is removed; unacknowledged words stay unacknowledged and do not return to the queue), a new one is seated via `HarnessRegistry.seating`, and the binding, capabilities, pick, and the `transport` journal record are written in the same transaction (`ThreadRebinding`). A native agent hosted by a harness — `binding.agent` — becomes the thread's `agentId`, and vice versa.

A handover between roads (`HarnessMoves.handover`) accepts the model between runs and refuses `thread-running` while a turn is running. One owner carries such a working turn — `carryModelMove` (`packages/agent/src/collaboration/modelCarry.ts`): it holds admission, on `thread-running` stops the turn at a step boundary with reason `model`, changes the model, and continues the saved work. A turn waiting on a question's answer already stands at a boundary and stops immediately: the carry's admission does not let through the answer that would advance it to the next boundary. An adapter turn stops at the nearest step boundary the adapter reports with `stepped` (on `acp` — the end of the last open request call), just as native: the run ends `aborted` with `by: model`, no interruption row, and the continuation goes to the new road. Three owners call it: `set_agent_model` via `TreeActs.move` (window — the call window, 60 s), `carryDefaultMoves`, and the operator's pick carrier (below). A native change inside the native road does not touch the turn: the row changes immediately, the running run finishes on its model. A stop with reason `model` keeps requests with no interim report; the stop-intent stores the carry key, and the keyed result the resumable run, so a retry finishes the broken carry instead of stopping its successor. An explicit Stop cancels auto-continuation; a natural end wakes the queue that stood behind admission; boundary waiting is bounded by the call window, except the operator's pick carrier, which has none. The current run cannot wait on its own foreground tool finishing and answers `self-move`. A process that had not finished by the record answers `session-uncertain`: that is about the resource, not the run. The whole turn holds the thread's `RunAdmission`, so a word never manages to open a run on a process that will then be freed. The agent door enters via the call key: `ThreadModels.adapted` records the result under the key, a retry answers with it with no new turn, and the same key with a different model is a `ThreadModelConflict` that the failure plane serves with code `key-reused`.

**The operator's pick is the thread's durable fact the moment it is made** (`HarnessMoves.pick`, `threads/harness/picks.ts`). Under a per-thread lane the pick takes the thread's `RunAdmission` and tries to land through `move`. `handover` answers its static refusals (`harness-host`, `thread-project-missing`, a thread with no journal) before the running check, and `move` answers `model-pinned` and `model-unavailable` before it, so the call still refuses those itself. A `thread-running` answer instead records the pick in `native_thread.pending_model` while admission is held, so no turn opens on the old road, and the call answers at once with a snapshot showing it. The pick depends on no request: interrupting the caller, leaving the thread, or a step longer than any window changes nothing. One carrier per thread, a fiber of `HarnessMoves`' own scope, takes over that admission hold and runs `carryModelMove` with `until: 'boundary'`: the step stop waits for the boundary for as long as the turn runs, then the carrier lands the row's pending pick and continues the turn; words sent meanwhile stay unread across the stop and open the continuation on the new road. A native step stop fires only at the start of a step, before that step's context projection where a step compaction runs, so a compaction already running finishes on its summarizer and the turn stops at the boundary after it. The carrier asks again a second later on `session-starting`, `session-uncertain`, `harness-moved`, `journal-moved` and `thread-running`, holding admission through the pause; on `step-unreached` (a turn another process drives) and a failed resume it pauses without the hold, since the first must let this process adopt a run whose driver died and the second must let its continuation start. It stops quietly when the thread is gone. A terminal failure continues the stopped turn on the previous model (`restoreOnFailure`, or the carrier itself for a turn an earlier attempt stopped), appends a `model-pick` journal entry the feed draws as a failure row, then drops the pending pick by its id — a write lost between them leaves the pick pending, never dropped without its notice. A newer pick interrupts the carrier before landing — a boundary wait it cuts leaves the turn untouched — and replaces the pending pick; when a carry has already stopped the turn, the newer pick goes through a carrier too, which continues that turn. Every landing of a pick (`seatKernel`, `chooseModel`, an aggregate patch carrying the provider) clears it in its own write; the carrier's handover lands only while the row still holds the same pending id (`pick-replaced` otherwise), and a carrier that finds its pick gone or replaced continues a turn it stopped on the row's model. Server start carries every thread that still holds a pending pick once maintenance opens after run recovery; it takes no admission before the carrier's first attempt, so a run left by the previous process can be adopted first.

The landing carries the account together with the model pick: an operator birth takes the pick from the `KernelSeat`, spawn and fork carry the child row's account, and a road or transport change carries the picked account into the new landing.

History is never copied: the Tagma journal is one per thread. The native harness continues from it (the `packages/llm` origin policy drops foreign-origin reasoning), and the Claude Code runner assembles the vendor session from it on first opening.
