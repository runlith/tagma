How Orca opens a copy of a conversation in terminal TUI (fork) and how it returns to a conversation (resume): which agents, on which act, how the fork terminal gets its new session id, and how its cold restore never lands back in the source conversation. Read in `.external/orca` @0df25b7ac9 (2026-10-11); the code was never run, the agents' CLIs were never launched. All paths below are from `src/`.

## Observations

**What Orca can do on the TUI surface.**
- Resume by id exists for ~25 agents (`RESUMABLE_TUI_AGENTS`, `shared/agent-session-resume.ts`); `getAgentResumeArgv` assembles the argv for each (`shared/agent-resume-argv.ts`): `claude --resume <id>`, `codex resume <id>`, `gemini --resume <id>`, `grok --resume <id>`, `devin --resume <id>`, `cursor-agent --resume <conversation_id>`, `opencode --session <id>`, `kimi --session <id>`, `copilot --resume=<id>`, etc. The `conversation_id` key (Cursor, Antigravity) and `session_id` are different identifier kinds; a resume with a foreign key yields `null`.
- Fork — only two agents: `claude --resume <id> --fork-session` and `codex fork <id>` (`getAgentForkArgv`). The `shared/tui-agent-fork-startup.test.ts` test is called "forks Claude and Codex and nothing else" and verifies that `null` is returned for `gemini` and for Claude with a `conversation_id` key.
- Fork is not a separate TUI function at all: the comment above `getAgentForkArgv` says it is needed "only for the two agents whose conversation can belong to native chat". The only user path to a TUI fork is the "Resume in New CLI" item in AI Vault (session history): `handleResumeInNewCli` in `renderer/src/components/right-sidebar/ai-vault-session-launch-actions.ts`, available only when the conversation is already owned by structured (native) chat and the agent is claude or codex (`aiVaultSessionCliForkWorktreeId`, `…/ai-vault-session-cli-fork.ts`). An ordinary "Resume" on a TUI row is `claude --resume <id>` with no fork. Neither `components/terminal-pane` nor `shared/agent-hook*` nor `main/agent-hooks` contains the word rewind (directory search): neither fork nor rewind starts from a live TUI pane.
- A pane's cold restore after the process exits is a second entry into `--resume`: `renderer/src/components/terminal-pane/pty-connection/cold-restore-resume-startup.ts` takes `providerSession` from the pane's live status record (`agentStatusByPaneKey[…]`) or from the "sleeping" record (`sleepingAgentSessionsByPaneKey`) and builds the same `buildAgentResumeStartupPlan` (`shared/tui-agent-resume-startup.ts`) without the `fork` flag.

**How the fork terminal gets its new id.**
- The `providerSession` field (`{key, id, transcriptPath?}`) arrives from the CLI hook event: `extractAgentProviderSession` (`shared/agent-session-resume.ts`) reads `session_id` from the payload (Claude/Codex/Gemini/Droid/Kimi/…), `conversationId`/`conversation_id` (Antigravity, Cursor), `sessionID` (OpenCode, MiMo), `session_file` (Pi/OMP). `normalizeHookPayload` (`shared/agent-hook-listener.ts`) attaches it to every event; the status store puts it into the pane record (`renderer/src/store/slices/agent-status-live-entry-builder.ts`, `agent-status-provider-session-actions.ts`).
- A fork launch deliberately carries **no** preassigned id: `buildAiVaultForkStartupForWorktree` (`renderer/src/lib/ai-vault-session-fork-startup.ts`) returns the command, env, cwd, and `launchConfig`, but no `providerSession`. Its docstring: "No `providerSession` either: the copy gets its own id, and a cold restore of this tab must never re-enter the chat's conversation". The `ai-vault-session-fork-startup.test.ts` test verifies `expect(startup).not.toHaveProperty('providerSession')` for Claude and Codex. An ordinary resume, by contrast, puts `resumeProviderSession` into the launch (`launchAiVaultSessionInNewTab`, `renderer/src/lib/launch-ai-vault-session.ts`) — the main process awaits that id to verify Codex provenance.
- A conclusion (inferred, not directly read): Orca learns the fork copy's new id from the launched CLI's first hook event, not from argv and not from a transcript scan; a TUI fork has no preassigned id (`--session-id`). This is not stated outright in code; I did not trace the `setAgentStatus` recording code that folds the first event's `providerSession` into the empty record, but `agent-status-live-entry-builder.ts` (lines ~147–172) takes `metadata.providerSession`.
- For structured Claude (SDK, not TUI), Orca does preassign the id: `claudeSessionIdForOrcaSession` (`main/claude/claude-structured-session-id.ts`) — a deterministic UUIDv4-form id from the sha256 of the Orca chat id.

**The "second writer" on the same conversation.**
- Structured chat owns the conversation by lease. A flat `--resume` of the same id from TUI is a second writer into the same transcript, so `assertLegacyAiVaultResumeAllowed` (`main/ai-vault/structured-session-ownership.ts`) refuses `agent_session_conflict` / `agent_session_ownership_unknown` (depending on whether the lease admits a writer, `agentSessionLeaseAdmitsWriter`), while fork preparation (`args.fork`) checks no ownership: "A fork writes a new conversation".
- The same guard parses a hand-typed command: `parseResumeInvocation` counts `claude --resume X` / `-r X` / `--resume=X` / `codex resume X` as conversation references; `claude --continue`/`-c` and bare `--resume` are "target-less" — inadmissible while any conversation belongs to chat (they could pick any). Claude fork (`--fork-session`) is excluded from the check — but not alongside `--session-id` (it sets the id the fork writes under) nor after `--`. Tests in `main/ai-vault/structured-session-ownership.test.ts` (`claude --resume X -- --fork-session`, `--fork-session --session-id X`, `--session-id=X`). `codex fork` passes on its own because it contains no word `resume`.
- When the agent cannot fork, Orca does not substitute a plain resume: `buildAiVaultForkStartupForWorktree` returns `null` ("a plain resume in its place would make the terminal a second writer on the chat's conversation"), the UI shows "This session cannot be opened in the CLI.". Test: `tui-agent-fork-startup.test.ts` "refuses a fork for an agent that cannot fork rather than resuming it".
- On the chat journal side `--fork-session` is described as an event with a new root identity: `appendAgentSessionProviderHandleLink` (`shared/agent-session-provider-handle.ts`) refuses `agent_session_provider_handle_forked` when a resume lands on a different root, and accepts `origin: 'forked'` only with a new root and `forkedFromKey`. Test `shared/agent-session-provider-handle.test.ts` "refuses to record a fork as a resume". Item ids in the journal still match the source: `--fork-session` copies record uuids, so a Claude record key is session id + uuid (`shared/agent-session-journal-item-key.ts`, `agentJournalItemKey`), a Codex key is thread + turn + ordinal (`thread/fork` copies turns with their source turn ids).

**Command override and the saved selector.**
- A user launch command (`agentCmdOverrides`, e.g. `claude --continue`) or saved default-args may carry their own conversation selector competing with the id. `buildClaudeResumeLaunchCommand` (`shared/agent-resume-launch-command.ts`) strips `--resume`/`-r`/`--continue`/`-c` (with their value) from the base and adds exactly one authoritative selector — test `tui-agent-fork-startup.test.ts`: override `claude --continue` + fork yields `claude '--resume' 's1' '--fork-session'`. This is rule #12982 in the comment.
- A joint `-r<id>` is deliberately not stripped ("any `-r…` token is ambiguous with someone else's value"). The selector is inserted before claude's own `--` terminator. When the command cannot be parsed (`bash -c claude` wrappers, operators, substitutions, PowerShell `--%`, cmd with single quotes, line continuation), the function "fails open": the base stays byte-for-byte, the selector is appended at the end. Dozens of `shared/agent-resume-launch-command.test.ts` tests parse these forms across posix/powershell/cmd/fish shells.
- Only Claude goes through this cleanup; other agents get plain argument appending (`buildAgentResumeLaunchCommand`).
- `dropAgentResumeArgvFromCommand` (`shared/agent-resume-argv-drop.ts`) is the reverse operation: strip exactly the appended resume tail (the boundary is a space, so `resume-foo` never matches `resume`), so the pane starts "clean" when Orca cannot verify which account owns the session. For Claude it is practically unusable (the selector may stand before `--`), it returns `unrecognized`, and the launch is refused.

**cwd, env, remote hosts.**
- Codex: on fork and on AI Vault resume Orca puts `-c tui.resume_cwd=current` before the subcommand (`resumeInLaunchCwd`, `shared/tui-agent-resume-startup.ts`, comment: "Codex otherwise prompts for the folder, defaulting to the recorded one even once it was deleted (#17745). Kept before `resume` so dropAgentResumeArgvFromCommand strips only that"). Test: `codex '-c' 'tui.resume_cwd=current' 'fork' 's1'`. `-c tui.resume_cwd` stays when the AI Vault resume is stripped.
- Kimi and Muse are directory-bound: `RESUMES_ONLY_IN_RECORDED_CWD` in `renderer/src/lib/ai-vault-session-resume-preparation.ts` (Kimi outside the directory refuses resume or since 1.52 opens a new empty session under the same id). DSH keys sessions by workspace path (`agent-resume-argv.ts`, comment). For an SSH session `dropDeletedSshResumeCwd` removes the recorded `cwd` and the probe command only if the host confirmed the folder is gone; a lost host does not count as proof.
- `CODEX_HOME`: `buildAiVaultResumeShellCommand` (`shared/ai-vault-resume-command.ts`) puts `CODEX_HOME=…` as a prefix on the agent itself, not on the `cd … && agent` chain, and for posix shells removes non-inheritable variables via `env -u` — but not the just-set `CODEX_HOME`. When the session has a real (system) home, the pane removes `CODEX_HOME` and `ORCA_CODEX_HOME` from its env (`realHomeCodexResumeEnvDeletion`). For a Codex fork Orca prepares the home itself (`prepareAiVaultSessionForFork` → host `prepareCodexAiVaultSessionResume`, `main/codex/codex-ai-vault-session-resume.ts`): "a fork carries no provider session, so the pane spawn never readies the home a resume would", and home preparation with hooks is best-effort (the fork still launches without hooks).
- Codex-resume provenance check in main (`main/ipc/pty-spawn-env-codex-resume-provenance.test.ts`): when the rollout lies in a home Orca no longer trusts, the resume argv is stripped from `command`, from `ORCA_SEQUENCED_STARTUP_COMMAND` (the wrapper `eval`s it), and in the runtime controller; the pane starts without resume and returns `agentResumeUnavailable`; a resume whose locator remains in the command and cannot be stripped is refused with "could not verify the originating Codex session file"; a pane with non-Codex layout metadata launches as before.
- Remote hosts: cold restore never replays an id on another host: `agentResumeOriginNamesAnotherExecutionHost` / `sleepingRecordNamesAnotherExecutionHost` (in `cold-restore-resume-startup.ts` and `resume-sleeping-agent-session.ts`): "A session id names a transcript on the machine that captured it"; on a foreign host resume yields `No conversation found`; while the host answer is unknown (`unverifiable`) the record is neither deleted nor launched. Host capabilities: `agent-session-resume-runtime-capabilities.ts` — flags like `agent-session.kimi-resume.v1`: a new enum member on an older host yields `invalid_argument`, so the client checks first.

## Second fork kind: over terminal text

`terminal-agent-session-fork.ts` ("Fork Agent Session…" in the pane context menu, `TerminalAgentSessionForkDialog.tsx`): takes up to 800 scrollback rows from xterm (`serializeAddon.serialize({ scrollback: 800 })`), strips ANSI/OSC/control characters, takes a tail of ≤ 36,000 chars (`MAX_FORK_CONTEXT_CHARS`, `renderer/src/lib/agent-session-fork-context.ts`), wraps it in a markdown fence with headroom (`getMarkdownFenceForTranscript`), and launches a fresh agent in a **new git worktree** with this text as an editable draft. Comment: "v1 is a context fork, not a process clone"; works for any agent and for SSH because it reads xterm, not the CLI transcript. Cannot: a branchless workspace, archived, bare, and floating terminals do not fork ("This workspace cannot be forked into a git worktree.").

## What the reading does not establish

- Orca never shows which id `codex fork` mints and when it appears in hooks: Orca only launches the CLI and waits for events; the CLIs' own behavior was never verified.
- How the remaining hook sources (Gemini, Devin, Grok) react to `--resume` was not read, nor whether any CLI exists where resume creates a new id instead of the old one (in Orca this is reflected only as the "resume must keep the root" rule, `providerHandleRoot`, `shared/agent-session-resume-marker.ts`).
- Binding exactly the first event to the fork-launch pane is inferred, not traced through every `setAgentStatus` branch.
- What Claude Code `--fork-session` does to the on-disk transcript (a copy, a new file, keeping record uuids) is visible here only through Orca tests/comments about record uuids, not through the CLI itself.
