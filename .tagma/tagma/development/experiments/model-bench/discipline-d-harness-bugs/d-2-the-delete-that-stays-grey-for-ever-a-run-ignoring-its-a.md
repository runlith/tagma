D-2: pressing Delete on a running harness thread greys the button and nothing else happens, ever; reloading shows the thread still standing, and Delete is grey in every other thread's dialog too.

- **Start commit.** `ea7c4e2d5` — the parent of the one repair commit, so the snapshot is exact. The brief supplies the symptom and the operator's law: a delete is theirs, it is answered — deleted, or refused by name — and never left standing.
- **Reference repair, withheld from workers.** One commit, `e9201605c`, in four layers: `packages/agent` — a stop aborts the run with a typed `ThreadRunStopped` reason naming its actor, so an agent can tell the reader's Stop from a departing server; `harness/agents/harness/run.ts` — the run's race gains a third ending and on `ThreadRunStopped` ends the CLI through the same stop the operator's door makes, leaving it standing on every other abort; `ThreadActs.delete` + `terminals/endHeldExecutions.ts` — the door ends every execution the subtree holds or names BEFORE the kernel's unit, on the host's proof where one exists, and the whole delete is bounded at 30 s with a `delete-timed-out` refusal; `ThreadList.svelte.ts` — the delete mark is per row, not one `busy` flag for the list.
- **Why it is hard.** The hang has one mechanism the contestant must read across three owners: the kernel's `deleteRow` stops the run with `settled: true` and waits for its fiber; the harness run is `raceFirst(exited, parked)` and never observes its abort; so the wait never ends and the HTTP answer never comes. Nothing logs. The grey-everywhere is a second, unrelated cause in the page. The terminals resource kind's refusal is a third, and it is CORRECT — it must stay.
- **The partial fixes a contestant is drawn to.** Stopping the process in the delete door alone: the hang goes, but the reader's Stop still leaves the CLI running. Making the run honour every abort: a server restart then kills every CLI a successor should have adopted. Removing the resource kind's refusal: a thread row goes while custody still names it.
- **Oracles**, all landed in the repair: `ThreadActs.delete.test.ts` (5; "a kernel that never answers is refused at the patience, never left hanging" is the symptom), `endHeldExecutions.test.ts` (9), `harnessRun.itest.ts` "a stop somebody asked for ends the CLI" and "an abort nobody asked for … leaves the CLI standing" (real execution host), `ThreadRunLease.test.ts` "a stop aborts the run with a typed reason", `ThreadList.remove.svelte.test.ts` (per-row marks). The `ThreadActs` and `endHeldExecutions` cases are bound to the reference's owner names and need a behavioural rewrite before a launch; the itest cases and the page cases are behavioural as they stand.
