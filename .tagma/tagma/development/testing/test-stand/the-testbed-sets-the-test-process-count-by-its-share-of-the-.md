testbed removes `--parallel`, `--max-concurrency` (bun) and `--maxWorkers` (Vitest) from the runner command and sets once the number of processes it got. A number left in the command is only an upper bound: so a script whose files share one outside resource holds `--parallel=1`, and `test:all --jobs N` caps the measurement. Vitest takes no several scalar `--maxWorkers` values, and a maxWorkers in the inherited project config would override the outside CLI budget, so the value stands once and in the CLI. For bun "needed" is at most the number of named files: an extra worker would cost loading and do nothing.

The budget leaves CPU to the test processes' children and caps the worker family's memory: the worker count alone never describes load from git, SQLite, hosts and shared worlds. The limit is the smaller of physical memory and the process limit; current free memory is no good because the file cache would change equal runs' shares. The CLI and the shared scheduler read one formula, otherwise the scheduler could wait for room the CLI would never give. At least one worker stays even on a small machine; this is a conservative default, not a prediction of each set's optimum. The command takes `min(needed, free, ceil(budget / (other holding and waiting + 1)))`, never below one; when no units are free, it waits. Already running bun cannot gain processes: it starts workers once, so shares split on entry — one run on an empty machine takes the whole budget, several simultaneous ones equal shares. Giving back is allowed: a bun worker leaves as soon as it has no files left, and testbed frees units down to the runner's living worker count — but only after seeing all workers bun must start: under load bun spawns them slowly, and a unit freed early would go to a neighbour with a worker yet unborn. Not seeing all keeps holding units to the run's end. So the tail of a run, where one worker finishes the last file, never holds the whole budget. Each unit is a flock of its own file, the command's presence in the queue a flock of a file in `commands/`. Only testbed holds units, otherwise it could not free them; the runner gets one queue entry, so a runner surviving a killed testbed still counts as a neighbour. The next counter of the file removes the dead one's file. Waiting with no timeout: the "is there a free unit" question repeats until one appears.

The test runner and everything it starts (git, SQLite, holder, servers) go with nice 10: on an empty machine tests take all, under load interactive processes get the CPU first.

A testbed nested inside a test inherits its runner's units and takes none, otherwise it would wait for budget its own parent holds. A command that is no runner itself (`test:all`, `testbed bun script`) holds and passes no units: each set and chunk it starts takes its own share anew. Running side by side is one testbed scheduler (`runJobs`), through it go both `test:all` and `check:change`; on one machine a package set is one runner start with all its files, with no own lifetime: only the operator's rule sets a command's life. Across CI machines `test:all --shard i/n` gives every set's runner its share of the files, balanced by recorded per-file durations, and a set with no runner goes to the first machine only. Under `--shard` testbed reads the shared `.bun-test-timings.json` but writes the shard's own `.bun-test-timings.i-of-n.json`, which CI merges back for the next run: bun under `--shard --update-timings` writes only its shard's files into its first timings file, so a shared first file would lose every other shard's durations, and shards reading different durations would assign one file twice and another to none. Most expensive first, next when free units cover all it needs (its file count, else the past run's files, else the whole budget), and small ones fill the rest; so the budget never idles between sets and on tails. The next set is admitted by fact — the previous runner got its processes or the set ended — not by timer: admitted earlier it would grab units the runner standing for a build has not taken yet. A composite set (`build && test`) goes in stages as separate processes, so stopping reaches the running stage, not one shell. The admitted set's share is never cut on entry: a share cut to two processes would stretch a heavy set into hours. So the set admitted by the scheduler takes all free up to its need (`TESTBED_ADMITTED`), and equal splitting stays between independent commands; the runner never sees this mark, and a testbed nested in a test splits budget as before. Under `test:all --jobs N` sets go one by one each capped at N processes — a measurement mode comparable with the past. The cap goes through the environment (`TESTBED_JOBS`), not flags in the plan, so `--resume --jobs N` also caps a plan taken without it. On a CI machine, recognised by the standard `CI` variable, the tests are its only tenant: the budget keeps the children's share of cores and drops only the reserves for other tenants: two thirds of the cores, as many as the whole memory holds at one worker per `WORKER_MEMORY`. A worker is not one core of load: on the 3-core macOS runner one server-integration worker averaged 1.16 cores with its git, SQLite and servers, and three workers there tripled the CPU of the same files and ran slower than one. `TESTBED_CORES` sets the core count instead of the real one, and `TESTBED_BUDGET_ROOT` a separate unit pool.
