For the commit's private index, everything in the checkout that is not staged is someone else's uncommitted work. Stash-framework hooks (pre-commit framework, lint-staged) take it off disk for the hook's duration (`git checkout -- .`, `reset --hard`), and another agent's write in that window is lost. So hooks of every Tagma commit — landings, commit_checkout, the pull merge commit and merge worktree in `merge` mode, `post-commit` and `post-merge` included — run in the commit tree: one private working tree per checkout in the machine store (`workspace/commit-trees/<path key>`) with its own index and the checkout's git dir, so hooks see the command's refs. Hooks see user config as under `git commit`: `git add` inside a hook would otherwise hash without its filters (LFS) and `core.autocrlf`.

- Before each use, the previous run's links are removed, the tree is brought to the commit version (`read-tree --reset -u` rewrites only what differs) and cleaned of untracked files (`clean -fdq`, without `-x`): no leftover of the previous run leaks into the next. The tree's index lock files are deleted first: only Tagma writes there under a lane, and a lock left by a cut hook would otherwise lock every later landing.
- The tree unfolds whole except in one case: every commit step declared `reads: "nearby"`, and the checkout never needed the full tree yet. Then only the steps' files unfold, plus tracked paths from `run` (the `tools/fmt.sh` script) and tracked files of ancestor directories of both (that is where the tool looks for config: `.oxfmtrc.json`, `package.json`, `.gitattributes`); the tree index's remaining records are marked skip-worktree, and git neither writes, compares, nor counts them deleted. Otherwise the first landing in a new checkout would unfold the whole repository for a single file. Sparseness is only declared, never derived: a tool missing a file often does not refuse but silently makes another shape, and neither a retry after refusal nor a guess from `run` catches that. The full tree stays full even for such steps: a repository with hooks would otherwise unfold it anew on every landing. The shape mark (`shape`) is written before the index switch, and a tree without an index counts as fresh: an interrupted bring-up never leaves an index with skip bits under a full-tree mark. A file a step wrote in place of an unfolded tracked record is deleted on next use: `clean` does not see it.
- The checkout's ignored files (`node_modules`, `.venv`) are visible as links to the same place; otherwise `npx lint-staged` would not find the tool. A link is placed only where the commit version has neither a tracked path, nor a tracked descendant, nor a file at an ancestor location: otherwise a local ignored `.env` would shadow a `.env` the commit started tracking, and `git add -A` would commit the local one. Links are placed only on the outermost paths: git names both a directory with its own `.gitignore` of `*` (husky `.husky/_`) and each of its files, and a link inside an already-placed link would delete a file of the checkout itself. Directories link through a junction (on Windows it needs no privilege), so a directory is never copied; a file with no symlink right is recopied on every use. Format steps only need the ignored files next to their paths: `check-ignore` finds them from ancestor-directory contents, not by walking the whole checkout. A derivation runs an arbitrary program, so its tree links every ignored path of the checkout: in a workspace, a package's own `node_modules` stands beside its sources, not beside the derived outputs. A tool's write through a link lands in the checkout's ignored files — the same power it would have in the checkout itself; tracked files and other people's lines are protected, ignored files are not.
- To git a link is an untracked file (`node_modules/` does not cover it), and `git add -A` would commit the absolute link. So the tree has its own exclude file: the user's excludes (`core.excludesFile` or the XDG default), followed by literal paths of the current links without trailing `/`. It is fed via `GIT_CONFIG_PARAMETERS` from `TreePlace.env` to every git process of the tree, hooks and `clean` included; the command's `.gitignore` and the shared `info/exclude` are untouched.
- The hooks lane is held by checkout key for the whole tree use: two commits of one checkout never share the tree at once. A lane-ceiling cut interrupts the hook process and stops its process group (SIGTERM, SIGKILL a second later) before the tree is read or released; a process that left the group (`setsid`, daemon) is not stopped this way.
- `post-commit` and `post-merge` run after publication in the commit tree brought to the published commit: `reset --hard` or `checkout -- .` in them would otherwise wipe other sessions' uncommitted work. `post-commit` edits (landing and commit_checkout) are taken after the hook and carried into working files as nobody's uncommitted lines, as git would leave them in the working tree; a file where the edit did not land becomes `post-commit` debt (see the steps debt). `post-merge` edits are carried nowhere: the tree's next use resets them.
- The commit index is taken right after `pre-commit`, as with `git commit`; `prepare-commit-msg` and `commit-msg` run in the same place after it, and what they change does not enter the commit. What a hook staged before the snapshot enters the commit and is carried into working files through `ChangeRecord.reshape`; what hooks changed after the snapshot or past the index is taken after the last hook that ran and carried as uncommitted work, otherwise a formatting hook would refuse forever.
- Edits are carried on any failure after a hook (the hook itself, message hooks, a repeated rule judgement, signing, a moved HEAD) and after a hook cut by the lane ceiling: then the tree is reread without reset. If commit steps ran before the hook, on failure and before retry their edit is carried first (pre-steps file version → assembled tree), then the hook edit on top: the disk holds the pre-steps text, and a hook edit carried alone would conflict with it on every repeated landing. If the tree index is unreadable (a killed hook's lock, an unmerged record), edits are taken from working files over the assembled tree in a fresh index; if that fails too, the refusal names the reason. A landing retried for a moved HEAD carries every attempt's edits forward as the session's work, so the next attempt commits them. Merge worktree carries all attempts' edits at the end, with nobody holding: carried earlier, they would dirty the base checkout for the next attempt. The answer names such files in `edited`, and files left as they stood in `kept` (conflict, binary file, symlink); a carry failure is named, never passed off as no edits.
- The branch the commit publishes to is read before assembly by the same read as the base (at submit_work, in prepare) and checked at compare-and-set: signing runs outside the commit lane, and a branch move onto the same SHA while waiting for the signer would otherwise publish the commit to the wrong place.
- Pull does not open a merge in the checkout: `merge-tree` computes the merge, hook and commit run in the commit tree, and only after publication does the checkout move to the commit with `read-tree -m -u` — like a fast-forward, with git refusing where it would overwrite local edits. So agent landings never meet MERGE_HEAD for the hook's duration. A merge with git conflicts still stops in the checkout itself.
- Trees of checkouts that lost their `.git` are deleted by a pass at server start; the tree of an archived, deleted, or forgotten worktree is deleted by the same act.
