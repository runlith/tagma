A checkout snapshot before and after a `bash` command yields the same dirty paths, digests, and HEAD as a full `git status`, but usually reads only what changed since this checkout's previous snapshot. The change source is the kit's `ChangeSource` port (`changeSource.ts`): composition fills it with the watch-process cursor ([[e611425d]]); without the port every snapshot is full.

- **Basis.** After every successful snapshot the checkout frontier stores a basis: cursor position, full dirty state, HEAD, index stat and entries, ignore-rule file stats. The position is taken before status, after the delivery barrier (`settle`): every record before the snapshot is already in the process record, and events between the position and status arrive again, which is harmless. A failed snapshot resets the frontier (`lost`), and the basis with it — by frontier generation.
- **Next snapshot** takes paths past the position and adds paths whose index entry changed in content (mode, hash, stage, `skip-worktree` and `assume-unchanged` flags), and HEAD-diff paths of the old HEAD vs the new. `git status` is read only for these paths with a literal pathspec — a directory path covers its subtree, so a deleted or moved directory is read whole — while other paths stay from the basis. The index is judged by content, not by `.git/index` stat: any neighbour's `git status` rewrites it without changing entries. Index entries are read from disk only when the index stat changed; HEAD from git-directory files, via git only when their shape is unreadable. `.git/*` paths and the barrier cookie are dropped. With no changes status is not read at all. Path-scoped reads and untracked-directory expansion run with `core.fsmonitor=false`: Tagma's watch process named the paths, while git's fsmonitor lags tens of seconds under load and would stay silent about the command's edit. Such a read's file work is limited to the named paths. A full snapshot keeps the monitor for cost in large repositories. But when a post-position path is already known yet the snapshot turned full due to `.gitignore`, pathspec overflow, or unread HEAD or index, these paths are re-read without the monitor and added to the full list. Without a cursor, when there are no paths, a full snapshot trusts the monitor.
- **Full snapshot** — when there is no basis (first command in a checkout, after a loss), the cursor gives no guarantee (`changedSince` → `null`: another subscription, the record boundary passed the position, the watch process lost), the barrier did not pass, `.gitignore` is among the paths, the stat of `info/exclude`, the excludes file, or one of the configs (shared git directory and global) changed — a config change re-reads `core.excludesFile`, the old HEAD does not read in diff, the index does not read (split or sparse index), or paths do not fit one command line (`pathspecFits`).
- **Subscription.** The port holds a root subscription while at least one command runs in it, and 5 minutes after the last: a cursor exists only on a live subscription, and a checkout-tree subscription without watchers closes. Exceptions match the checkout tree's, so the watch process shares one stream with it. When a snapshot sees ignore-rule changes, the port re-lists excluded directories and, if the list differs, opens a subscription with the new list before closing the old one, and takes a new position after the barrier: otherwise a write in a directory that stopped being ignored would never be named by the cursor. If it failed to open, the subscription is dropped and snapshots read in full.
- **Write moment.** mtime inside the command window is the write point. Otherwise the point becomes the ctime that landed before the "after" snapshot start: `mv`, `git mv`, `cp -p` assignments preserve mtime but set ctime at operation time, while a status change during the snapshot itself is already not the command's. With neither (deletion, ctime outside the window) a path receives the interval when the engine heard it, extended back by the delivery delay and clipped by the window; a post-window mtime is not replaced by an event. An mtime or ctime with zero fractional part (second-precision FS) counts as unknown: a truncated time may land before the process start. The basis stores heard intervals per path (last few thousand), so another command's snapshot in the same checkout between "before" and "after" does not take them from this one.
