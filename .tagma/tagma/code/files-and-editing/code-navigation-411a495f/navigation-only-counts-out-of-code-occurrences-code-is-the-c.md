For navigation, code is the extensions of the code-facts kit languages (`LANGUAGES` of its `languages` door) and the adapter's extensions (`Capability.extensions`). So `.svelte` and `.py` stay in the “no adapter” boundary by files with occurrence counts, while JSON, markdown, lock files, and the rest go into the `outside` summary as match and file counts. Unreviewed items from file or language coverage fold by file and cause; changed positions, untyped and unclear values, and cut aliases keep places and text for the agent to read. Folding is shared for JSON and text and precedes pages; otherwise the cursor and `total` would count hidden occurrences while the agent still paid for them with context.

So every name gets two ripgrep passes: `--json` over code only and `--count-matches` over everything else. Counting answers per file, and its cost does not depend on line length: `--json` hands over the whole file line, and minified one-line JSON became megabytes of output the server parses on its event loop. The answer holds no file line either: a place carries a 60-UTF-16-unit excerpt on each side of the occurrence, and adapter declarations are cut the same way.

Code is picked by ripgrep type (`--type-add` plus `--type` / `--type-not`), not `--glob`: ripgrep's glob overrides ignore rules, and `-g '*.js'` lets git-ignored files into the search. The owner is found by a separate `--files-with-matches` pass over code only: a declaration stands only there, the owner's name occurrences are not in the summary, and parsing needs only the file list — the server parsed `--json` for a frequent owner (`Effect` in runlith — 72 thousand lines, 23 MB) longer than the search itself took.

`Owner.member` is both a declaration in a candidate file and an import of that name from a package (not a relative one): `Effect` from `effect` is declared in `node_modules`, which the search does not see, and it is not in the repository at all. Files importing the same thing (module and imported name; `import X = require()` too) are one owner: the kit asks the adapter about the member in the first of them where the language has an adapter, and moves to the next until the adapter says the owner resolved in the file — with or without a member: same-import files resolve to the same thing, so an empty answer from a resolved owner is final. The rest are not hidden by a file without an adapter, outside programs, one with an unresolved import, or a file changed after the snapshot: in the snapshot it may still resolve the old name. Different versions of one package in different parts of the repository are this rule's limit: the group answers with the first resolving file's version. Walking to the first answer with a member would pass, for an owner without such a member (`Layer` from `@runlith/layer` at `Layer.effect`), all 88 importing files, each in its own program. The engine itself resolves the import and finds the declaration in the library. Declared and imported owners give subjects together — identical ones by declaration merge, different ones stay as they are: an answer per each or an `ambiguous` refusal with the list; the same module under the same local name but with different imported names means different owners. Files that failed to parse still make the question ambiguous instead of silently vanishing. A frequent-owner question costs candidate-file parsing plus one `locate` call per module, not per file. Parsing grows with the file count, so it runs off the server loop: `owners.worker.ts` reads files and parses them with the code facts, and only the wanted name's declarations and imports return to the loop. Files are split across several workers by path hash (one to three, by core count minus one) so a file always lands in the same worker and its blob memo works on repeat: a repeat waits only for file reads and hashes. Language functions cannot cross the worker boundary, so the caller does not pick the language set: the worker takes `ADAPTERS` from the `adapters` door, and the loop takes the same languages' extensions from the `languages` door, which does not load parsers. So only the worker loads `oxc-parser`, and the built server does not import it at startup even with navigation off; the memo lives while the process lives. The worker link is the shared `workerLink` from `@runlith/utils/worker`, the same as for long NDJSON-RPC lines and CDP payloads. On runlith, parsing 4.4k `Effect` files took 2.3–2.6 s on the loop with a cold memo, now 1.2–1.8 s in workers with the loop free; a repeat takes 0.04–0.13 s. A single sample measured on a machine under 7–10 load.
