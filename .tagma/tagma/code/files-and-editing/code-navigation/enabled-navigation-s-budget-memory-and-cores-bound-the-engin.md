The enabled navigation engines of all repositories together take 5/16 of the machine's memory, but no less than one engine with the smallest bound plus a client needs: an engine runs on any machine where Tagma runs (the operator's decision), a small machine getting a smaller bound and slower answers. The smallest bound is 2 GiB: memory never drops below it — the process holds its live heap at any bound — and back-to-back collections only stretch loading and cold questions (measurements — [[8689cf64]]). Each engine counts together with its client (up to 1 GiB above the engine process bound), because the driver measures the whole process tree's memory, and a budget counted on one engine bound alone would evict healthily working engines.

An engine holds the whole repository — base and all its worktrees — so its `GOMEMLIMIT` is the entire navigation share minus the client: one active repository may take it all. How many worktrees hold their own snapshots inside that memory is the adapter's call; the holder tells each engine its share — the budget divided by live engines — and by it the adapter stops warming new worktree snapshots. How many engines run at once counts on the former bound of one checkout — an eighth of memory within 4–6 GiB: the bound is soft, and an engine given less live heap than its base takes only answers every question slower with back-to-back collections; on machines up to about 16 GiB RAM that is the whole share minus the client, and in a large project answers are slower there.

Cores are bounded by an engine's own share, not split between engines: a third of the machine's cores within 3–4, but no more than half the machine. Cores are not reserved; an engine takes them only while answering, warming a snapshot, or collecting garbage, and idles most of the time. Splitting the share between engines would leave one core to each on an ordinary machine, and then a collector pass over a heap of several GB stops answers for seconds. The 3-core floor keeps collection parallel. The live-engine count is bounded by memory and cores both: all engines busy at once take no more than two thirds of the machine's cores together, so a memory-rich, core-poor machine holds fewer engines than memory would fit. No fewer than two questions run against one engine at once. The numbers derive from measurements of the TS 7 process on runlith on one machine; budgets on other machines are an open spec question.

Space counts two ways. Past this count, starting a new repository's engine stops a free one — with no leases and no questions in any checkout — the least recently asked; when none is free, the question waits until one of them finishes an answer, and never evicts a working question. Every 30 s the holder's driver measures every engine's memory. An idling engine never stops: a cold start would cost the question after idle seconds, while an idle engine returns memory itself. A worktree idle for 15 minutes rests: the engine releases its own snapshot while the worktree stays connected, and its next question is answered by the base snapshot at once while its own snapshot warms again — disconnecting would cost it a fresh git diff computation, seconds on a large repository. An engine above its share likewise releases the least-recently-asked free worktree's snapshot — one per pass, because memory returns only as the collector returns it. When the engines together still exceed the budget, free engines stop by least-recent use, but never the last: an engine alone exceeding the whole budget holds its memory bound, and stopping it would only trade memory for a cold start.
