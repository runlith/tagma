While `navigation.enabled` is off, a lease refuses without starting; switching it off stops the generation together with subscriptions and cancels a still-waiting start. A project setting overrides the user layer; navigation is off by default. When navigation is on, the first question to a repository starts the launch in the holder's background and waits until the engine serves the first snapshot (seconds of cold start once per repository); every question before a ready snapshot waits on the same start — there is no second `open` for the same repository, otherwise simultaneous questions would raise a process each. An already-running engine's worktree attaches to it: its first question waits on the worktree-vs-base diff computation, not on loading. The wait has no deadline: the engine is its own process, and it ends on a fact — a snapshot, space freed by an engine that finished an answer, or a new generation after the process end. There is no "no engine" answer: the tool is offered only where navigation is on, and a grep-grade answer is useless to an asker who asked for precision.

Only a start that took space holds it — a running or stopping engine; a repository waiting on space holds none — otherwise two waiting starts would wait on each other. A waiting start is cancelled when its questions stop waiting: otherwise it would raise an engine nobody asks about and stop another's for it.

A generation ends one way — by a watcher that waits on the process exit or an end signal (a `touch`, `usage` or `rest` failure, eviction). It first refuses `EngineLost` to every question of that generation, queued and running, then closes its scope — process, checkout connections and subscriptions — and only after that may the slot start again. Without that order a question would get a dead process's adapter, or two processes of one repository would live side by side. A start failure or a process exit pauses before the next start, doubling it from 1 s to a minute and resetting the count once a generation lived 30 s: otherwise a breaking engine would restart on every question. A question that finds the pause waits out its end and the next start. Only an engine that ended three times in a row refuses waiting and new questions with `EngineFailed` with the last end's reason — a failure with a diagnosis, not a verdict — and the question after the pause tries again.

An engine belongs to a repository — the root's `repositoryId` in the registry, and for a checkout without git its `RootId` — and a checkout in it belongs to the root (`RootId`), not to the path spelling: every question re-learns the root from the registry. The question's chosen project persists until the lease; at a root shared by several projects each project's settings read separately while the physical connection stays one. Switching off stops the former generation, but an enabled project may ask the shared checkout again. The engine base is the repository's main worktree when registered and navigation is on for its project, otherwise the first question's checkout: its files are the base layer of all the rest, so the engine watches it even when unasked and never releases it. A checkout found at a new path reconnects on it; when it is the base, the engine stops and the next question raises it anew. Stopping for space checks the engine has no leases and no questions in any checkout, and moves it to `ending` in one synchronous step: a question arriving after the decision never gets a stopping process's adapter.

A lease holds the snapshot of the revision it read until the question ends, and the lease adapter judges on exactly it: otherwise one answer would carry one snapshot's revision and subject and another's verdicts. Questions of every checkout of one generation go through its multi-place queue: a long question does not hold the rest, and an interrupted tool call either leaves the queue or interrupts its request, which the adapter cancels in the process.

A checkout's change subscription is taken before the engine reads it — before `open` at the base and at attach for a worktree: everything that changed between subscribing and the engine's disk read arrives again, never lost. Agent writes through file tools arrive through the checkout's mark in the same step as the write — before the tool answer — so the next question sees the file in the snapshot's `changed`.
