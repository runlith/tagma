Whether it opens beside or in a full place is decided by the owner of link opening, `Opening` (`features/opening`); `FileOpener` (app tier) is the executor of the "file" link view and decides only where the file lands within the chosen place: `place_path` answers what stands at the path — a readable file or a server directory — and, if the path belongs to a checkout of a registered project, also returns `(projectId, checkout, path)`. A file outside checkouts goes to the same place with `rootId: null` and an absolute path — a disk document the same editor opens and edits (see [[78efcd89|note on files outside checkouts]]). A picture from the feed goes to the chat lightbox (`picture` in the request); a PDF opens as a browser tab. The "PDF goes to the browser" decision is one for everyone who opens files (`shows`). The server derives the file type with a single `mediaTypeOf` function (by name) for `place_path` and for the records the client already receives: `read_directory` lines, `search.subscribe` file frames, and `scratch.subscribe`. So the Checkout page tree and search and the Scratch tab of the Changes tab (beside and in a full place) decide synchronously from the record type and open a tab at once, without a request; such an opening cancels an `open` still waiting for its `place_path`, otherwise its late answer would override the last click. A file link carries its name's type, not its target's, like `place_path` with a byte address: otherwise tree and server would disagree on one file's type. `place_path` is asked only for paths whose type is unknown: chat, terminal, and palette links. The client extension does not parse: otherwise the same fact would be derived twice. Without an editor surface a file does not open. A missing or unreadable file never becomes a feed link.

- The Checkout page registers itself: `Tabs` (graph tier) via `stand(aim, …)`. When there is a `beside` in the request (`LinkFrom` of a link opened beside, or empty — for the palette opened from "+ → File…"), the file opens as a `file` tab of the right area through the shared `Beside` port (`features/opening`, fills the composition) under the "where a tab lands" rule: in the screen layout where the thread is shown, otherwise in that thread's own layout, and without a thread in the section layout; the page does not change. `quiet` in `LinkFrom` (set by the terminal) opens the tab without moving the area focus to it. The same file with a different line moves its tab to the new line instead of opening a second one. Otherwise — the pinned Checkout tab of the current `GraphAim` and navigation to `Addresses.git('tree', branch)`. A file from another project's checkout opens as a tab of that project's Checkout page: `FileOpener` holds it until the `stand` of that `GraphAim` and navigates there, because page tabs are checkouts of one project and rebinding a tab without a branch would drag someone else's path into your own checkout. A Checkout page does not address another project's checkout that is missing from its `list_branches` (detached worktree, accepted root), and opening answers with a notification.
- A link's full place (Cmd-click, "Open in Files" in a file tab header; `reveal` in the request) leads to the Checkout page of the checkout holding the file, even from another worktree of your own project, and switches the side column to the tree: ordinary opening in your own project leaves page and column as they are, while a tab from someone else's branch is marked with its branch name.
- A directory (the `directory` view; built by the block Sources line over its own graph-copy checkout and by a recognized path that `place_path` called a directory) never opens as a tab: a directory has no tab. The link carries the answer's place: a checkout directory opens in the Files of that checkout's Checkout page, and a directory outside all checkouts, in `.git/`, or in the graph tree opens in the machine file manager (`reveal_entry` by absolute path), so only the local door builds such a link. A click asks `place_path` again: a vanished directory opens nothing, and the checkout page is found by `FileOpener.pageOf` via `list_branches`, as for another project's file. `Column.point` (app tier) holds the `(RootId, path)` request while the `ExplorerView` of the tree with the same root expands the directory, its ancestors, and selects it. The request outlives the `goto` itself, because `Explorer` (graph tier) is built lazily and learns its root only after the navigation, but lives only with it: `Column.point` drives the navigation itself and drops the request if the navigation was refused, led somewhere other than a Checkout page, or the next navigation leaves it. Otherwise that copy's tree, opened later for another reason, would walk to the directory of a long-dead click on its own. Expanding a path in the tree — by directory request or by active tab — is one intent in `ExplorerView`: only the last one gets selection and focus, so a restored active tab or an earlier request whose directory read finished later does not drag the tree away from the just-opened directory. Of the outside places, a checkout directory has only Finder (`reveal_entry`): the tree calls `open_in_editor` only for files.
- `place_path` reads the path as absolute, from `from` (the thread root) or from the `root` checkout (the root id, as the thread's file panel calls its checkout), otherwise from the calling checkout's root, otherwise from the project's main checkout. With `thread`, a relative path that matched nothing is read again from that thread's scratch: bare names the agent passes to Tagma operations live there, and a link carrying `LinkFrom.thread` (thread feed, its Changes) passes that thread. The `checkout-files` module learns where the scratch lives through the `ScratchFolders` port, which the composition fills from `ScratchAreas`. The palette passes its own checkout's root, so a worktree relative path does not slide into the main one. A file from someone else's checkout gets a tab with the branch name (from `worktree` in `list_branches`).
- `FileOpener`, the file's outside places (`Outside`: machine editors, Finder), and the disk byte address live with the rest of the file code in `features/checkout/files`: the checkout declares the "file" view, and `opening` knows no view. Path recognition (`pathCode`) and its check (`PathChecks`) stay in `features/opening`: chat, terminal, and markdown call them, not only checkout. A check answer is already a link builder: the `PathRoads` road from checkout supplies it, because `opening` knows neither the link view nor the `place_path` answer shape.

A tab is `rootId` + path + view; the `diff` view does not distinguish side and commit — they change in place (`aimDiff`), so one path has one diff tab. `PlatformStorage` on the `GraphAim` holds tabs, the active one, recent paths, the primary selection with direction, and scroll; contents and one-off navigation to a line (`goto`) are not stored. An `OpenedDocument` session is recreated only when `rootId`/path changes: the effect reads a derivative of them, not the tab itself — otherwise writing the cursor position when closing the editor would recreate the session forever. One `document.subscribe` on `(rootId, path)` is held by the `Documents` registry (app tier, keyed by project, root, path) with refcount: source and preview of one file share a document; after the last tab closes the subscription ends (no keep-alive), except a document with unwritten content: it lives until the write lands — see the autosave note.

The view position is written by the editor itself on close and is bound to the tab id, not to "active"; a closed tab enters it into the closed stack, so Cmd+Shift+T restores the primary selection and scroll. Tabs of your own checkout (without a branch) rebind to the new `rootId` when the worktree is recreated; a tab of someone else's branch that is gone from `list_branches` counts as orphaned and renders a stub. File search is one pass of a finite stream (`hold(..., 'once')`): without it `Live` would resubscribe after `done` and ripgrep would run again.
