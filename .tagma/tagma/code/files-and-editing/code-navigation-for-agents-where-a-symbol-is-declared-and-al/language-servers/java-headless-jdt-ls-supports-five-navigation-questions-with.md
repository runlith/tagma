## Observation — what was read

Eclipse JDT Language Server answers all five questions through standard LSP requests in the full, semantic server; no editor process is needed to run it. The upstream sources were read at commit `408588f9739bf91cd7acc280e6af008d4220ff61`, the version in `pom.xml` is `1.64.0-SNAPSHOT`, along with the primary LSP 3.17 documentation. Local read-only copy: `/opt/workspaces/runlith/.external/jdtls-nav-research`. This is a reading of the snapshot, not a check of a released milestone; the server was neither built nor launched, and there are no own measurements. [Version](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/pom.xml#L9).

## Observation — the LSP matrix

| Question | Full JDT LS capability | Request and actual result |
|---|---|---|
| Definition | `definitionProvider: true` when the client has no dynamic registration | `textDocument/definition`, `{textDocument:{uri},position:{line,character}}`; JDT LS returns the `Location[]` branch, usually 0–1 elements, though LSP also allows `LocationLink[]`. |
| References | `referencesProvider: true` when there is no dynamic registration | `textDocument/references`, position and `context.includeDeclaration`; `Location[]`, with no containing-function name. |
| Incoming callers | `callHierarchyProvider: true` | First `textDocument/prepareCallHierarchy` by position → `CallHierarchyItem[] | null`, then `callHierarchy/incomingCalls` with `{item}` → elements `{from,fromRanges}` or `null`. `from` denotes the calling member, `fromRanges` — the call sites in its document. |
| Outgoing callees | The same `callHierarchyProvider`, no separate capability | The same prepare, then `callHierarchy/outgoingCalls` with `{item}` → `{to,fromRanges}[] | null`; `to` denotes the called member, the ranges belong to the calling side's document. |
| Implementations | `implementationProvider: true` when there is no dynamic registration | `textDocument/implementation`, position; JDT LS returns the `Location[]` branch. This is a separate type/method search, not a call list. |

With `textDocument.definition.dynamicRegistration`, `textDocument.references.dynamicRegistration` or `textDocument.implementation.dynamicRegistration = true` the corresponding static capability is skipped, then the server calls `client/registerCapability`. Call hierarchy is declared statically without this fork. The client capability for call hierarchy is `textDocument.callHierarchy`; incoming/outgoing share the prepare registration that appeared in LSP 3.16. LSP coordinates require a column, so the spec's “path + line + name” input cannot be passed directly: the adapter will have to resolve the selected symbol's position.

Evidence: [InitHandler, capability declarations](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/InitHandler.java#L162-L209), [dynamic registration](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/JDTLanguageServer.java#L381-L419), [actual definition/references handlers](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/JDTLanguageServer.java#L732-L773), [implementation handler](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/JDTLanguageServer.java#L1091-L1097), [definition-addition conditions](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ImplementationsHandler.java#L59-L131), [mapper](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ImplementationToLocationMapper.java#L53-L85).

## Observation — scope and incompleteness

- **References:** the search runs over the Eclipse workspace's Java projects, sources and referenced projects. `java.search.scope=all` is the default; `projectOnly` excludes application/system libraries but means the workspace projects' sources, not only the selected symbol's project. `main` excludes test code. In `all`, application libraries are included, system libraries — when the selected symbol sits in the JRE. `A_INACCURATE` matches are dropped. When the type root/symbol cannot be resolved an empty list is returned; part of `CoreException` is logged, after which the accumulated locations are still returned. [ReferencesHandler](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ReferencesHandler.java#L62-L135), [match and binary filtering](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ReferencesHandler.java#L181-L214).
- **Definition and binaries:** the source unit must resolve into the JDT model. For class files, attached sources, other-source lookup, decompiled sources and a class-file fallback are provided. The result may carry a `jdt:` URI rather than a checkout file path. References/implementations include class-file locations under `extendedClientCapabilities.classFileContentsSupport`; the default of this extended flag is false. The snapshot also declares the standard LSP 3.18 `workspace/textDocumentContent` for the `jdt` scheme, alongside the existing `java/classFileContents`. Bare locations are not enough to promise the original sources' line: [Definition](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/NavigateToDefinitionHandler.java#L165-L198), [extended capability](https://github.com/eclipse-jdt-ls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/preferences/ClientPreferences.java#L240-L243), [content capability](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/InitHandler.java#L211-L216).
- **Call hierarchy:** JDT LS uses `CallHierarchyCore` from JDT core manipulation rather than computing a runtime call graph. It prepares a resolved member or the containing method/initializer/field; before searching it reconciles the compilation unit. For incoming, `projectOnly` creates a scope of sources and referenced projects; otherwise a workspace scope. Separate static incoming/outgoing caches are shared process-wide and cleared by each prepare. [CallHierarchyHandler](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/CallHierarchyHandler.java#L72-L275), [outgoing and JDT delegation](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/CallHierarchyHandler.java#L287-L351).
- **Implementations:** the selected element must be an `IType` or `IMethod`. For a type, all subtypes are taken, so the type list does not equal only the concrete implementations. For a method, receiver binding and hierarchy scope are used; accurate, non-abstract method matches are accepted. Private/final/static methods, constructors and methods of final types are not searched as overridden implementations. In some contexts the handler adds the definition itself. For binaries without attached sources the mapper may return the default `[0,0]` position. [ImplementationCollector](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ImplementationCollector.java#L128-L259), [definition-addition conditions](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ImplementationsHandler.java#L59-L131), [mapper](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/ImplementationToLocationMapper.java#L53-L85).

## Observation — the headless process and its lifecycle

Upstream documents launching the JVM via the Equinox launcher, `-Declipse.application=org.eclipse.jdt.ls.core.id1`, OS-specific `-configuration` and an absolute `-data` unique per workspace/project. Java 21+ is required. stdio, sockets and named pipes are supported; without connection environment variables stdin/stdout are used. In socket mode the client listens and the server connects. Maven is supported via M2E, Gradle via Buildship; no separate UI editor process is needed. [README](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/README.md#L42-L123).

After `initialize`/`initialized` come background Eclipse jobs for import/build/index. The server sends `ServiceReady` before subsequently waiting on build jobs, registering watchers and checking indexes: this message alone does not prove full index readiness. The full server declares incremental `didOpen`/`didChange`/`didClose`, `didSave` with text, and workspace folders. It requests `workspace/didChangeWatchedFiles` from the client via dynamic registration with patterns for sources, build files and libraries; this is compatible with delivering events from Tagma's existing watcher. That this reading proves no other internal watching mechanisms exist is not established. [Startup order](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/JDTLanguageServer.java#L307-L358), [watch registration](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/managers/StandardProjectsManager.java#L485-L596).

Lightweight `SyntaxLanguageServer` is a different mode: it declares definition but not references, implementations or call hierarchy. It cannot stand in for the full server for a cheap start of all five operations. [SyntaxInitHandler](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/syntaxserver/SyntaxInitHandler.java#L54-L104).

The full server is not a guaranteed read-only checkout analyzer: Eclipse metadata may be created in the project root; the corresponding system property `java.import.generatesMetadataFilesAtProjectRoot` defaults to true when unset. Gradle import uses the Buildship configuration with Gradle JVM settings, so “one engine JVM” does not prove “a single process for the whole execution tree”. [Metadata default](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.filesystem/src/org/eclipse/jdt/ls/core/internal/filesystem/JLSFsUtils.java#L189-L198), [Gradle configuration](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/managers/GradleProjectImporter.java#L527-L558).

## Observation — cold start, memory and index storage

The README cites `-Xmx1G`: this is an example Java heap ceiling, not actual RSS, not minimum memory, and not proof that 1 GB suffices for an arbitrary checkout. The read materials establish no universal RSS numbers, cold-start p50/p95 or latency of the five requests.

The `on-demand-import.md` document on this snapshot describes the new opt-in `java.import.mode=ondemand`: instead of a default full import, projects open on `didOpen`, closed projects keep a disk index. It cites the authors' reference points: ~18 ms workspace initialization without import, ~6 s for the first module import, ~450 ms reopen; for Quarkus with 1300+ modules — over two hours of classpath resolution in full mode and OOM. These are not this study's own measurements; hardware, command, Quarkus version and a reproducible harness are not stated in the document, so the numbers are no headless cold-start benchmark. A hard limitation is written down directly: references/call hierarchy do not see unimported workspace projects. For Maven dependencies of such modules, JARs installed in the local repository are needed. [Upstream on-demand import](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/docs/on-demand-import.md).

`-Djdt.core.sharedIndexLocation=...` turns on moving library indexes to a shared directory; the implementation iterates library classpath entries and handles external JARs. This is reuse of library indexes across workspaces, not a source index by Git commit and not a shared live worktree layer. [IndexUtils](https://github.com/eclipse-jdtls/eclipse.jdt.ls/blob/408588f9739bf91cd7acc280e6af008d4220ff61/org.eclipse.jdt.ls.core/src/org/eclipse/jdt/ls/core/internal/handlers/IndexUtils.java#L61-L149), [upstream change](https://github.com/eclipse-jdtls/eclipse.jdt.ls/pull/2341).

## Conclusion for the adapter

One long-lived full JDT LS with a separate `-data` per checkout and a shared Tagma LSP client is a reasoned integration model, not a measured optimum. The client can receive callers and call ranges directly but must separately read/render the source text, handle `jdt:` resources, project readiness and changed documents. An empty `Location[]` does not prove there are no references: the code drops inaccurate matches and allows empty results for an unresolvable element or a failure. Neither the capabilities nor the reviewed handlers' answers carry the spec-required list of invisible files or type-unlinked text matches; this tail needs its own coverage accounting in the adapter. On-demand mode without such a tail is especially dangerous for callers/references. Calls via reflection, DI or strings should not be promised as a complete runtime graph on the basis of static JDT search.

## Not established

Actual RSS and startup on a small/large Java checkout, warm latency, correctness of concurrent prepare/incoming/outgoing from different agents, completeness on unresolved/generated code and non-standard build layouts, whether extra Gradle processes are required, and a metadata mode safe for the concrete project were not checked. It is not established in which released milestone the snapshot's on-demand import and LSP 3.18 content capabilities are available. The spec's reference on Java was not run; the study confirms the protocol's existence and the current source's limitations, not the quality of Tagma's future adapter.
