Hypothesis: before an edit, an agent misses fewer calls and drowns less in same-named matches if it has `definition`, `references` and `callers` from a TypeScript language service next to grep. Build the server and attach it to runlith via `add_mcp_server`. Then collect 10–20 cases from thread history where an agent looked for usages or calls before an edit, and compare what the agent's grep gave versus what the tool gives: misses, extra matches, steps. Separately measure load time, `tsc --api` process memory, and request latency. If the hypothesis holds, the right version is a navigation core with per-language adapters inside Tagma, not this package.

Result, 18 cases from runlith threads, compared on the 2026-10-22 code (measurement [[01a160ad-a3fc-7bfd-9429-b5b92abc25f6|code-nav-measure]]): the hypothesis is partly confirmed. The agent's grep drowned in same-named method noise in 6 cases (for `ThreadAggregate.release`, 40 of 43 lines were unrelated) and lost real calls through a narrowed path in 3 (for `withdrawRun` — zero lines instead of five); the tool found them all. The tool itself does not see `.svelte` (3 cases, 6 places), string keys, and documentation, and it does not always find the interface-to-implementation link in object literals. The search took 27 steps versus 18 — a small saving. One sample on a 12-core / 32 GB machine: `tsc --api` memory 2–4.25 GB over 92 projects, first request about 12 s, warm ones usually about 200 ms, but 5–17 s after file edits by neighbors, because every edit rebuilds programs. What the sample does not prove: that grep misses led to errors (a signature break is caught by typecheck) or that agents would use the tool themselves.

Second round, TypeScript only without Svelte, 31 cases from history: benefit confirmed. The agent's grep lost calls in 15 cases (13) or gave more noise than true lines (10); in them code-nav gave the full list in one call with no false matches. Its misses are 5 cases, all from TypeScript reference-search semantics: a destructuring chain, a structural implementation without `implements`, an object literal without a contextual type, a constant and a type sharing one name; the answer still looks complete ("1 reference"). No broken edit caused by a grep miss was found in the threads; the value is where behavior changes, not the signature. The 5–17 s delays from rebuilds after unrelated edits do not occur: swapping a changed file cost 1–3 ms. Open code-nav defects: the symbol is also searched inside a string literal on the request line; "implements it" is put on a shorthand return of a function.

A/B, one run per branch: two Muse Spark 1.3 xhigh agents with one task — all calls and implementations of seven symbols (`RunLifecycle.stop`, `OperatorNotes.standing`, `ThreadHandle.release`, `RunControl.ended`, `runTransition`, `HarnessInputs.deliver`, `rowsOver`); one allowed only code-nav and read ([[01a160cf-50ae-7fbe-8af8-bc6701b1c747|nav-codenav]]), the other only grep, glob, read and bash ([[01a160cf-50be-711a-b03d-cd9bc39da93f|nav-grep]]). With code-nav: 404k input tokens without cache and 570k from cache, 22k output, 110 s, 58 calls, no misses. With grep: 1.42M without cache and 2.93M from cache, 27k output, 204 s, 77 calls, missing the `core(threadId).release()` call in `protocolFork.stest.ts:23` and the `inputs: { deliver: unexpected }` implementation in `placement.itest.ts:156`. Neither side has false places.

Repeat of the same task on two more agents per side; averages over three runs. With code-nav: 267k input without cache, 16k output, 87 s, 39 calls. With grep: 1.28M without cache, 29k output, 195 s, 89 calls. Of 74 true places, code-nav missed 0, 3 and 3 — all `rowsOver` calls through destructuring, the answer "0 calls". Grep missed 2, 1 and 2: the implementation in `placement.itest.ts:156` in all three runs, plus one `protocolFork.stest.ts:23` call and one `moves.ts:97` each. No false places on either side.
