The runner keeps Muse's session as the one model loop of a Tagma thread, so its cache and history survive between turns; every choice below protects that or keeps the user's own Muse setup out of the thread.

- **A Muse home per account, settings per thread.** `HOME` and the XDG data, state and cache directories point at a home under Tagma's data directory, which reaches the user's login only (a link to the CLI's `auth.json`, and on macOS also `Library/Keychains`, where the token lives; off macOS the token is in `auth.json` itself). Without it the user's rules, skills, hooks and settings ride every request and the user's `muse resume` list fills with Tagma sessions. `XDG_CONFIG_HOME` is per thread, because `settings.json` carries that thread's frozen prompt and toolset: one file shared by two threads would hand one thread the other's prompt at its next host start.
- **Muse updates itself.** No spawn sets `MUSE_NO_AUTO_UPDATE`: the launcher's update runs detached while the call execs the installed binary, so a live host is never replaced, while with the variable a user who reaches Muse only through Tagma would never update past a version Meta's release manifest retires (`must_download`, `min_version`). A new binary between host starts is the skew any user's own update causes; MSP v1 is additive.
- **The host reads prompt and catalog once.** Its selected prompt, web mode and ordered catalog are saved per vendor session beside the thread's settings. Resume and reopen reuse those definitions and their order while the prompt, web mode and tool-name set agree; a changed description, schema or catalog order alone cannot silently replace a prefix the live source still uses. A deliberate prompt, web or tool-name change selects and saves a new configuration before restarting the host. A session predating this saved state has no recoverable proof of its original catalog.
- **A disclosure never touches the host.** Muse never re-lists MCP tools, so the thread runs the `dispatch` catalog: the host key holds only the direct tools, `tool_search` and `call_tool`, and a tool `tool_search` reveals is reached through `call_tool`. The feed announces such a call under the revealed tool's own name and input, read through the bridge that unwraps it, because Muse's item and approval name only `call_tool`: announced as Muse names it, the journal, display and law would see a call of a tool that does not exist.
- **A Tagma turn owns the Muse turns its steers open.** Muse drains an accepted steer into the running turn, or, when that turn ends first, runs it as a follow-up turn under the steer's command id. The Tagma turn ends only after every accepted steer was read and every turn it owns completed. Ending at the first `turn/completed` left the follow-up running with no Tagma turn around it: its approval request went unanswered and every later `turn/start` queued behind it in Muse forever. A Muse turn no Tagma turn owns is interrupted for the same reason, and its trailing deltas and approvals are not taken into the next turn. Muse's admission of a steer is not its reading: the steer is answered read only at its steered item, so a word a stop or failure left unread goes back to the core rather than being recorded as heard.
- **A `configError` turn drops the host.** On resume Muse runs a turn it still had queued before the session MCP server is up, records an MCP startup audit fault, and fails every later turn of that host process. The next turn starts a fresh host and resumes; the session itself is sound.
- **Muse fork and rewind are journal rebuilds, not byte-exact vendor copies.** Native `session/fork` loses the session MCP configuration on 1.4.14: the next turn fails with an unknown MCP tool. Cold resume can reattach it, but the inherited history travels as `external_history` and Meta cache identity is unproven. The runner keeps the journal road, which does not retain the vendor's reasoning or private history; it cannot promise source-request identity.
- **Session ids and turn ids are UUIDv7.** Muse refuses other session ids, and a v7 Tagma turn id becomes the `turn/start` command id, so Muse's turn id is Tagma's.
- **Every Tagma call is approved at once.** Sessions run `:ask-me` with `promptUnmatched`, so no Muse judge reviews a call; Tagma's door judges it. Only a vendor `web_fetch` goes to the thread's own confirmation.

- **Every word, call and control ends on a vendor fact.** A host ends on process exit or MSP transport EOF, whichever comes first. MSP promises no wire order between a `view/gap` and its neighbours, so the hole is spliced by cursor: paged from `after` until the first event that already arrived, live or still queued, and handed on ahead of the queued ones; an event delivered once is never delivered again, and a page that makes no progress, reads wrong or fails ends the host rather than counting the hole filled. A turn's outcome is read only once the host delivered every frame it received before the end, so a hole paged back after `turn/completed` still lands in its turn. A stop before `turn/start` is answered sends nothing on a host that still answers; a stop while Muse holds back its answer to the opening, the turn start or a compaction admission replaces the host, because only the host's end proves that what Muse may have admitted does not run on unseen. The opening counts as heard only when Muse starts the turn, not when it queues it. A stopped turn answers each accepted unread steer by an admitted `turn/unqueue` or by what a `session/read` snapshot or inline history shows Muse holds of it, never by local stop state, since Muse would otherwise run the follow-up after the core handed the words back; a read that serves no history (`none`, e.g. over its budget) leaves the steer's fate unknown and refuses it rather than handing it back. A refused approval decision stops every turn the Tagma turn owns and fails it only once Muse ended them and its accepted steers have fates; a refused interrupt replaces the host: a Muse turn left waiting on an undecided call blocks every later turn of the session.
- **Side questions run in a side session.** `session/sideChat` copies the warm session's history into a new session, which opens on the host's default model; the runner pins the thread's model and effort there before asking. One side question at a time, reserved before the first command, so a second is refused rather than opening a side session no one waits on. A side turn runs Muse's own toolset, so it may ask back (`request_user_input`); nothing answers there, so such a request fails the side question and interrupts its turn. Muse reports no cache lifetime, so the runner stamps every measured request with the lifetime Muse Code declares (`MUSE_CODE_CACHE_SECONDS`, the provider's `cacheLifetime` too): the session copy for recap and titles then expires with the cache, as Claude's does, instead of being dropped at the turn's end for having no deadline.
- **Each model request is keyed by its own ordinal in the turn.** Muse's `session/tokenUsage` and retry frames name no request, and the core lands a measurement or retry once per key, refusing the same key with other content. So the runner numbers the turn's requests and keys both by that number, never by the message id text and calls group under: a request with no reasoning or text before its usage (a tool-only call) shares the previous request's message id.
- **A turn costs the session's priced rise.** Muse prices the session cumulatively, so a turn's cost is the rise over the turn before; a new session starts at zero, and the last total seen is kept per session in the thread's config directory, since resume serves no total: the first turn after a runner restart is priced from it, and a session with no kept total stays unpriced until a turn has seen one.
- **A compaction cut off by a stop is reconciled.** A stop or host death during a compaction leaves unknown whether Muse completed it; that doubt and the last recorded compaction are kept per session beside the priced total, since a host death ends the runner itself. The session's next turn or compaction, in this runner or a later one, reads `session/read` and records the boundary of a completed compaction no frame delivered — as automatic, so it never answers a compaction request waiting at that moment; a read that serves no history keeps the doubt for the next. Tagma would otherwise keep hosting history Muse already folded away. Both per-session files are replaced atomically, and an unreadable priced total reads as unknown, never as zero, which would charge the session's whole spend again.
- **Muse's own compaction waits behind Tagma's.** Muse cannot turn automatic compaction off, so its thresholds stand at 0.97/0.99 and Tagma's threshold fires first.

Muse's compaction keeps its summary inside the session: MSP gives the client no retelling, so the boundary Tagma records carries an empty summary, and Tagma's journal is not folded on it.
