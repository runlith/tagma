What a client can control through `muse serve` (MSP) on Muse Code 1.4.10 (`1.4.10-R6427.1`, macOS arm64) with `@muse-code/sdk` 1.4.10 for live runs and 1.4.14 types/schema read. Date 2026-11-01. Account: the operator's signed-in Meta subscription. Model for all live turns: `muse-spark-1.2` (cheapest non-contributor row of `model/list`; no cost data is published, `cost: null`), `reasoningEffort: minimal`.

**Method.** A Node harness over `spawnMspConnection` (handler-level frame log, not the raw byte stream) drove `muse serve` in scratch workspaces. What the model received is read from `muse trace inspect --session-log <session.jsonl> --render-mode verbose` (it prints "Run Configuration": base instructions, developer prompt, every run-context message with byte size, the tool list, the model-input lanes, and per-request totals), not from the model's self-report. The wire schema came from `muse schema generate-json-schema`. Settings keys were found by `muse serve -c KEY=VALUE` acceptance/refusal, `strings` of the binary and the docs at dev.meta.ai. Five model turns were spent; turn 1 fanned out into 18 model calls because the prompt invited tool experiments.

## 1. Does a subscription turn succeed today?
Observed: yes. Five turns on the operator's login completed through `muse serve`, answered by `muse-spark-1.2` (`session/tokenUsage.modelId`), with no 403 and no `client_attestation_denied`. `usage/changed` after a turn reported a subscription window (`window.usedPercent`, a 300-minute window, and a weekly `usedPercent`). Turn 1 did not reach `turn/completed` within 150 s although the answer ("done") was produced (`turn/foregroundCompleted`): see section 6.
Unknown: a different account/tier; whether Meta's attestation check is applied to `muse serve` differently from the TUI later.

## 2. Can the main agent's system prompt be replaced or extended?
Observed:
- `muse serve --agents` and `--preset` are refused (`unexpected argument`); the overlay and presets exist only on the top-level `muse`. `muse serve --help` lists no such flag.
- `session/start` has no instruction field (`config` admits only `mcpServers`; unknown keys are ignored on the wire) and `turn/start` has none either.
- `-c run.system_prompt="..."` is accepted (string) and **replaces the whole base instructions**: trace "base instructions: provider_default 45892 bytes" became "settings 60 bytes" with exactly the given text; the model request's `option:meta.instructions` lane carried it. The value is a host-wide launch setting, so it is fixed per `muse serve` process and applies to every session that host loads.
- `-c run.developer_prompt="..."` is accepted (string) and the trace lists a `developer` lane ("developer prompt: settings 18 bytes"), but the per-request lane totals of that run do not include its bytes, so whether it reaches the model is not established.
- Other setting keys accepted by `-c` (type-checked, effect not all measured): `run.toolset`, `run.reminder_roster`, `run.workflow_trigger_mode`, `tools.web_search.mode`, `skills.activation.*`, `hooks`, `managed_hooks_path`, `runtime_capabilities`, `agents.execution_capacity`, `presets` (free-form map, schema unknown), `session_retention_days`, `mcpServers.<name>`. Unknown keys refuse the run (`unknown key: no such setting`). `permissions.default_profile` is refused on `-c` (profile selection is wire-only: `session/start.permissionProfile`).
- With the Meta provider the base prompt is replaceable; the echo provider refuses `run.system_prompt` ("provider does not support base instructions").
- Docs describe no agent-definition file format for `--agents`; its schema was not found. The `muse` top level `--agents <JSON>` was not exercised.
Inferred: `run.system_prompt` is the one supported replacement point for a Tagma-driven runner; a per-session prompt would need one host per prompt or the prompt in the user turn.

## 3. Which built-in tools does the model receive?
Evidence: the trace "tools:" line of each run (the request tool list).
- (a) Default (turn 1, with one session MCP server): `workflow, read_file, search, write_file, edit_file, read_memory, add_memory, edit_memory, work_stop, work_list, web_fetch, web_search, bash, bash_input, monitor, cron_create, cron_delete, cron_list, get_goal, create_goal, update_goal, report_progress, request_user_input, read_skill, snooze_reminder, write_todos` plus `mcp__probe__*`.
- (b) `--disable-shell --disable-write` (turn 4): removes `bash`, `bash_input`, `write_file`, `edit_file`, `add_memory`, `edit_memory`. Still sent: `workflow, read_file, search, read_memory, work_stop, work_list, web_fetch, web_search, monitor, cron_*, get_goal, create_goal, update_goal, report_progress, request_user_input, read_skill, snooze_reminder, write_todos`. A `capability_policy` developer message is added ("Filesystem writes are disabled... Shell execution is disabled...").
- (c) `-c 'run.toolset=[...]'` is a whitelist over built-ins and MCP names: `["read_file","mcp__probe__*"]` sent exactly `read_file, mcp__probe__probe_add_tool, mcp__probe__probe_echo`; `["mcp__probe__*"]` sent only the MCP tools (turn 3, which also used the disable flags); `["web_fetch","bash","mcp__probe__probe_echo"]` and `[]` were checked with the echo provider (tools: exactly those names / none). A name that is neither a built-in nor an `mcp__` pattern fails the launch (`unknown tool names: x`). `*` patterns are accepted for MCP names. `--preset empty` could not be tried (refused on `serve`).
- File- and web-reading built-ins: `read_file`, `search`, `read_memory`, `read_skill`, `web_fetch`, `web_search`, `bash`/`bash_input` (shell), `monitor`, and `workflow` (spawns child agents). `--disable-shell`/`--disable-write` remove only the shell and write ones; `read_file`, `search`, `web_fetch`, `web_search`, `read_memory`, `read_skill`, `monitor`, `workflow` remain. Only `run.toolset` removes the rest (turn 3: none of them sent). `tools.web_search.mode` is accepted but its effect was not measured.
Unknown: whether `run.toolset` is also honoured for child agents of `workflow` when `workflow` is whitelisted; whether `--disable-shell` combined with a toolset naming `bash` removes it.

## 4. Session MCP
Observed (turns 1, 3, 4, 5; MCP server logged raw `tools/*` requests):
- `initialize` with `requestedCapabilities: ["sessionMcp"]` grants it. `session/start.config.mcpServers.<name>` takes `stdio` (`command, args, env, framing, mode`) or `streamableHttp` (`url, headers, mode`); a `session/resume` takes the same `config`.
- Names: the model sees `mcp__<server>__<tool>`, e.g. `mcp__probe__probe_echo`; non-alphanumerics become `_`. Tools named `bash`, `read_file`, `edit_file` in the MCP server were sent as `mcp__probe__bash` etc., so no clash with built-ins (turn 3).
- Muse calls `initialize`, `notifications/initialized`, `tools/list` once at session start, before the first model call, and registers the result for the session. After a tool call made the server send `notifications/tools/list_changed` and list a new tool, Muse never issued a second `tools/list` and never offered the new tool (turn 1: the model tried `probe_new_tool` and fell back to other tools). Docs: "A process reads its MCP configuration once".
- Link to the MSP item: the MCP `tools/call` params are `{name, arguments, _meta: {callId, idempotencyKey}}` with `callId` = `call_...` equal to the MSP `toolCall` item `callId` and to `approval/request.toolCallId`; `idempotencyKey` = `tool:<callId>`. No `itemId`, turn id or session id in `_meta`. The MSP `itemId` is on the `item/*` notifications beside the same `callId`. No other MSP id reaches an MCP server (stdio env additions are only what the config sets; docs add `MUSE_SESSION_ID` for stdio servers, not verified).
- `streamableHttp` on `127.0.0.1` works with a custom header (turn 4: `x-probe: custom-header-ok` on every POST; request carried `accept: application/json, text/event-stream`, `mcp-protocol-version: 2025-06-18`; my server answered plain JSON and never issued an `mcp-session-id`; no GET was observed). T3 Code ships the same shape with an `Authorization` header and `mode: "optional"`. Docs: header values are literal, no `${VAR}` expansion; `mode` defaults to `required` (a failing server aborts the run).
- Approvals: the default permission profile is `:auto-review`: with `approvalMode: promptUnmatched` an LLM judge (`approval/resolved.resolvedBy: "llmJudge"`) approved MCP calls without any `approval/request` (turn 1; the judge adds model calls). With `permissionProfile: ":ask-me"` and `promptUnmatched` the host sends the `approval/request` server request (also the `approval/requested` notification) with `toolName: mcp__probe__probe_echo`, `toolCallId`, `itemId`, `availableChoices` (`allow_once`, `allow_session`, `allow_local_mcp_tool` = persistent "always allow", `abort`). The decision is the **command `approval/decide`** `{sessionId, approvalId, choiceId, requirementId: currentRequirementId}`; replying to the server request with `{choiceId}` does not decide it and the turn hangs at the tool call (turn 2, observed until the host was closed). After `approval/decide` (`status: accepted, terminal: true`) the call reached the MCP server (turn 5). With `approvalMode: allowAll` plus `permissionProfile: ":unrestricted"` no approval was raised (turns 3, 4). `allowAll` alone with the default profile was not run.
Unknown: behaviour when the MCP server dies mid-turn; read-only hint skipping approval under `onRequest` (docs only); SSE/GET channel use by Muse's HTTP client with a server that offers it.

## 5. What reaches the model besides the prompt
Observed from the per-request lanes (the first request is ~114 KB by default, 62.5 KB with `run.system_prompt` replaced, 15 k input tokens versus 36 k in turn 1):
- Base instructions: 45,892 bytes, "You are Muse Code, an agentic coding CLI ... powered by Muse Spark ..." (replaceable, section 2).
- Run-context developer messages, all at session start: `workspace_identity` (219), `security_mode` (471, states approval/sandbox/trust), `capability_policy` (222, only with the disable flags), `rules_file` (23.6 KB), `workflow_choice` + `workflow_cookbook` (4.5 KB, only when the `workflow` tool is present), `agent_definition_catalog`, `skills` catalog (32 KB), `meta_context_note` (4.4 KB), `session_identity` (690, tells the model its session log path), `sandbox_policy` (817, only with shell), `memory_snapshot` (1.1 KB).
- Rules: the **operator's user-level `~/.claude/CLAUDE.md`** was loaded into `rules_file` as `scope="user" ... written-for="Claude Code"` in every run, trusted or not. Setting `CLAUDE_CONFIG_DIR` and `CODEX_HOME` to empty directories did not stop it; a changed `HOME` broke login (turn failed `authRequired` in 112 ms, no model call; credentials are home-dependent). Project `AGENTS.md` in a git workspace was loaded only with `--trust-workspace` (`scope="project" path="AGENTS.md"`, canary present) and absent without it (canary count 0). Skills and hooks follow the same trust rule per docs (project-level ones; not separately tested).
- User-level hooks from `~/.config/muse/settings.json` (here: hooks installed by a third-party agent manager) fire as `hookRun` items in every served session; `-c hooks={}` did not suppress them. They run outside the sandbox and the approval system per docs.
- Hidden extra model work: with defaults, "reminder" child sessions (`skill-reminder`, `scope-reminder`) run beside the turn and hold `turn/completed` back (`turn/foregroundCompleted` names `blockingAgents`); turn 1 made 18 model calls. `-c 'run.reminder_roster=[]'` removed them (0 `reminderChild` items in turns 3-5).
- Memory under `.agents/memory` is loaded as the `memory_snapshot` message (committed project memory even if untrusted, per docs).
Unknown: how to switch off user rules/skills catalog/memory snapshot per host (no key found); the exact effect of `skills.activation.*`; whether `run.developer_prompt` is sent.

## 6. Usage, turn end, fork, resume
Shapes (schema + live):
- `session/tokenUsage`: `{sessionId, turnId, modelId, usage:{inputTokens, outputTokens, cachedTokens, cacheWriteTokens?, cacheReadTokens?, reasoningTokens}, promptTokens, totalTokens, finishReason, durationMs, cumulative:{promptTokens, outputTokens, totalTokens, cost?}}` per model completion.
- `session/contextUsage`: `{sessionId, windowTokens, usedTokens, pressure: "normal"|...}` (window 1,007,997 for `muse-spark-1.2`).
- `usage/changed` notification and `usage/read` result `{usage?}`: `{window:{usedPercent, windowDurationMins, resetsAtMs}, weekly:{usedPercent, resetsAtMs}, tier, observedAtMs}`; `usage/read` on a fresh host returned `{}` ("nothing observed") until a turn made the host observe a window.
- `turn/completed`: `{sessionId, turnId, terminal: completed|failed|cancelled, durationMs?, timeToFirstTokenMs?, usage?, error?: {kind, message}, reason?}`; a login problem arrives here as `terminal: failed, error.kind: authRequired`. `turn/foregroundCompleted` is non-terminal and appears only when reminder checks hold the turn open.
- `model/list` rows: `modelId, contextLimit, outputLimit, variants (effort tiers), defaultReasoningEffort, isDefault`; contributor rows carry the data-use notice.
- `session/resume` across a `muse serve` restart works: same `sessionId`, history retained (`turnCount`), `approvalMode` replayed (`source: "replay"`), a turn that was in flight is `cancelled` ("cancelled during model step"; `pendingRequests` empty, the pending approval is gone). The resumed session and a fork report the host default model (`muse-spark-1.3-contributor`), not the session's earlier model: the model must be re-set with `session/setModel {sessionId, model: {modelId, providerId}}` (accepted).
- `session/fork {sessionId, cutPoint: {lastTurnId}}` works from a closed-host session: new id, `forkedFrom: {sessionId, cutCursor, cutExplicit: true}`, `turnCount` kept, approval mode reset to `onRequest`.
- `permissionProfile/list` requires the experimental API; profiles `:auto-review` (default), `:ask-me`, `:unrestricted` were selected by id at `session/start`/`resume`.
