`tagma harness-run claude-code` is a stdio ACP agent the ACP driver launches as the thread's process. Inside is one long-lived Agent SDK `query()` per open session: streaming input, partial messages, `replay-user-messages` echo, the user-installed `claude`, `tools` of built-in tools per the turn answer (`['WebSearch', 'WebFetch']` with vendor web, else empty; see "Vendor web"), `strictMcpConfig`, `settingSources: []`, `bypassPermissions`, and the `tagma` MCP server inside the runner process (`type: 'sdk'`). The prompt is `read_hosted_agent`, tools are `read_hosted_tools`, every call is `call_hosted_tool` with `claudecode/toolUseId` as the call id; the runner executes nothing itself and walks to the server with the thread grant from its environment. The SDK loads only in this process. With `--cut` the same process is not an ACP agent but the offline session-cut server for terminal threads ([[f3d47a3e]]).

- **Turn tools.** The native agent's catalog is assembled per thread run, so the list is empty before the first turn. Before every prompt the runner takes `open_hosted_turn` (the turn context and step guidance go as the message's first text block) and re-reads the catalog; a changed list goes out as `notifications/tools/list_changed`, and the runner waits for a repeated `tools/list` (up to 5 s, a lapse is written to stderr) before sending the message — otherwise the model's first request would leave with the old list. Measured on 2.1.289: Claude Code re-reads the list on notification, including mid-turn. A call that moved the list (`offered`) answers after the same wait: Claude Code re-reads the list even with an open `tools/call`, and assembles the next request milliseconds after the result — without the wait a disclosed tool would reach the model a step late, and it would call it with no schema ([[d63511e6|probe on 2.1.296]]). All calls whose notifications are still unheard wait: a repeated `tools/list` releases them together. Cancelling the turn interrupts the prompt's wait, but not the notification itself: otherwise the list in Claude Code would diverge from the served one. The next prompt with the same catalog awaits the same repeated `tools/list`, or its first request would leave with the old list.
- **Run prompt.** `open_hosted_turn` answers with both the prompt frozen for the run and the `web` value (see "Vendor web"); when the prompt differs from the one the query runs with, `web` differs, or the run holds different tool names, the runner reopens the query on the same session (resume, snapshot off) before sending words, so the new prompt takes effect from this turn. `Lifecycle` owns the reopen, which runs on its own fiber: cancelling the turn answers the prompt immediately, while the reopen runs to its end. Otherwise the session would be left with no query. Everyone needing the query (send, recall, interrupt, side question) awaits the reopen's end rather than being refused. Prompt and compaction land in the session ahead of this wait, so `session/cancel` catches them even during someone else's reopen. Closing the session interrupts the reopen, and a query still opening closes its scope. The native agent's prompt names tools by bare names, while Claude Code refuses a call to a name missing from its list (`No such tool available`), so the runner appends to the prompt (`servedPrompt` in the hosted kit's `bridge.ts`) that Tagma tools in the list are called `mcp__tagma__<name>`. It says nothing of deferred tools: the hosted thread's catalog hides them until disclosure, and the run context's `deferred-tools` section tells the model how to disclose them — only where deferred tools and `tool_search` exist. Claude Code itself refuses a pre-disclosure call of a deferred tool ("No such tool available"). A bare name executes as on the native road (`ClaudeCodeTools.receive` keeps the unprefixed name as is): the query opens with the SDK's documented `toolAliases` option — an alias from each run-catalog name to its list name (`names.ts`). Names arrive with `read_hosted_tools` (`names`: the whole catalog, not just the step's offering); a name whose `mcp__<server>__` prefix belongs to the session's own MCP server gets no alias. Aliases are set only when opening the query, while a run starts after the session opens, so every runner process's first turn reopens the query (~0.6 s in the [[d63511e6|probe]]), as does a turn whose run holds different names. `Translation` marks an alias call as a Tagma call under the same names (`Names.routed`).
- **Permission question.** The runner writes nothing to the ACP client about Tagma tool calls (the only question is the vendor's `WebFetch`, see "Vendor web"): `call_hosted_tool` answers when the call is executed or refused. A call the thread's mode asks about waits on the server: `ThreadHosting` places the thread's native approval and waits for the operator while the runner's HTTP request stays open. Cancelling the turn ends the run and lifts the wait; a broken request never lifts the question, and a retried call finds it by `toolCallId` (see [[fe7e09a3|approval outlives the MCP call]]).
- **Vendor web.** The runner never decides whose web the session has: `read_hosted_agent` answers `web` (`vendor` | `none`) when opening the session, and `open_hosted_turn` confirms it on every turn — a server decision (taken once at run opening and held with it) from the `agents.web` setting and the transport capability (one decision for native and acp). With `vendor`, Claude Code's `WebSearch` and `WebFetch` are the session's only built-in tools, while the hosted thread's catalog holds no Tagma web, so the model sees one search and one read, with no name filter in bridge; with `none`, `tools` is empty and there is no hook. When the turn's answer mismatches what the session opened with, the runner reopens the query the same way as a prompt change. The `vendor.ts` declaration (the wire name and Tagma name of each vendor tool) is read by `lifecycle.ts` (the `tools` list and the hook), `fetching.ts`, and `translate.ts`: both calls are `fetch`; in the journal they are called `websearch` and `webfetch`, as on a native thread; Tagma never executed them, and they carry no `_meta['tagma/executes']`. `WebFetch` leaves `pending` and gains `in_progress` from the hook that allowed it; the hook travels outside the message-reading loop and may overtake `tool_call`, so the start passes through `Translation`, and a call allowed before its `tool_call` leaves as `in_progress` immediately; `WebSearch` has no hook and, like other session MCP servers' calls, leaves `in_progress` with the `tool_use`: they have no other start evidence. `WebSearch` never asks: Tagma's `websearch` never asked either. `WebFetch` is asked by the `PreToolUse` hook (`fetching.ts`, matcher `WebFetch`): the ACP client receives `session/request_permission` with the `toolCall` (`toolCallId` — the `tool_use_id`, `kind: 'fetch'`, `rawInput` — the call input) and `allow_once`/`reject_once` options; the driver judges it as a vendor question (`fetch` → `webfetch`: in review mode it places the native "allow/deny" question, in others it answers itself). Only `selected allow_once` yields `permissionDecision: 'allow'`; a refusal, cancel, unreadable answer, or a refusal of the request itself is `deny` with a reason Claude Code hands the model as a call error. A turn interrupt by Claude Code cuts the hook's signal and ends the turn without awaiting its answer ([[b54e302c]]); the hook hands that signal to its question, and the abandoned client request breaks off with it. The hook waits up to a day for an answer: `timeout` sits on the `HookCallbackMatcher` itself, and on lapse or hook failure Claude Code never executes the call (the timeout default is unmeasured). Measurement 2026-10-09 (claude 2.1.295, SDK 0.3.292, haiku, one run each): `WebSearch` and `WebFetch` work on an OAuth account under `bypassPermissions`, only they are listed in `init`; a hook `deny` blocks `WebFetch` even under `bypassPermissions`; a 4 s hook with `timeout: 1` yields a "did not respond before its timeout… not executed" refusal, with `timeout: 3600` and an answer after 75 s the call executes. An end-to-end run through `claudeAgent` with the real adapter: `allow_once` — the page is read, `reject_once` — the call is `failed` with the hook's reason.
- **Execution on fact.** A Tagma call leaves for the client as `tool_call` with status `pending` and `_meta['tagma/executes']`: whether Claude Code executes it and when is its own decision, while hosting records the execution start for Tagma. Every Tagma tool is served with `readOnlyHint: true` (`destructiveHint` truthful, per `mutates`): under the runner's options the annotation changes only that Claude Code executes a message's calls in parallel rather than one by one ([[00a81b23|probe on 2.1.296]]; repeated when the `claude` version changes). Hosting holds the record order into the same paths (`ready`), as on native. Claude Code starts such a call while the model message is still being written, so `call_hosted_tool` arrives before `_tagma/said`. The `_tagma/said` boundary names the calls the message passed as `assistant` blocks (Claude Code yields a block at its end, before `message_stop`), not every started `tool_use`: a block an interrupt tore mid-input never reaches the message, and a boundary naming it would be a driver refusal. A message whose stream never started (no `message_start` with its id) is yielded by Claude Code as one `assistant` with all blocks — as the answer arrived after four 529s in the 2026-10-23 incident — and `Translation` closes it with a boundary right after its calls, naming all its `tool_use`. Without it hosting would await the message record before admitting the call, Claude Code would await the call result, and the turn would never end. A whole message with no calls gets no boundary and is sealed by the turn end: this is also how Claude Code yields service messages outside a turn (`Compaction canceled.` of a cancelled compaction), while a boundary with no open turn is a session failure for the driver. On entry the kit's `Bridge` marks the call id in `Handed`, shared for the session, and on `tool_result` `Translation` sets `tagma/executes: true` only when the call was marked, else an explicit `false`: such an ending is Claude Code's own words (a deferred or unknown tool, off-schema input, a call removed before sending), and the driver writes it itself instead of awaiting hosting. A `call_hosted_tool` refusal lifts the mark: the server never executed the call, and the driver also writes its ending with the refusal words. A server failure or unreadable answer keeps the mark — whether the server executed the call is unknown, and hosting or the run end closes it. A call with no `claudecode/toolUseId` in the MCP request `_meta` (the Claude descriptor's `callIdOf`) is never executed by `Bridge` and answered with an error: an id invented in its place would diverge from the `tool_use` record.
- **Broken calls and server restarts.** Claude Code's MCP-request cancel signal breaks the server HTTP call, but not the execution: hosting executes the call in the run scope, and it reaches its outcome or the run end. The runner process lives while its run holds the server (after a restart onto another build it plays the turn out and is replaced at rest, [[8711a398]]), so `ServerDoor` rides out the restart: the operation repeats every second with no limit while the server answers `run-not-held` (the new server has not adopted the run yet) or stays silent, while the shared client door rides out a starting server ([[db6732e6|waiting for start]]). Every door operation retries a request broken mid-flight: reads and `call_hosted_tool` are answered from the record, and `open_hosted_turn` answers an opening the agent has not taken yet afresh ([[7d6de4a6]]). Cancelling a turn still opening (the door answer, query reopen, repeated `tools/list`) interrupts the wait, and the prompt answers `cancelled`, handing nothing to Claude Code. Only so does a call in flight during a restart get an answer. A false error instead of an answer costs double: the model retries the call with a new id, while the first one, left with the `Handed` mark, stands `queued` in the feed until the turn ends. The retry never executes the call twice: hosting recognizes it by the call record (a running one joins, a `started` from the server's past life answers "unknown", an `ask_user` answer comes from the transcript).
- **End of query is end of process.** When the SDK `query` ends on its own (Claude Code crashed or closed), could not be reopened onto a new prompt, or the main thread's `assistant` body is unreadable, the session dies: awaiting prompt, steer, and compaction are refused, the runner closes input and exits with an error, and the driver sees the process death and raises the session anew instead of sending prompts into a dead query. `Lifecycle` records and announces the death, and it owns sending messages into the query.
- **Continuation with no words.** An empty `session/prompt` means keep working: when adding history and turn context leaves it with no content, `Turn` sends Claude Code a non-empty continuation instruction with this turn's id. Empty input after resume may add a synthetic assistant `No response requested.` even over a tool result and leave the request with no final user message; a model with no prefill refuses such a request. The runner never rewrites history or previous call results.
- **Fresh session.** While no message has gone into the session, Claude Code has not recorded its file; reopening it for a new prompt uses the same provenance (new or fork), not resume.
- **A new session carries the journal.** `session/new` reads the thread history with `read_hosted_history` (journal messages, paired and with attachments, no reasoning) and, when non-empty, writes the Claude Code session file from it (`transcript.ts`) and opens the query via `resume`; so a thread arriving from a native provider, as well as a "last N turns" fork, turn deletion, and restore, continue from the Tagma journal. The file is verified by reading `getSessionMessages`: when this `claude` version never read it, the file is deleted, and history goes before the first prompt as neutral hosted-kit blocks: text with role labels and image bytes in their places. Only this road carries hosted-session history: the recap driver never counts it for a profile with `hosts`. Probe 2.1.289: an externally assembled file with `tool_use`/`tool_result` is accepted by `resume`, the model sees the tool results; call ids are cleaned to `[A-Za-z0-9_-]`; a call's name is the one Claude Code knows it by: vendor tools — `WebSearch`/`WebFetch`, other MCP servers' calls — their full name, Tagma tools — `mcp__tagma__<name>`.

What upholds the driver contract (the thread run must start before `session/prompt`, or the turn runs with no tools or context):

- **Turn id.** The uuid of the message by which the runner hands the prompt to Claude Code is the request's `_meta['tagma/turn']` when it is a uuid, else its own. The prompt answer carries in `_meta['tagma/turn']` the prompt uuid and the turn's last record — the last main-thread record Claude Code yielded, its own echoed prompt included; a failed turn carries the same in its fault `data._meta`. By the prompt uuid `_tagma/rewind` finds the turn in the transcript (`getSessionMessages`) and forks the session on the record before it; so a Tagma turn id handed over as a uuid makes Tagma-turn rollback exact.
- **Fork and rewind are lazy.** `_tagma/fork` and `_tagma/rewind` open a new `query` with `resume` + `forkSession` + a new `sessionId` (+ `resumeSessionAt`) and answer with the new id immediately, but Claude Code writes the fork file only on the first message. A process dying before the next prompt leaves an id with no transcript, so the server keeps the fork origin until the child's first turn reached Claude Code and forks again from it. A fork with no `resumeSessionAt` (no point) copies the whole history; rolling back the first turn is a new empty session. A whole-copy fork carries `through`, the record ending the source transcript at the fork's birth, and every opening of the fork — the reopen its first turn makes included — resumes at that record: on the tail `resumeSessionAt` keeps the history whole (2.1.316 appends nothing when no record follows it, read from the client code), and once the source went on it cuts what came after. A record or turn the transcript no longer holds is refused `notFound`, which makes the server open the child from the journal instead. A standalone SDK `forkSession` is rejected: it writes the file immediately but renumbers uuids, and the Tagma turn is lost in the fork; an empty `shouldQuery: false` message to record the file is rejected: it stays in history as `(no content)`, and with `isSynthetic` the model reads it as foreign input.
- **Request measurement.** At the end of every model request (`message_stop`) the runner sends `usage_update` with the current model window and `_meta['tagma/measured']`: `Meter` assembles it (`meter.ts`, held by `Feed`) from the stream's `message_start` and `message_delta`, and `Settings` holds the window ([[c7d3d8a2|read on every request]]). No `usage_update` is sent on `result`.
- **Spend.** `Meter` reports `Spend` on every request, and the driver lands its spend immediately. So the prompt answer's `usage` is only the remainder: the cumulative `modelUsage` difference (translated into the Tagma convention: `inputTokens` — the whole input, cache — its parts) minus the turn requests' sum, per field. The remainder is subagents, in-turn compaction, and requests whose `message_start` was never read. A negative field means the measurements contradict each other: there is no remainder, and a line goes to stderr; `reasoning` is excluded from the check because Claude Code's `thinkingTokens` is sometimes incomplete. The turn cost is the `total_cost_usd` difference against the `basis` from the models' `costBasis` in `_meta['tagma/cost']`; the driver records it in `thread_run.cost`. Unreadable cumulative values, or the first turn after resume and fork (whose initial value includes history), yield neither remainder nor cost: the turn spend is the requests' sum.
- **Phase.** `Phases` (`phases.ts`, held by `Feed`) translates main-agent events into `$/tagma/phase { phase }`: prompt echo and tool result, `message_start`, a `thinking`/`text` block end, and `message_stop` with no `tool_use` — `calling`; a `thinking` block start — `reasoning`, `text` — `writing`, `tool_use` — `tools`; `system/api_retry` — `retrying`; `status: compacting` — `compacting`, `compact_boundary` — `calling`. A repeated same phase is never sent. The ACP client serves a `$/` method as a live `Signaled`, not a durable step, so the phase never closes the open message. The same road carries `Inputs` (`inputs.ts`) for the input the model writes: `$/tagma/input` on a `tool_use` block start and on every `input_json_delta`. `system/api_retry` leaves as a durable `_tagma/retrying` notification with the failure family (`retryFamilyOf` in `failure.ts`, the same table as the turn-end failure class), while `Meter` puts the attempt number into the next request's `tagma/measured`.
- **Mid-turn words.** `_tagma/steer` sends a message with priority `next`; its uuid is the inbox record id from `input`, when that is a uuid. Claude Code tucks it into the running turn at a step boundary (after a tool result); an echo with the send uuid acknowledges receipt — `injected`; when no more steps come, the word goes as the next turn of the same prompt — `startedNewTurn`, and the prompt answers after it. An echo is recognized even with no own uuid: Claude Code 2.1.303 executes words an interrupt failed to recall as one merged message under a new uuid (its transcript holds `mergedSendUuids`, the echo lacks them). So an echo with an unfamiliar uuid acknowledges every waiting word whose text blocks all stand in it (trimmed: on merge Claude Code appends a newline). Otherwise the turn would await the echo forever, and the prompt would never answer. The prompt awaits only words the runner itself sent and whose echo is still missing: the result's `queued_turn_count` also counts a word recalled after the result was assembled — the turn would never end with it. `_tagma/withdraw` by `input` removes an untaken word via `cancelAsyncMessage`: its steer answers with a -32800 refusal, while the recall itself is `withdrawn: true`; when Claude Code already took the word — `withdrawn: false`, and the steer awaits the echo; a failure of the recall itself (no method, the SDK call crashed) is a `_tagma/withdraw` refusal with the channel error, not `false`. A turn that awaited only the recalled word ends with its last result's outcome. A word arriving before the first send (the turn still opening or reopening the query) waits in the turn queue and leaves right after the prompt. It receives neither refusal nor `promptRequired`, or the driver would deem it unacknowledged. A `call_hosted_tool` answer names in `words` the turn's words whose `_tagma/steer` the host already recorded to the runner and whose echo is still missing, and `Relay` hands the result to Claude Code only after each of them has gone into the query (`Turn.queued`): otherwise a result arriving over HTTP ahead of steer over stdio would yield a model request without those words. Gone means the SDK recorded the message and asked for the next: `Channel.send` ends only then (`sdk.ts` holds its own prompt stream), while the SDK writes the MCP-call answer into the same stdin later. A word the runner itself refused (input never translating into a message) holds no wait either. This wait is also ended by the turn's end, cancel, or death.
- **Cancel.** While the turn has not yielded the prompt, cancel only ends it: `cancelled`, and the turn queue's words get a -32800 refusal. After sending, cancel is the turn's state. Every cancel calls `interrupt({ cancelQueued: true })`: Claude Code removes our words from the queue and from the next turn's batch, lists them in `cancelled`, and they never execute ([[980edf66|probe on 2.1.306]]). A CLI that does not know the argument answers `still_queued`, and those words are removed via `cancelAsyncMessage`. A removed word answers with a -32800 refusal, and the driver returns it to the queue. A removed prompt Claude Code never started no longer awaits its `result`.
- **A new turn after cancel is interrupted at start.** A word the CLI has not read from stdin yet survives any interrupt, as does a word the old CLI never removed. Claude Code is sure to start a turn with it. So while the turn is cancelled, the runner calls `interrupt()` on every `command_lifecycle` `started`: that frame arrives before the model request. It also calls it on every echo: on a CLI without those frames the echo-bound request already left. The `command_lifecycle` frames are undeclared in the SDK types; `sdk.ts` parses them. A surviving word defers the prompt answer until its echo (steer answers `startedNewTurn` or `injected`, and the driver records the word as read) or until a `cancelled` frame with no `started`. An earlier answer would mean the Claude Code turn starts after the answer: its `result` would finish the next prompt, and the word would stand twice in the transcript. A cancelled turn's `queued_turn_count` never counts such a word: on 2.1.306 it is 0 though the word stands in the queue. A cancelled turn's prompt always answers `cancelled`, and a late `result` never rewrites it. It answers the same when the session died and echoless words get -32800. An `interrupt()` failure is a fact: `Lifecycle` closes the query and announces the session death. A non-cancelled turn ending with no echo refuses the steer as unacknowledged.
- **Compaction.** Autocompaction is allowed only by a standing Tagma request: its flag survives a query reopen for the prompt or tool names. With no such request `autoCompactEnabled` is off; `idleCompaction` and `precomputeCompactionEnabled` are always off. The query opens with the documented `CLAUDE_CODE_AUTO_COMPACT_WINDOW=1000000` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=1` in the environment: so enabled autocompaction fires before the very first model request, while the 1000000 window never understates the model window `Settings` reads ([[332f3ece|probe]]). `_tagma/compact` with `at: 'end'` sends `/compact` into the same session; the answer carries the compaction turn's spend just as a prompt answer, and `_meta['tagma/turn'].last` — the summary or a later main-thread record Claude Code yielded — once the transcript was rewritten, so a fork after it resumes on the compacted transcript rather than before the boundary, and `session/cancel` interrupts it with a -32800 refusal holding the same spend in `data`. A cancel arriving before Claude Code read `/compact` never removes the command: it starts and compacts the session to the end ([[b54e302c|probe on 2.1.306]]), while Tagma would deem it cancelled. So a cancelled compaction is interrupted again on its command's `command_lifecycle` `started`, or on `status: compacting` for a CLI without those frames; a repeated `session/cancel` of an already issued command interrupts it once more. `_tagma/compact` with `at: 'step'` during a prompt enables autocompaction via `applyFlagSettings`: Claude Code compacts before the next model request, the `PostCompact` hook switches it off ahead of that request, and the turn goes on; the answer is sizes and retelling with no spend. A step-compaction start leaves as `_tagma/compacting` (`running: true`); a Claude Code `too_few_groups` refusal is `running: false`, the flag stays, and it tries at the next step. A turn ending with no next request answers `_tagma/compact` with a -32010 refusal ahead of the prompt answer; the same refusal when there is no turn or the flag never flipped. Both roads' instructions go via the `PreCompact` hook (`systemMessage`), while `/compact` leaves with no arguments. The `compact_boundary` boundary and the retelling leave as `_tagma/compacted`. A turn hitting the window limit (`terminal_reason` `blocking_limit` or `prompt_too_long`) is continued by the runner once: it enables autocompaction and sends a "continue" message — Claude Code starts a model request only from a new message, and compaction runs ahead of it; a second overflow ends the turn.
- **Side question.** `_tagma/aside` is answered by the live query's `askSideQuestion`: text and spend as the session cumulative-usage difference; transcript and turn untouched ([[f3949b43|recap copy]]).
- **Prompt snapshot.** The runner opens every query with `systemPrompt: { type: 'custom', prompt, snapshot: true }` and `CLAUDE_CODE_HOST_PROMPT_SUPERSEDES_RECORD=1` in its environment. With the snapshot Claude Code records the system prompt and the tool declarations by value at the session's first request; a later request, a resume and a `forkSession` copy send that record: the declared tool set is latched from it and each declared tool is rendered with its recorded description and schema, while tools the catalog lists later are announced inside the conversation (`deferred_tools_delta`). Without a record every new process latched whatever `tools/list` served at its first request, so a reopen after a server restart or a prompt change, and a fork whose catalog held tools the source revealed later or a changed description (`spawn_agent`'s model rows), changed the `tools` prefix: the whole cache missed and Claude Code dropped the history's thinking blocks as `prefix_mismatch` (2026-11-02, claude 2.1.316: a fork of a 742k-token thread read 0, wrote 650,230 tokens and lost 249 of 250 thinking blocks). The supersede variable keeps Tagma's run-frozen prompt authoritative: a host prompt the record does not already hold is rendered and recorded anew, one it holds leaves the record untouched. Both behaviours are read from the 2.1.316 client code, not measured on a live run. Where prompt recording is off on the account the SDK accepts the option with no effect; a session opened by the older runner with `snapshot: false` has no record until its next open records one. The runner reads the `claude` version (`claude --version`, at most 5 s) only when assembling the session file from the journal: it enters that file; when the version cannot be read, history leaves as a text retelling rather than a launch refusal.
- **What the runner never lets into the session.** Not just `settingSources: []` and the built-in tool list, where only the vendor web remains — and only when the turn answer provides it: Claude Code auto-memory (`MEMORY.md` from `~/.claude/projects/<cwd>/memory`) enters context on its own, `settingSources` never closes it, so every query opens with `settings: { autoMemoryEnabled: false }`. Measurement 2026-10-07 (claude 2.1.292, SDK 0.3.292, haiku, one run via `claudeAgent` with the real adapter and a memory directory in a temp cwd via `autoMemoryDirectory`): with `autoMemoryEnabled: true` the model spoke the marker word from `MEMORY.md`, and it stands in the session transcript; as the runner opens the query the answer is `NONE`, with no marker in the transcript.
- **Calls outside the SDK types.** The runner calls `askSideQuestion`, `cancelAsyncMessage`, `interrupt({ cancelQueued })`, and the experimental `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET` only in `sdk.ts`: the single file touching `Query`, and the adapter of the runner's own `Channel` contract (`channel.ts`: send a message, message stream, interrupt, setModel, setEffort, setThinking, withdraw, sideQuestions, reading, quota, close; `ClaudeSdk` opens a `Channel` and reads the transcript). There the `command_lifecycle` frame missing from the types becomes `Commanded`, and an unreadable one is dropped. A missing method is a `methodNotFound` refusal, not success; a spend answer in an unreadable form is an `internal` refusal, a missing spend method is `null`. Session owners take `Channel`, not the SDK type, so an SDK change shows as a type error in one adapter. The quota window-reset time passes from the SDK into `QuotaObservation` in epoch seconds; the separate `rejectedUntil` deadline in epoch milliseconds, since the retry delay is computed from it. The adapter is verified by `sdk.test.ts` on a fake `Query`, session behavior without live Claude by `contract.test.ts` on fake `ClaudeSdk` and `Channel`.
- **Session owners.** The shared [[14227879|hosted kit]] holds the process ACP session, turn opening, early steers, pre-send cancel, the server door, relay, and client output; Claude plugs in with the `Cycle` port. `ClaudeSession` assembles the vendor owners and deals them query messages: `lifecycle.ts` (query, reopen, generations, and death), `turn.ts` (sending, steer echo, interrupt with recall, and turn outcome), `compaction.ts`, `aside.ts`, `settings.ts` (model and option picks persist across the process sessions), `feed.ts` (SDK event translation), `fetching.ts`, `vendor.ts`, and `spend.ts`. `ClaudeSession` also accounts for a turn the kit is still opening, so a step-compaction request is allowed while awaiting context or a query reopen. The kit's `Bridge` (`@runlith/hosted-runner/bridge`) serves the MCP catalog and hands execution to the shared `Relay`; Claude gives it the `claudeVendor` descriptor (name, `callIdOf` reading `claudecode/toolUseId`, `relists: true` — the `list_changed` notification and the 5 s repeated-`tools/list` wait) and wraps `bridge.server` as the SDK's `type: 'sdk'` config (`claudeConfig`, runner `bridge.ts`); `Translation` reads the same `Handed` as the relay. `HostedDoor` is the port of the hosted kit (`@runlith/hosted-runner`), filled by the server's `ServerDoor` (`external-harnesses/cli/serverDoor.ts`), which `tagma harness-run` hands the runner it resolves from the builtin package (`claudeRunner` of `@runlith/adapter-anthropic/runner`); the shared `Process` port sets stderr and death, while the CLI path and version stay with Claude. Channel close precedes the read-loop stop: while input is open the SDK never yields completion to the iterator, and the loop stop waits until timeout.
