Reading of 2026-10-22 supplements [[1249b48f|the October 4 reading of the official Cursor surfaces]] with new facts and previously undetermined bounds only. Checked: current official docs/llms.txt, the npm registry and tarballs, cursor/sdk-bridge releases, and staff answers on forum.cursor.com. The SDK was not launched here, private endpoints were not called, and there are no legal conclusions.

## 1. npm 1.0.35 → 1.0.40: published versions and measured diff

[npm registry](https://registry.npmjs.org/@cursor%2fsdk) at reading time: latest `1.0.40`; after `1.0.35` came `1.0.36` (2026-10-05 16:38:15 UTC), `1.0.37` (2026-10-07 20:13:46), `1.0.38` (2026-10-16 22:07:11), `1.0.39` (2026-10-20 18:01:07), `1.0.40` (2026-10-20 18:24:56). The [SDK changelog](https://cursor.com/docs/release-notes/sdk) still ends at `1.0.35`; [GitHub Releases](https://github.com/cursor/sdk-bridge) for `.36–.40` confirm matching binaries and versions but do not list behavior changes. So below is the cumulative `.35→.40` diff, not an attribution of changes to a specific intermediate version.

`npm pack` downloaded both SDK versions and `@cursor/sdk-darwin-arm64`, then `diff` compared `package.json` and all `dist/esm/**/*.d.ts`. Kept tarballs and unpacks: `~/.tagma-dev/scratch/01a163f8-4052-774f-9c63-5e76a16694da/` (`cursor-sdk-1.0.35.tgz`, `cursor-sdk-1.0.40.tgz`, `sdk-35/`, `sdk-40/`, `platform-35/`, `platform-40/`). This is a reading of officially published artifacts, not of closed-server sources.

- `agent/options.d.ts` adds `ModelSelection.maxMode?: boolean`, `ModelVariant.isMaxMode?: boolean`, and `AgentOptions.teamId?: number`. `teamId` is also added to account/catalog reads and cloud list/get/operation calls in `agent.d.ts`. A positive safe integer goes in the `x-cursor-team-id` header; the field is neither kept nor read from CLI config. Without it the account's ambient team stays. In the `.40` bundle a local request really builds the protobuf model with `maxMode: true`; catalog resolution derives it from matching variants and keeps the resolved choice on later sends with the same params/alias.
- Signatures of `tools`, `disallowedTools`, `systemPrompt`, `local.customTools`, per-send custom tools, `settingSources`, `local.store`, `Run.steer/cancel`, token usage/getUsage, and `Cursor.auth.login` are unchanged. `run.d.ts`, `custom-tools.d.ts`, `usage-types.d.ts`, `tools-option.d.ts`, `auth/login.d.ts`, `auth/mint-api-key.d.ts`, `sdk-config.d.ts`, `sdk-statsig.d.ts`, `store/local-agent-store.d.ts` are byte-identical. JSONL/SQLite store declarations differ only in type-import shape. Wider generated conversation/tool/delta schema changes are beyond this list; full wire-contract invariance is not claimed.
- `zod` moved from a plain dependency `^3.25.0` to peer dependency `^3.25.0 || ^4.0.0`; published generated schemas switched their import from `zod` to `zod/v3`. This is an install/compatibility change, not a proven break of user code. Node engine `>=22.13`, exports (including the `bun` condition and `/bundled`, `/bundled/sqlite`), protobuf/connect/statsig dependencies, and the optional platform-package matrix are unchanged.
- `.40` adds `local-store-open-failure.d.ts`; on recognized SQLITE_CANTOPEN / unable-to-open-database the bundle switches blob storage to memory and warns that a checkpoint may not survive process exit. `.35` had no such mechanism. This is no guarantee of survival after a disk failure.
- In `@cursor/sdk-darwin-arm64` the file set and package constraints are the same; `bin/cursorsandbox`, `bin/rg`, both `vendor/tree-sitter*/binding.node` differ in binary. The changelog does not name the reasons for these binary changes or matching fixes.
- Bun is no `.36–.40` novelty: the changelog dates working send to `.21`, a streaming fix to `.23`, the flat bundle to `.28` ("Ship the SDK as a single file"). Both compared versions carry a `bun:sqlite` driver in the flat bundle; the earlier study's wording about SQLite being unavailable specifically under Bun is not confirmed by current code. I did not run a default-SQLite runtime probe.

## 2. systemPrompt access, runtime, telemetry, local limits

**New decisive answer on systemPrompt.** [Mohit Jain, October 19](https://forum.cursor.com/t/how-do-i-get-access-to-systemprompt-in-cursor-sdk-unknown-option-system-prompt/175262/7): "isn't open to external accounts yet" and "not something we can switch on per account, plan, or waitlist today". That is more specific than the remaining account-gate wording in the [SDK docs](https://cursor.com/docs/sdk/typescript#custom-system-prompt). That answer gives no public way to request enablement and no list of qualifying plans; buying a plan cannot be counted as a way to unlock systemPrompt. The staff member offers AGENTS.md/rules/per-send instructions only as an additive layer, not a replacement for the built-in identity.

Runtime requirements and packaging: Node ≥22.13; npm publishes `darwin-arm64`, `darwin-x64`, `linux-arm64`, `linux-x64`, `win32-x64`. That is a package matrix, not support of every OS checked here; the Windows arm64 package is absent from optionalDependencies. Bun automatically picks the flat bundle; with a compiled executable the native platform binaries sit next to it in `node_modules/@cursor/sdk-<os>-<arch>/`. The [documented JSONL store](https://cursor.com/docs/sdk/typescript#jsonl-store) keeps `agents.ndjson`, `runs.ndjson`, `run_events.ndjson`, `checkpoints.ndjson` in the given directory. For unavailable SQLite the docs offer JSONL/a custom store. The docs name no minimum Bun version.

**Statsig and analytics are different mechanisms.** `@statsig/js-client@3.31.0` stayed a dependency; in `dist/bundled/index.js` of both npm versions the SDK creates the Statsig client itself with `disableLogging: true`, `disableStorage: true`, `networkConfig.preventAllNetworkTraffic: true`. It fetches the config earlier from Cursor via BootstrapStatsig. So a statsig dependency alone does not prove direct Statsig telemetry sends. Separately the SDK holds `sdk.run.created/completed`, `sdk.operation.failed`, send-latency/startup, and PR analytics, and `analytics.d.ts` has `flushSdkAnalytics`. No switch for all this analytics was found in public `CursorConfigureOptions` or current SDK docs; full absence of network telemetry is undetermined. SDK and analytics network were not launched for this reading.

**A numeric local limit found on the forum.** [Mohit Jain, October 7](https://forum.cursor.com/t/cursor-sdk-runs-fail-mid-turn-with-resource-exhausted-which-per-key-limit-is-it/173940/9): get_models has "30 requests a minute" plus an unnamed hourly cap; counted per user/service account, not per API key. Per his answer Agent.create loads the catalog once per process+cwd; a Teams/Enterprise admin may ask for a raise. The mid-run resource_exhausted in that report turned out to be temporary Opus capacity, not a key limit. No public number for concurrently running local agents or TPM was found. An older [answer of August 24](https://forum.cursor.com/t/how-to-scale-cursor-api-usage/169111/6) speaks of buckets per key and higher Teams concurrency; it is about the Cloud API and must not replace the later specific get_models explanation.

## 3. Billing: legacy versus The X Subscription must now be told apart

The new [pricing page](https://cursor.com/docs/models-and-pricing) sells The X Subscription: Free ($0, limited use), Plus ($8/mo), Premium ($30), Super ($100), Ultra ($200); Teams — matching paid seat tiers $30/$100/$200. Paid plans share one weekly Cursor-models pool, shared with Grok; Premium/Super/Ultra give 4×/15×/50× of Plus respectively. Third-party models are outside the pool and on Premium+ are paid from the first request out of prepaid credit at the API list price. Free/Plus do not include them. Teams additionally charges the Cursor Token Rate $0.25/M on eligible input/output/cache tokens; some models are excepted. Each paid seat has its own pool, never moved between members; the team prepaid balance is shared.

[Legacy plans](https://cursor.com/docs/account/pricing/legacy-cursor-plans) remain with no forced move: Hobby Free, Pro $20/mo, Pro+ $60, Ultra $200; Teams Standard $40/seat, Premium $120/seat (5× Standard). Here the two monthly Cursor Models/Other Models pools and on-demand billing still hold. Hobby is limited Agent/Chat/Tab, with no Other Models/Cloud Agents and no on-demand; Pro and above explicitly include the SDK. The current page publishes no numeric legacy-pool dollar sizes. Start explicitly excludes the SDK.

The SDK docs tie the SDK to the user-key owner's tariff ("User API keys bill to that user's plan"), not to separate SDK billing; a service-account key bills the team. `Cursor.auth.login()` is documented as minting exactly a user API key; no separate tariff category or special commercial terms for this issuance path were found. The API overview lists the TypeScript SDK for All users at the same time as the legacy Start page excludes the SDK, and Free/Hobby eligibility of the full local SDK is not spelled out. So the existence of auth.login cannot be used to infer availability of every SDK function/model on Free.

## 4. Agent spend exists; no whole-user quota by user key is established

The earlier cloud-only note on getUsage is outdated: the [docs](https://cursor.com/docs/sdk/typescript#agentgetusage) describe local per-turn and cloud per-run billed usage, but local is behind an account rollout. [Colin, October 7](https://forum.cursor.com/t/local-sdk-agent-get-usage-returns-feature-unavailable-while-run-usage-succeeds/173987/6): "isn't generally available yet". Current docs pin the refusal to `403 feature_unavailable` → `UnknownAgentError`; the forum Python case first showed a misleading 500. Those are different surfaces/versions of the error, not proven TypeScript `.40` behavior.

Public SDK fields: `AgentUsage.usage`, optional `cost.{rawCostCents,chargedCents}`, `runs[].{runId,usage,cost}`. `chargedCents` can be 0 on included/BYOK/credit-grant usage and appear after settlement: it is not a remaining quota. [GET /v1/agents/{id}/usage](https://cursor.com/docs/cloud-agent/api/endpoints#get-agent-usage) gives totals/runs for an agent; [GET /v1/me](https://cursor.com/docs/cloud-agent/api/endpoints#api-key-info) and `Cursor.me()` give the key's name/date and the owner's identity, not balance, percentage, limit, or reset. No official user-key endpoint/SDK method for the whole account's remaining pool was found in the catalog as read.

The [API overview](https://cursor.com/docs/api) lists Admin and Analytics availability as "Enterprise teams"; Analytics [repeats this explicitly](https://cursor.com/docs/account/teams/analytics-api), most endpoints need admin:* (Bugbot analytics read:*). At the same time [Team Pricing](https://cursor.com/docs/account/teams/pricing) promises usage/spend via the Admin API and Teams — the texts diverge, so Admin API should not be firmly declared Enterprise-only. Both cases are team/admin access, not a personal user's quota API.

For `cursor.com/api/dashboard/*` no published contract of a third-party quota client was found. [Staff member Mohit in troubleshooting](https://forum.cursor.com/t/support-failed-to-load-github-settings/160868/17) even suggests a concrete `fetch('/api/dashboard/disconnect-github', {method:'POST'})` in a logged-in dashboard. Private endpoints were not called in this reading.

## Not established

No detailed `.36–.40` changelog is published, so the concrete release reasons for binary/bundle changes are unknown. Comparing public types and a few runtime fragments does not prove no runtime regressions. The systemPrompt opening date/plan, the numeric hourly get_models cap, TPM/concurrency of local SDK, an official switch for all SDK analytics, a shared user quota API, and full Free eligibility are undetermined. No SDK run, live test of new packages, telemetry capture, or legal review was performed here.
