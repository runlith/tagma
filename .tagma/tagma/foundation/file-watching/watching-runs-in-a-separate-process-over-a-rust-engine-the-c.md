The native watcher is a Rust engine (`packages/watch/native`, a cdylib through `bun:ffi`) living in a separate process: a native-code crash or a long call into fseventsd doesn't touch the server. On macOS every subscription runs its own FSEvents thread on its own serial queue, on Windows its own read thread, so opening and closing one root doesn't touch the rest; on Linux every subscription in the process shares one inotify instance and one read thread, and its queue overflow touches every root.

- **The channel is a Unix socket `watch-<build>.sock` in the directory the client named** (at the server — the data directory); `<build>` is the watcher-code and engine-library hash, so a process of another release stands on another channel and the protocol isn't negotiated across releases. A new build's client tells the directory's other channels `retire`: such a process leaves when its last client disconnects, and a socket with no live process the client deletes under its flock. The client first connects to the socket and raises a process only if nobody answers; a process finding a live neighbor on the same socket leaves itself. The process does the neighbor check and address grab under the `<socket>.lock` flock, and leaving deletes the socket only if its inode matches: two clients raising the channel at once get one process, and the leaving one doesn't take the new address down. Process handoff between servers rests on this: it's found by channel, not by parenthood. A path longer than `sun_path` holds is replaced by a deterministic name in the temp directory — the directory hash, then the build — so the same directory gives the same channel again, and `retire` finds other builds' channels of the same directory.
- **Events go from OS threads to the process with no callback into JS.** OS threads pile events into the engine's waiting batch and write a byte to its pipe; the process reads the pipe in its loop and collects the batch with `take`. Collection takes one subscription's events, resets and ends under one lock: an event arriving mid-collection stays in the next batch and isn't lost between them. Opening, closing, the snapshot and "what changed" run on the engine threads and answer over the same channel, so a long call doesn't stop the process loop.
- **Batch gluing.** One record per path in a batch. A plain "changed" or "deleted" is given as is; everything else — created, renamed here, a mix of different events — is decided by the path state at give time: no path → `delete`, path exists → `create` (if a creation or rename was among the events) or `update`. So "replaced a file and deleted it at once" gives `delete`, instead of vanishing like a glue that drops "created and deleted". FSEvents flags are sticky and don't say what stood before the batch, so only the path state judges them. On a case-insensitive volume old writing after a case-only rename is still found by `lstat`, so on macOS the engine checks the name the volume holds (`getattrlist`), not opening the path: opening hangs on FIFOs and triggers TCC access prompts. A directory renamed here the engine walks and names each of its descendants `create`; the directory's old path arrives `delete` (on Linux — with its subdirectory paths from the watch map), and the files' old paths don't arrive: FSEvents and Windows don't name them, and the engine holds no file tree; readers treat the deleted directory as a subtree.
- **A subscription on the "root, recursive, exclusions" pair is shared in the process.** A repeat subscription with the same key from any client joins the standing one. The last client's `unsubscribe` closes the OS thread and answers only after that: holding a deleted tree waits exactly for that. The subscription thread is closed only by `unsubscribe`, never by the thread itself: an FSEvents thread has one owner. A broken connection doesn't close the thread — the subscription stays with no clients and accumulates changes for the next one. A server leaving for its successor therefore doesn't unsubscribe, only forgets the subscription at home (`leave`): otherwise closing its places on stop would have taken the roots' records down before the socket disconnects.
- **Process life.** `with-client` (tests) holds its stdin pipe from the client and leaves with it. `with-parent` (a server under ServerLaunch: install and `tagma:try`) inherits the server's stdin, i.e. the launch owner's pipe, like execution host: it outlives a server change and leaves on EOF when the owner is gone. The server's own pipe won't do, because Bun closes it when the server exits. `detached` (a server with no launch owner) outlives a server restart: a subscription with no clients closes 10 minutes after someone connected to the process, and a process with not one client leaves in an hour. A server stopping with no successor (Stop, install removal) sends it `shutdown`; one leaving for a successor doesn't. Its own process group: the terminal signal to the server doesn't kill it before the server closes its subscriptions.
- **Root change record.** A recursive subscription remembers the last changed paths with the batch number, up to a machine-memory-derived limit (`retainedPaths`, 1024 to 65536 paths); an evicted path raises the lower bound, and a subscription reset — to the current number. A `<subscription epoch>:<number>` cursor answers the paths after it, or `null` if the subscription is another one or the bound passed the cursor. A `mark` position carries a cursor and, if the caller named a file, the engine snapshot; `changedSince` tries the cursor, then the snapshot, else `null` — the reader re-reads everything. The snapshot also covers a process change and a process-less gap. On macOS the snapshot is the fseventsd event number and the volume journal UUID (`FSEventsCopyUUIDForDevice`), and the answer is read from fseventsd history up to `HistoryDone`; another UUID, a volume with no journal, and a reset in history answer `null`. On Linux and Windows the snapshot is `stat` of every tree path: time, size and inode on Linux, so replacing a file with the same time still shows; on Windows the creation time instead of inode, which NTFS tunneling carries onto the file replacing the earlier one under the same name, so such a replacement of the same size and time doesn't show there. fseventsd history lags a just-made edit and then silently doesn't name it; so the process writes `.watch-cookie-*` into the root and repeats the request until the cookie is in the answer; cookie names are cut out of every answer. A root the cookie can't be written to answers `null`. The same barrier stands as a separate `settle` request: the process writes the cookie into the root and answers when the subscription heard it — after that the `mark` cursor covers every write made before the request; snapshots around an agent command take it on every measurement. To keep the barrier at milliseconds, the FSEvents thread is created with a 10 ms delivery delay and `NoDefer`. `cursor` and `settle` name the subscription's exclusions: the cursor and barrier are taken at the subscription with exactly that key — another subscription of the same root has its own delivery. Every record path remembers the interval when the engine heard it (`heard`): the batch's first and last event, marked in the OS thread when piling into the batch, not when giving to JS, so the process queue doesn't shift the interval. A record happened no later than the interval end and no earlier than its start minus the OS delivery delay (`HEARD_LATE_MS`); that bound is a guess about FSEvents and inotify delivery, the OS doesn't guarantee it.
- **Loss of the process** ends every open subscription at the client (`ended`), and a request in flight — with a `WatchLost` refusal. The next call raises a new process; it rewrites the standing socket.
- **Reset** (`MustScanSubDirs`, UserDropped, KernelDropped at FSEvents — with the event's path; the inotify queue and Windows buffer overflow — on the whole root) reaches clients as `dropped` with a subtree (`null` — the whole root), the thread not reopened; the root record loses track up to the current number. **End** (`ended`): the root is gone — the engine checks it after every batch in which it heard anything, so on macOS renaming the root and its ancestor (`WatchRoot`) is also an end, while the FSEvents thread watching the path keeps hearing the directory newly created at the same place; inotify watches the inode, so on Linux deleting or renaming the root itself is an end even if a new directory already stands at its place — the thread died or the new directory got no watch for the inotify limit.
- **Exclusions.** FSEvents applies none of the exclusions if there are more than eight, so on macOS the OS gets the first eight, the engine filters the rest. The caller orders: the dearest directories first. On Linux an excluded directory stands under no watch.
- **inotify.** One instance per process, opened at the first subscription; an open refusal (the instance limit) refuses the subscription and isn't remembered. A watch on every directory except excluded ones; a new directory is walked right after the watch is set, and everything that appeared in it before is given as `create`. A directory renamed inside the root gets watches again on the new paths, one that left the root is taken off. Queue overflow loses directory creations too, so after it the engine walks each root's tree again: puts watches on directories with none and takes them off ones no longer in the root — otherwise a directory created in the lost gap would stay watch-less forever; the walk costs O(root directories) per overflow. `ENOSPC` on subscribe is a refusal naming the `max_user_watches` limit, the process doesn't fall.
- **The event batch** leaves in rows no longer than `CHANGES_PER_LINE` changes, so parsing one client-side row stays bounded. From a client that doesn't read, the process piles rows up to the machine-memory-derived limit, and past it closes that connection: the client hears a loss, not a growing queue.
- **Subscription life order.** Opening and closing one subscription run chained, so an `unsubscribe` arriving mid-open answers only after the open thread is closed. A subscription that ended before the open answer refuses that open.
