`install-from` points `current` at the new release only after writing the attempt `install/attempt.json` `{from, to, starts, copied, ended}`. The `to` release's server clears it by opening the local door. The predecessor cannot take the place back after leaving: the successor's migrations make the database unfit for the previous build, and 0.1.0 with its handover protocol is issued for good. So only the `to` code rolls back, before its own door.

- **An attempt stands while `current` equals `to`** and it has not ended, or ended with its data not returned (`unrestored`). Only such one does the sweep keep with both its sides, and only such one does its release drive through. Once `current` has moved, the record holds nothing. A start removes every copy that no standing entered attempt holds, so copies left by a death between ending the attempt and dropping them go at the next start.
- **The start counts first thing in `serve`**, before reading the release's parts. So a third start with no door rolls the attempt back, even when the `to` parts are broken. The rollback takes the data directory lock. When a live server holds the directory, the process exits unchanged, and the next start drives the attempt through. The cli and the server are different bundles, each with its own copy of `composition/attempt.ts`, and the server's copy holds the attempt. So a server-module failure outside the cli phases hands it over with a process event and waits for the rollback to end.
- **Copies instead of a snapshot.** On first entry, under the data directory lock and before the stores open, the machine, activity and performance databases are copied whole together with `-wal`/`-shm`: an APFS clone, and where there is none — a plain copy after a space check, with words to the human. A table snapshot before migrations is not covered by rollback: before the door `to` also writes tables migrations never touch (boot lays the dictionary directories), and their snapshot never restores them. A missing database is marked with an empty copy, and the rollback deletes it. Every re-entry starts from copies, not from what the interrupted start left.
- **Rollback order.** First everything open in the data directory closes: on its own build's failure the runtime closes itself, the rest is closed by the registered closing, on the `runMain` path — before the lock is released. Then the `-wal`/`-shm` standing beside the data are removed, the main file goes back, and then the copied `-wal`/`-shm`, each through a clone into a temp file and rename: an interrupted return leaves a whole database without its log, never a log of the copies beside a main file `to` migrated, which SQLite would replay into it. Then `current` moves to `from`, `ended` is written with the reason, outcome and the refusal owner's words, and only then are the copies deleted. Every step repeats: the next start drives an interrupted rollback through.
- **Unreturned data** (`unrestored`) leaves `current` on `to` and the copies in place. Every next `to` start first retries the return without opening the database. It worked — `current` moves to `from` and `ended.data` becomes `restored`. It failed — the process exits with the previous outcome. The window's "Retry" is a `current` start.
- **The fingerprint of unreturned files.** Once `to` has died before the door, 0.1.x raises its own build by itself, knowing nothing of the attempt. Such a build serves and writes on the unreturned database. So together with `unrestored`, `left` is written: the inode, size and mtime of the main file and the `-wal` of every database, as the failed return left them. Every failed retry rewrites `left`. A repeated return starts by matching the fingerprint. `kept` is set only when the fingerprint has diverged and every database's on-site migration ledger equals its copy's ledger, i.e. the `from` chain. Then `from` was serving the database, and returning the copies would wipe its writes. `to` leaves the database as is, moves `current` to `from` and deletes the copies. Knowing `from`'s migrations is unnecessary: the copy holds its ledger. The ledger is read from a clone of the files in a nearby temp directory, so the space fingerprint never shifts the read. When the database still carries `to`'s migrations, `from` never served it: it may have opened it, refused, created a `-wal` and shifted the mtime. Then the copies return just as with a matched fingerprint. A ledger that failed to read is treated the same.
- **Before the door only copy-covered writes happen.** Listening resume, the hourly pass over call records, indexing, retention and deletion of activity body trash bins, `traces` deletion all await the door at their owner (`Handoff.opened`, `ActivityPlace.opened`). Body deletion on resetting a folded activity chain is not tied to the door: there is no folding between issued builds, and an attempt only ever happens between them. `to` never writes the graph mirrors (`data/mirror/<project>/*.sqlite`) before the door, so they are not part of the copies. The mirror pass awaits `Maintenance.opened`, which opens after the door. A project's mirror is opened by a query, and queries go through the door. The run with 0.1.1 confirmed it: while `to` stood before the door, their inode, size and mtime never changed. The execution host is untouched in a live attempt before the door: `to` places no bundle of its own, talks to no host and writes nothing about terminals, and after the door it takes the host at the cost of another's host (`placeOverForeign` + `askForeignToYield`). The price is a two-to-three-second pause after the door: every host call from consumers (reads, subscriptions, input, commands) waits in it until the takeover ends in success or failure, and terminal start and cancel also wait for the end of the loading work after the takeover; executions live on and lose no output. The takeover itself talks to the host without that wait — otherwise it would wait on itself. A copy of the host database is rejected: executions write into it between handover and rollback, and returning a copy would lose or double their output ([[e0867f81]]).
- **The `from` side judges the host takeover, before the attempt is written.** Having published a version, `install-from` asks its channel's running server (`check_successor`) whether its execution host will accept this version's bundle. The server lays the bundle as a candidate next to the host, asks the host with its `prepare` verb, and removes the candidate — so even hosts issued before that code give a verdict. An accepted probe leaves a remembered PREPARE in the holder, but without `bundle.next` it never activates: `activate` first reads the holder part from `bundle.next`, and a failure of that read starts the standing bundle's logic; a new candidate always arrives with its own PREPARE, which clears the previous one. A refusal leaves the version beside, but not current: the answer is `held`, with no attempt, no `current` and no sweep, and the server keeps it as pending installation. `unasked` — no server, a server without that operation, without custody, with a candidate already standing, or one going away — installs as before. `--new-host` never asks: that way consent to a new host makes the pending version current. The `to` release still never touches the host before its own door.
- **Every move of `current` goes under `install/install.lock`** through the installation core (`closure/moves.ts`): an install of a release or of a checkout build, a step back, and each start's admission, entry, pass and rollback of the attempt. The current release and the attempt are read already under it, and the lock is waited for as long as a live process holds it. It is held only for work on this machine's files: asking the running server (`check_successor`) and preparing a step back (`prepare_downgrade`) happen between two holds, and the second hold checks that what stands is still what the first one decided from, so a start waiting for the lock never waits on a server that waits on that start. A version is built or copied into a hidden `.<time>.incoming` under a lease and renamed into the version only whole, named by the moment of that rename, so the release before the one that stands is the one it replaced. Picking the previous release never sees a half-written one, and the sweep deletes abandoned files with no lease. A standing attempt — entered, or `unrestored` — is never replaced: `install-from` refuses `attempt-open`, the window raises `current` on that code, which finishes the attempt or retries the return, and repeats the install. An attempt never yet entered is replaced by the new install with the same `from`, and the release it was moving to is no longer kept. While an attempt stands, a start of a release that is neither its `to` nor its `from` refuses to open the data: it would migrate data whose copies `to` takes later. That judgement is made again under the lock when the start takes the data directory, which also records the release now opening the data in `install/served.json`. A new attempt moves from that release rather than from `current` when they differ, because its copies hold that release's data. Once `current` has moved, the release is published, and a sweep failure never cancels the install.
- **A record that does not read is a state of its own, never "no record".** An `attempt.json` or `served.json` that does not decode, or that the process may not read (anything but its proven absence), may name an attempt whose copies are the only data from before it, so `install-from`, a step back and a checkout install refuse `attempt-open`, and pruning removes no release. The next start, under the lock, sets the record aside as `attempt.json.unread-<ms>` together with every data copy standing beside the data (each renamed with the same suffix), drops none, and serves with no attempt; then installs proceed. A start cannot rebuild the lost `from`, `to` and outcome, so it gives up the automatic return rather than guess one, and serving rather than refusing keeps Tagma usable while the data from before stays on disk. `served.json` heals at once: every start writes it.

The return record `install/returned.json` `{left, to}` is written by "Go back": it stays in force while `current` equals `to`. From it and from the attempt's `ended`, `install-from --json` answers `ask` before installing (`stepped-back`, `failed`, and also `irreversible`), and the window asks the human. A `returned.json` that does not read holds no data and no release and only decides that question, so the install asks nothing about the step back and logs why.
