`tagma:release publish` reads `release.json` and the files it names from the build site: every platform's archive and DMG. The release is named by the tag `v<version>`; a file matches by name, size, `uploaded` state, and GitHub's digest, when GitHub named one.

- **Before Apple and before any GitHub write — reads only:** `gh` is signed in and can `push` to the repository; the cut's commit is in the repository; the `v<version>` tag, when GitHub already holds it, points at that commit — otherwise GitHub would publish the release on someone else's commit, because a draft's target is ignored while a tag stands; the number sits above every published release, prereleases too, and every `v<n>` tag of the checkout. A refusal of any of these costs neither an Apple submission nor a trace on GitHub.
- **Notarization** of an unnotarized build goes in the notarized cut's own directory, which takes the standing one's place ([[6bc98bc4]]), so a retry never submits the build to Apple again.
- **The feed is a release file.** The draft is created targeting the cut's commit; a standing draft's target is corrected. The archives, DMG and `feed.json` are uploaded into it: the current Latest's feed with this release as the first entry. The feed gets the archive addresses upfront — as the file's address under the tag, because in a draft the files sit under `untagged-…`. Only then is the draft published as a stable release (`--draft=false --prerelease=false --latest`: a prerelease is never Latest), and `releases/latest/download/feed.json` serves the new feed at once. No client ever sees a release without its files, and a failure before publishing leaves Latest as it was.
- **The body is the release notes.** Read from the checkout's history in the reads-only phase, before Apple: the `feat`, `fix` and `perf` commits from the previous release's tag in the checkout — the highest number below this one among published releases, Latest feed and checkout tags — to the cut's commit; with no such tag in the checkout, the whole history up to the cut. Sections come in the order BREAKING CHANGES (a `!` or a `BREAKING CHANGE:` trailer, the commit listed there only), Features, Fixes, Performance; an entry is the scope and subject with its `Task:` trailers as sub-lines. A commit whose every change lies under `.tagma` is a graph commit and never listed, nor is any other type or a subject without a type. The draft is created with the notes, a standing draft receives them if its body differs, and a published release's body is never written.
- **The tag on GitHub** appears at publishing on the cut's commit — the same one the upload then tags in the checkout — so the repository and checkout tags never diverge.
- **A retry picks up what stands.** The draft is uploaded to completion, its feed recomputed from the current Latest. A published release with the same files and a feed offering it first receives only the checkout tag and the maps.
- **The published is never re-uploaded:** it may have been downloaded, and bytes under a number are never swapped. A published release with different files refuses. A pulled (prerelease) retry never brings back and names the return command. A number whose tag stands in the checkout while GitHub has no release refuses: it may stand on someone's machine. A fresh build takes the next number.
- **After publishing**, the upload verifies that the release is no draft and no prerelease, the files are in place, and GitHub serves each at the address written in the feed.
