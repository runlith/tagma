The channel address is fixed, and on it a stranger program or another macOS account's Tagma may answer. The window opens a server only if its `/health` `database` lies in the window's data directory; otherwise it shows that Tagma's place is taken and raises nothing. The window counts only the 503 of Tagma's launch-state shape (`{ok: false, startup, issue}`) as its own server starting; any other reply without the `/health` shape is someone else's address. Waiting ends only on a fact: the server answered; your own raised server exited while nobody holds the directory; the restart the window asked for is no longer running. A recorded launch failure is no verdict by itself: a process exit always follows it, and the exit of a failed release attempt is what raises the rolled-back release by itself afterwards; the window shows the cause from the record while standing on “failed to start”. While the process is alive and holds the data directory, or a restart runs with a live participant, the window waits as long as it takes: a restart on a slow machine takes minutes, and any deadline would falsely say “failed to start”. Requests to your own server go with no deadline: a slow reply is not silence, silence is a refused connection. The poll frequency only decides when to ask again. A launch-record change and your own child process's exit wake an immediate recheck; the `/health` reply still defines readiness. File watching is an acceleration: its unavailability is logged and leaves the ordinary poll, needed for old releases too.

A second `serve` on a held directory only exits on the lock, so the window raises a server only when the address is silent and nobody holds the directory. Hold is answered by the directory lock itself (flock on `server.lock`): there is no `bun:ffi` in Electron, so the window asks it with a short script in the release runtime, at most once a second while held. Whether a restart is running is answered by its record (`readHandover` in `installation/process/record.ts`: an accepted/prepared/transferred stage with a live predecessor or successor, started after the machine's last boot — otherwise a pid taken by a stranger process after reboot would hold the window forever): between doors the lock is briefly free, and without this the window would raise a second server racing the successor. Your own raised server that exited while another live process holds the directory lost the directory race — the window waits for the holder instead of saying “failed to start”. The window waits for a restart it asked for while the record says it is running; a server that answered with the previous build after that is opened by the window, which says the move failed, with the record's cause if it survived: a successor that crashed after `standing-by` replaces the record with its new start. The predecessor writes the successor's pid into the record as soon as it spawns it — otherwise a standing-by successor would be invisible, and the window would raise a second server racing it if the predecessor died before handover. A restart-request reply lost when the door closed is no refusal if the record already carries a new restart.

While the surface is open, the window asks `/health` every 2 s (`SurfaceLoader.watch`) and waits for the reply as long as it takes; address silence re-decides the same way a failed page load does. The page itself never tells the window the server died. Without this poll a server that died with no successor would leave the window on “not responding” forever: e.g. 0.1.x refuses on a database a dead attempt partly migrated. On exit the window stops asking before stopping its own server, otherwise it would raise it again.

The only live server the window does not wait for is your own server whose `/health` carries `stalled`: the machine database's writer was taken without asking into SQLite past the store deadline. Such a server never leaves on its own, because its orderly departure waits on the same writer. So at launch and in the 2 s poll the window writes to the log of the server whose work holds the writer, takes the pid named in the reply down with SIGKILL, and raises the server anew, as with a silent address. Committed data stays in the WAL, and agent runs are cut off. Without this a stuck server outlived every exit and window relaunch: Force Quit takes only the window, Cmd+Q leaves the busy server, while `/health` answered 200.

The window reads `/health` and `read_machine_state` of the servers of every release ever issued, so its parsing is narrow and reads fields old releases lack (`server.calls`) as optional.
