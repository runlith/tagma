Electron's default dialog handler shows a modal window itself, and a managed page would get stuck in it with no engine answer. `-run-dialog` is a private webContents event; the page removes its previous listeners and installs its own. This relies on an Electron internal: Electron upgrades are checked by dialog system tests.

While an agent drives the page (debugger attached), `alert`/`confirm` are held until `PageHost.answer` — so the engine sees the open dialog and refuses other actions until it is answered. Without an agent the same dialog shows natively and is dismissed if the answer arrived another way. If the agent session ended with a dialog open (channel break, server restart), the dialog is shown to the person at that moment: otherwise the renderer would hang on it invisibly. Electron does not support `prompt`: it is refused at once, the page sees `null`.

`beforeunload` goes through `will-prevent-unload`, and it is synchronous: Electron gives no way to defer the answer, so leaving is cancelled and reported with a dialog. On consent, engine-initiated leaving is repeated, but only after a round trip through the main frame's channel. Chromium cancels the held navigation or close as soon as Electron's handler refuses it, while the frame keeps waiting for the renderer's own completion of that beforeunload. A repeat started before that completion joins it, and the late "stay" drops the repeat silently: no dialog, no load failure, a navigation or close that never ends. A slowed renderer makes this the usual case. The round trip travels on the same frame interface as that completion, so its answer proves the renderer has finished. Page-initiated leaving (a link, `location`) cannot be repeated: main does not know its address, `will-navigate` arrives after `beforeunload`. Consent then lets the page's next attempt through without asking. The load failure Electron fires for a navigation that `beforeunload` cancelled carries no frame process or routing ids, so the page tracks a main-frame navigation without them. Page closing goes through `close({ waitForBeforeUnload })` with the same dialog: consent repeats the close, refusal keeps the page and answers the server `stayed`. The exception is a hung page: it closes without asking, it cannot answer. The core also closes without asking where there is nobody to answer (`PageHost.close` with `ask: false`): pages with no record at reconciliation and pages of a profile being deleted. Otherwise one such page would hold reconciliation, and with it the registration of the whole host. A second close of the same page while the first waits for an answer waits for the same answer. Closing with a dialog already open (alert, confirm, navigation beforeunload) is refused: the dialog first. The managed host behaves the same.

The host reports its own `beforeunload` with a `dialog` event. Chromium then sends `Page.javascriptDialogOpening` of type `beforeunload` over CDP and immediately `javascriptDialogClosed`, because Electron cancelled the leaving synchronously. The engine session never receives those two events: CDP events and host events are applied at the core by different threads, and a late `Closed` erased the open dialog — the agent never saw it, and the close hung.
