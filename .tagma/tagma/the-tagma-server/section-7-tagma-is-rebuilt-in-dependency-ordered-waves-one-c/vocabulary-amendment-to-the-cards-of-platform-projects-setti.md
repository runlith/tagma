**Accepted by the tagma agent (coordinator), 2026-09-28**, after two rounds of independent Opus and Astra review and the collision sweep's triage. Builders take it as the naming contract of these cards.

This amends the eight server-module cards in [[f7e0b9dd]] under the accepted vocabulary of [[2cecbcac]] and its measured rename ledger [[4dfd93e7]]. It fixes target names and contracts before any wave; it changes neither a source file nor a stored value by itself. In the lists below, the path preceding a rename is its **current** path under `apps/tagma/server/src/`; target contract paths and all ids are under the named module. Each service tag has an inline shape and consumers use `Tag['Service']`, except platform's one brand-generic `Store<Brand>` contract permitted by 5b C9; scoped `Context.Reference` values keep their nullable/default semantics. Layers are built by named implementations, never by a locator bundle. A tag and an internal class of the same subject are distinguished by the class's private mechanism name. `M1` supplies runnable transitional bindings as in the cards; `M2` installs final paths. Each module's `<module>.ts` manifest lands at its own M2 against platform's K0 manifest contract, never ahead of that wave. Failure classes are renamed with their owner's in-process consumers; an actual persisted or wire carrier changes only through a specifically listed migration. A pure TypeScript rename never silently changes a stored column, `_tag`, wire property, operation id, or exposed operation `name`.

## 7.5.1 platform

**Contracts and consumers.** `Units` (`tagma/platform/Units`) owns `write`, `read` from `db/Units.ts`; its `ConnectionUnits` implementation owns the store transaction gate and is consumed by every module opening read/write units. `Store<Brand>` is the **one named generic contract** allowed by 5b C9, not a service tag: it declares `db: StoreDb<Brand>`, `path`, `schema`, `transaction`, `vacuum`, `incrementalVacuum` once from `db/Store.ts`, with `transaction` admitting `WriteUnit<Brand>` and reads using `Unit<Brand>`. `MachineStore` (`tagma/platform/MachineStore`) is a tag over `Store<'machine'>`; `GraphStore` (`tagma/platform/GraphStore`) is a tag over `Store<'graph'>`. `StoreDb<Brand>` and the units carry an invariant brand, and each opened store also checks its instance witness, so neither a machine handle nor a unit from a different graph instance can act on this store. The old unbranded `Store` tag retires at D0; consumers demand the corresponding full `MachineStore['Service']` or `GraphStore['Service']`. `storeLayer(path, chain, options?)` takes required positional `path: string` and `chain: MigrationChain` (rule [[c2f04d22]]), with trailing `StoreOptions` holding only `freeBytes?`, `readers?`, `through?`; `seededStoreLayer(chain, options?)` mints its temporary path and then calls the same store opener. `MigrationChain<Brand>` is the platform wire value `{ folder: string; seeds: string; reports: Readonly<Record<string, MigrationReport<Brand>>> }`, where `MigrationReport<Brand>` is the existing `db/landedReports.ts#LandedReport` callback typed against `StoreDb<Brand>`; it is a value passed by composition, **not** a new service. Installation contributes the migrations folder and seed directory; executions contributes keyed reports through its manifest. The open/seed/chain and transaction implementation owns the single writer permit, connection and writer telemetry for its instance. `WriterRegister` (`tagma/platform/WriterRegister`) owns `resolve`, `signedId`, `idOf`, `byId`, `writerOf`, `named`, `all` from `graph/projects/Sessions.ts`; its session-table implementation owns the writer register and registration-in-unit, consumed by graph, settings and all writers. `inProject` moves to graph's journal/setting projection rather than the register. The call-lifetime `SignedSession` (`tagma/platform/SignedSession`), `SignedCall` (`tagma/platform/SignedCall`) and `CallConsent` (`tagma/platform/CallConsent`) retain their one held value each as required references at K1; K1 callers receive them through the call, and the register reads `SignedSession`. `SessionIdentity` (`tagma/platform/SessionIdentity`) is the platform-declared port tag whose **entire value** is the wire-safe `{prefix: Readonly<Record<string,string>>, extras: readonly string[]}`: `prefix` maps harness ids to display prefixes, `extras` names vendor identity-environment variables. External-harnesses fills this one tag at `start`; low server consumers read the value, and the app receives the same data on its bootstrap wire. `sessionName(ref, identity)` and `identityVariables(identity)` stay pure platform functions taking `SessionIdentity['Service']` as their argument; `nobodyEnvironment(identity)`/`unsignedEnvironment(env, identity)` carry it through their callers. The one tag's inline shape is its wire value, so no second exported `SessionIdentity` type collides with it. Platform's `contract/wire/setting.ts` declares `SettingKey<A, Section extends string = string, Check extends string = string>` with `section: Section`, `decides: readonly Check[]`, value codec/fallback/scopes/merge and control; `settingKey`/`settingListKey` preserve those parameters rather than widening them to strings. A key owner's manifest supplies its own section and graph-check vocabulary—today `protocol/settings.ts` narrows them to `SettingSection`/`FindingCheck`—while platform imports no graph catalog or operation list. Composition validates every contributed `SettingControl{kind:'managed',by}` against the assembled canonical operation ids at `composition start`, refusing an unregistered id before settings can serve writes; the currently spelled operation id remains the wire carrier. Platform declares the pure `RemovalHold`/`ManagedWrite` hook *shapes* for the respective owners but holds no project- or setting-specific list. Git's existing tag `Git` belongs to `@runlith/git` (unchanged package id); `ownGit`, `runGit`, `runGitBytes`, `actingGit` are platform's invocation kit functions, not an extra locator tag. `Capacity`, `Passes`, durable-file and declaration mechanisms gain only the members declared by E0/K0, with installation as their composer; do not invent a service-shaped bag for them.

**State.** The `Store` open implementation owns its connection, single-writer permit, migration ledger and transaction settlement; `ConnectionUnits` owns no second writer. `WriterRegister` owns `session` rows and any in-memory registration lookup, with `SignedSession` and `SignedCall` scoped to one call. Platform's Git kit owns the hook/commit/index lane gates (280/290/300); the one platform heavy-slot arbiter owns both pure-job and impure-execution admission at E5. Each mechanism is one implementation even if several tags read it. `SessionIdentity` holds only immutable startup data: external-harnesses owns the vendor table that produces `prefix`/`extras`, and composition binds that value once for low server consumers; neither platform nor the app imports the external-harnesses runtime.

**Card text replaced.** “`Store`, `MachineStore`, `StoreFailure`, `StoreError`” and “`Store` and `MachineStore` tags, their faces” → the single generic contract `Store<Brand>` defines the six branded members; only `MachineStore` and `GraphStore` are service tags over its distinct brand instantiations, and the open-only failure union is `StoreOpenFailure`. “`UnitsFaces`”, “`WriterRegisterFaces` ← `SessionsFaces`” and “A service's tag and its faces type” → inline member shapes, consumed as `Units['Service']` and `WriterRegister['Service']`. “`OwnGitError` ← `ShadowGitError`” → `OwnGitFailed`. “`databasePath()` and `seedDirectory()` become arguments of `storeLayer`” and “`LANDED_REPORTS` becomes an argument” → `storeLayer(path,chain,options?)` with a required `MigrationChain` value assembled from the owners' contributions; the path is required and no chain service is introduced. “`sessionName` takes the vendor's prefix as an argument” and “`identityVariables(extra)` takes the external harnesses' variables” → both pure functions take `SessionIdentity['Service']`, the platform-declared port supplied by external-harnesses and bound transitionally at `composition start`. `SignedSession`, `SignedCall` and `CallConsent` become required at K1 as the card already says; no earlier ambient-optionals removal is implied.

**Open:** none about spelling. The D0 type distinction must preserve the distinct `MachineStore`/`GraphStore` contracts, rather than accidentally making their runtime keys aliases.

## 7.5.2 projects

**Contracts and consumers.** `Projects` (`tagma/projects/Projects`) owns exactly `list`, `byId`, `resolve`, `global`, `register` (from `add`), `setRoot`, `remove`, `registryVersion` from `graph/projects/Projects.ts`; graph coordinates its birth and removal, while workspace, settings, thread-record and the doors consume registration/resolution. `ProjectIdentification` (`tagma/projects/ProjectIdentification`) is the port with `identify(path)` (from `graph/projects/repo.ts#identifyProject`), returning the distinct **data type** `ProjectIdentity {repoKey,rootPath}`. `projects/identity.ts` supplies its standalone git implementation without importing workspace. Composition/graph binds a request-aware adapter **through workspace M1**: it reads `CallerCheckout` via `checkoutAt`, memoizes one checkout discovery for project resolution and graph placement, and projects that result to `ProjectIdentity`; composition start names the binding and its workspace-M1 replacement. This supersedes a request-specific projects instance or GraphRouting's manual reprovision, and introduces no projects → workspace dependency. Projects M1 keeps `ProjectRef` at `protocol/caller.ts` until graph moves `ProjectCall`; it does not move the caller's lens on its own. `Projects.setRoot(unit: WriteUnit<'machine'>, row, identity) → ProjectRow` is a registry-row participant, admitting only `StoreFailure | GateRefusal<'global-permanent' | 'duplicate-root'>`. Graph's `ProjectRelocation.move(projectId, root)` validates the root and identifies it *before* opening that machine unit, then calls `Projects.setRoot` and records `project_set_root` in the unit; projects imports neither graph `Act` nor graph refusal codes. `RemovalHold` (`tagma/projects/RemovalHold`) has `register(owner, holder) → dispose` (owner exactly `graph|workspace|threads`, several registrations per owner), `owners()` to read owners actually registered, and `check(unit, row)` under the caller's machine unit. `composition/start.ts#admit` checks `owners()` **after `Layer.build(stack.layer)` and before admission**, requiring at least one holder from each of the three owners; it refuses `AssemblyInvalid` naming every missing owner. The earlier `start` point is too early because the holders do not yet exist. At K0 the validation reads platform's contribution contract instead, while `admit` remains the admission point; there is no runtime empty-hook refusal. `ProjectRemoval.remove` invokes it **before** any purge: `global-permanent` first, then every registered holder collected into one `project-not-empty` refusal; only after admission does graph purge its knowledge and call `Projects.remove`, which deletes the registry row alone. `ProjectChanges` (`tagma/projects/ProjectChanges`, declared in `projects/contract/service/changes.ts`) has exactly `removed` and `changed` event channels, each with a publish/subscribe surface. `removed` replaces `releasing(ProjectRelease)` after removal; `changed` announces the registry counter or policy movement. Both channels publish after the **outermost successful transaction** commits and before the act answers; a failed outer transaction publishes neither, and a savepoint settling inside one is not publication. These channels are never a second removal gate. At projects M1 the graph declares `ProjectBirth` (`tagma/graph/ProjectBirth`, `create`) and `ProjectRemoval` (`tagma/graph/ProjectRemoval`, `remove`) in `graph/contract/service/serving.ts`: these are the graph-owning public acts; `Projects.register` and `Projects.remove` settle only the registry rows as participants of the respective graph acts. The other former `Projects` members move **only** to their owners: `checkout`, `checkouts` to workspace; `ensureVocabulary`, `set`, `setStorage`, `measureNotice`, `scopeByPlace`, `zoneByPlace`, `placeOf`, `ownersOf`, `scope`, `lens`, `servesFrom` to graph; the root-block/catalog part of `add` to graph. The pure `sameOrInside` stays a projects identity helper, not a service member.

**State.** The machine composition builds **one** `projectsLayer`, providing `Projects`, `RemovalHold` and `ProjectChanges` as required inputs to every `graphLayer`; graph constructs only its own contracts and registers its holder. Graph mirrors do not create another registry version or holder set; fixtures separately compose the lower `projectsLayer`. `graphLayer` accepts no optional registry bag. That one registration implementation owns `project` rows, `registryVersion` and the removal-holder set; graph owns its `project_policy`, served-graph projection, root block and catalog birth. At projects M2, `registryVersion` advances at the **start of `ProjectChanges.changed.publish` after the outermost commit**, before subscribers run. A rolled-back write advances nothing; a reader may briefly see committed rows under the previous version, but the later advance makes the next registry sync catch up. This intentionally replaces [[a4b7b43b]]'s current inside-unit guarantee at the merge that lands M2, when that claim must be reconciled from code. `WriteUnit.afterCommit` carries queued publications out of the transaction; a failed savepoint drops only its queued events, and a failed outer transaction publishes none. No `ProjectRelease` list lives next to the `RemovalHold` set: its successor is the `ProjectChanges.removed` channel on the same registration implementation. Installation consumes the `ProjectChanges.changed` registry-version event and restore participant; graph policy writes also publish `ProjectChanges.changed` after their commit through the composition-start binding until graph M1 owns `projectPolicyChanged`. Workspace/graph/threads register pre-delete holders through the project's hook, never keep a second removal gate. MCP's `release(projectId)` and executions' `disownProject(projectId)` are **post-removal** `ProjectChanges.removed` subscribers (`http/runtime.ts:439–440` today registers both with `Projects.releasing`), not `RemovalHold` contributors; graph pool and enforcement warm-tree retirement likewise subscribe after deletion.

**Renames.** `graph/projects/Projects.ts`: `ProjectsFaces →` inline `Projects['Service']`; `Projects.add → Projects.register`; `ProjectClaim → RemovalHold` contributor, `Projects.hold → RemovalHold.register`; `ProjectRelease`/`Projects.releasing → ProjectChanges.removed` subscription/publisher; `Projects.registryChanged → ProjectChanges.changed`; `ForeignGraphs → OtherGraphs` in the graph remainder (not projects). `graph/projects/repo.ts`: `identifyProject → ProjectIdentification.identify` (data `ProjectIdentity` stays); new `ProjectRemoved` (not in 377 ledger) follows event-tense grammar. `ProjectRefusal` remains the resolution-code union. Projects' `RootRefusal → ProjectRootRefusal` (root-change admission codes), distinct from workspace's *current* `protocol/projectRoots.ts#ProjectRootRefusal → ProjectRootFailure` (a union of tagged failures); graph retains `VocabularyRefusal`. Project `ProjectRef` remains the composite project reference, not a `Request` or a shaped service. The eleven graph-serving public members have final receiving contracts: `ensureVocabulary → Catalogs.ensure`; `set → ProjectPolicy.set`; `setStorage → ServedGraphs.moveProjectStorage`; `measureNotice → ServedGraphs.measureNotice`; `scopeByPlace/zoneByPlace/placeOf/scope/lens → GraphScopes` with those five member names; `ownersOf → GraphScopes.ownersOf` at projects M1 (routed through the current graph), then `Sources.ownersOf` at graph M1 without changing its answer; `servesFrom → ProjectPolicy.servesFrom`. `relativePlace` is a private graph scope helper, not a twelfth public member. No graph member keeps a `Projects` prefix.

**Carriers.** `tagma/graph/Projects → tagma/projects/Projects` is an in-process service-key migration at projects M1; new `tagma/projects/ProjectIdentification`, `tagma/projects/RemovalHold`, `tagma/projects/ProjectChanges` and graph's `tagma/graph/{ProjectBirth,ProjectRelocation,ProjectRemoval,GraphScopes,ProjectPolicy}` keys are likewise in-process. The graph tag implementations remain in graph's current files until graph M1, while their contracts live at `graph/contract/service/serving.ts`. Projects' own `projects/projects.ts` manifest lands with its implementation at projects M2 against platform K0; M1 has no empty assembly file. Projects' wire `ProjectRow` has exactly six registration fields: `id,name,repoKey,rootPath,createdAt,global`. Graph's `ProjectPolicyRow` owns the *extended* policy/storage reading until graph M1 moves its columns; `ProjectRow` never promises them. A consumer reads one or many `ProjectRow` values from `Projects`, then calls `ProjectPolicy.read(ids)` **once** only when policy is needed, even for a single id (as `[id]`). The table's six registration columns keep their spellings and its `storage` column continues to accept exactly `stealth|team|plain` through projects M1; graph's `strict_provenance`, `private`, `storage` columns leave only with **D6's graph `project_policy` table migration at graph M1**, and remain read/written by graph at their existing place until then. `ProjectRef` remains in `protocol/caller.ts` until `ProjectCall` moves with graph, not projects M1. `add_project` stays the exposed operation `name` and id although the service member becomes `register`; new K2 operations `list_projects`, `read_project`, `set_project_root`, `remove_project` have their declared ids. Existing typed route URLs remain through their compatibility release. `ProjectChanges.removed`/`changed` are in-process post-commit event channels, not renamed persisted event codes; graph's policy writer uses `changed` via the transition binding until graph M1 changes its own policy publisher.

**Card text replaced.** “`Projects` (faces: `list`, `byId`, `resolve(ref | cwd)`, `global`, `register`, `setRoot`, `remove`, `registryVersion`)” → the same eight inline members, plus independent `ProjectIdentification` and `RemovalHold` contracts above. “`ProjectRelease` → the `projectRemoved` event” → `ProjectChanges.removed` after-commit event channel (and `changed` for registry/policy movement); project removal calls subscribers before answering. ## 7.5.3 settings

**Contracts and consumers.** `Settings` (`tagma/settings/Settings`) owns `read`, `value`, `chain`, `live`, `held`, `changes`, `write`, `amend` from `graph/core/Settings.ts`; graph, provider/power/threads and the doors consume those setting values, writes and subscriptions. `SettingDeclarations` (`tagma/settings/SettingDeclarations`) owns `read` (former `Settings.catalog`), serving `read_settings` and installation's registry; one settings implementation fills both tags from the same declaration index. `ManagedWrite` (`tagma/settings/ManagedWrite`) owns `register(key, writer)` and `write(unit, input)` for managed key dispatch; graph contributes the `graph.catalogs` writer. `write_setting` dispatches a key with a registered writer to that writer; an `installs` key with no writer refuses `setting-managed` instead of falling through to an ordinary row write. The composing registry validates managed controls' `by` against the assembled operation ids before passing those declarations to settings; a missing operation refuses startup instead of leaving a managed key writable by nobody.

The operator-only write gate uses the call's `SignedSession`; a managed `installs` key without a writer refuses `setting-managed` by the existing refusal-code road. The card's `contract/wire/catalog.ts`, `contract/service/catalog.ts`, `settings/catalog.ts` targets become the declarations paths above; the old `protocol/settings.ts` remainder stays owned by settings until every contributing owner moved, as the card's dependency rule requires.
