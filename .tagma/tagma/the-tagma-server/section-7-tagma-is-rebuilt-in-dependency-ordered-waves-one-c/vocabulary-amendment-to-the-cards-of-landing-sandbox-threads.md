# Vocabulary amendment to the cards of landing, sandbox, threads, native-harness, external-harnesses, invocation, http, socket, cli and composition

The accepted vocabulary [[2cecbcac]] governs these ten server-module cards in [[f7e0b9dd]] (§7.5.18–27), measured against the current `restructure` checkout. The 377-name ledger [[4dfd93e7]] is input, not a complete exception list. This decision fixes target contract spellings before any wave opens. In every contract below, a tag carries its own inline member shape, consumers use `Tag['Service']` (`Context.Service.Shape<typeof Tag>` only where TypeScript requires a reference), implementation classes stay private and layers are named `<tag>Layer`; no `Faces`, `Owner` tag or service locator survives. Each service id follows `tagma/<module>/<Tag>`. A service id is in-process identity only. Plural tags own a collection's acts on its items; capability and policy tags are singular. Each map, gate, feed and receipt has one implementation owner even when that implementation fills several tags.

**Acceptance and scope (§8dab19b6, questions 1–9).** The observable result is ten collision-free target maps with every current exported service member allocated to exactly one subject tag, owners for stateful mechanisms, per-file rename pairs, carrier treatment, and superseded card sentences identified below; the problem is that the card names predate the accepted vocabulary and cannot safely be given to builders as written. What stands now is the source read at this worktree, while the cards' frozen baseline is `98d8d3a216`; builders still run the delta review of §7.2.2 and amend a new mismatch before moving code. The target is the accepted 5b vocabulary, with its rejected alternatives (named service-shape types, all-failure `Failure` classes, a free-form `Result`, `Live` implementations and merged state merely because a contract split) rejected for the reasons in 5b. The owners and their boundaries are the per-card entries below; the ten wave tasks remain the card's, without new work or claims created here. Existing current-truth claims are reconciled from code at their own M3, not restated or verified by this future decision. Order stays §7.2: `landing preservation` before worktrees M1, module M1 then M2 then M3 then N, `invocation K5a` before K2 retirement, `perf E5` at the joint lane/adapter cut, doors after invocation, and `composition M2` after all other M2 work.

**Compatibility (§8dab19b6, questions 10–17).** Contracts here are the M1 target; old TypeScript imports move with each module's M1/M2, without a re-export. A binding rename does not rename its `_tag`, service key, table/column, operation id, socket RPC verb, HTTP field or exposed `name`: each carrier below is marked retained, or attached to the card's explicit D4/D6/E4/E5/K2/K5a migration. Persisted rows read by the former build follow those migrations and §2's rollback/downgrade preflight; no opportunistic persisted rename is implied. Authorization is still decided by each owner and invocation at the operation door; the sentence “service named for subject” does not grant a new act. The owners of long-lived maps, subscriptions, gates, queues and receipts below retain their current failure, race and cleanup guarantees; contract splitting does not fork them. Resource ceilings, fallback at a full bound, deployment behavior, dropped connections, restarts, retries, and observability remain the relevant card's §§5–12 and accepted sections 2–4; no new figures or rollout change is introduced by a TypeScript spelling alone. At each M1, the old runtime's `composition/start.ts` must install the available real or specifically listed transitional implementation *before admission*; at each M2, public carriers change only through the named migration. A builder proves the target by a collision check of tags/ids/renames in that module plus the card's own M3 acceptance, with the existing operation/feed parity checks where it publishes them. Where no card-specific resource or access change is named, out: vocabulary leaves the standing owner's behavior untouched.

**Spec-list disposition.** 10 contract: the inline service tags and their ids/members below, with K5a's aliases and answer versions; 11 stored data: D4/D6/E4/E5 and the per-card carrier ledger below, with section 2 rollback; 12 authority: unchanged owner/door verdicts, with new hook or quiet acts installed before admission; 13 long-lived state: exactly one owner per gate/map/feed/receipt, with boot resumption in that owner's layer; 14 bounded resources: out — no new numeric limit, the existing card ceilings remain; 15 rollout: one M1/M2/M3/N per card, keyed/transitional work at the listed earlier milestones; 16 failures: typed condition words and unchanged refusal codes, with lost/unsettled settlement still through the original owner's receipt; 17 observability: owners' current feeds and the cards' M3 debt/parity checks, plus the per-module tag-id and target collision check. Questions 1–9 are answered in the acceptance paragraph and each card's contract, owner and implementation-order text.

The repeated §7.4.1 sentence “A service's tag and its faces type live in `contract/service/<concept>.ts`” is replaced throughout these cards by “A service's subject-named tag has its shape inline in `contract/service/<concept>.ts`; consumers write `Tag['Service']`, and the implementing file exports `<tag>Layer`.”

### `threads` (§7.5.20)

**Contracts.** Tags *declared here* use `tagma/threads/<Tag>` and inline members; kernel-declared ports retain `@runlith/agent/<Tag>` ids and have no second server tag. `Harness` (port, `HarnessRegistry` owns its registrations) has **the full neutral contract** of [[f658e190]] §1.2, with the 5b member spellings: `born(unit,thread,request)`, `begin`, `deliver`, `continue`, `answer`, `cancel`, `stop`, `end`, `quiet`, `retract`, `folded`, `record`, `evidence`, `current` (formerly `standing`), `row`, `models(requested)`, `titleContext`, `spent(spawnRootId, principal): { tokens, unmeasured: threadIds }`. Native sums its measured run usage; external names its unmeasured threads. C1 reading for this large accepted port: `born/begin/deliver/continue/answer/cancel/stop/end/quiet/retract` concern the *selected harness runtime* of the addressed thread; `folded/record` are that runtime's projections in threads' one journal unit; `evidence/current/row/models/titleContext/spent` are that runtime's evidence, capabilities and spend accounting. Every member is dispatched by the thread's harness id; no member owns the neutral inbox, mandate, journal lane or record. Native- and external-harness implementations each fill this one contract; they do not introduce competing `Harness` tags or their own journal lane. `HarnessRegistry` has `register`, `resolve`, `list`, consumed by `ThreadBirths`, `ThreadTurns` and composition. `Harness.quiet` is declared only when native and external implementations and the change-record/sandbox consumers land in one switch (§7.2.7), so no old check pretends to be an atomic lease. The kernel's target is the subject cut [[e4f76910]], not an `Harness`-shaped catalog/runtime pair. `threads` fills `Threads` (`@runlith/agent/Threads`: `find,named,lineage,list,watch,readBirth,create,delete`), `ThreadRuns` (`@runlith/agent/ThreadRuns`: `current,start,deliver,continue,stop`) and `ThreadBudget` (`@runlith/agent/ThreadBudget`: `of`), dispatching the run members to its selected `Harness` with no native fallback. `ThreadBirths.create` is the Tagma operation-facing birth; kernel `Threads.readBirth` settles its key/receipt before fresh admission, `Threads.create` coordinates the neutral birth and calls `Harness.born`. `ThreadTurns` supplies Tagma's turn operations, while kernel `ThreadRuns` supplies the kit's run controls; a Tagma ask's `answer/cancel` remain on `Harness`, never on `ThreadRuns`. The neutral selection is kernel `ThreadModelSelection = { provider: string, model: string, reasoning: string | null }`, never llm's incompatible `ModelSelection`; `ThreadRecord.model` is this type or null, a raw birth ask is `Partial<ThreadModelSelection>`, and a directory row's selection adds `account`. `ThreadBudget.of({spawnRootId,principal})` reads the mandate's allowance and aggregates `Harness.spent`; a finite allowance with any unmeasured spend answers `remaining:0` and the actual `unmeasured: readonly string[]` of thread ids, not a fabricated zero-use reading.

`ThreadActs` (`harness/ThreadActs.ts`) retires rather than keeping fifteen unrelated members. `ThreadBirths` (`tagma/threads/ThreadBirths`) takes `create`; `ThreadActs.types` delegates to the kernel-declared `ThreadTypes.offered` (`@runlith/agent/ThreadTypes`, `resolve/offered`), filled by threads' one library registry as a required tag (not a `CollaborationConfig.types` bag); each offer adds its opaque `harness` id and `capabilities: {messaging,compaction,modelMove,fork,readReach,judgedModel}` (all booleans), while stored `typeId` and exposed offer labels stay.
