# Vocabulary amendment: installation, change-record, power, mcp, artifacts, executions, enforcement, performance, worktrees

This is the name/contract overlay for server cards §7.5.9–17 in [[f7e0b9dd]]. [[2cecbcac]] §5b wins over a card, and [[4dfd93e7]] supplies its measured rename rows. Paths below are **current** paths under `apps/tagma/server/src/` unless a `packages/` path is given; the corresponding target path is the card's §8 map. This decision fixes names before these waves; it does not activate migrations or rename code. Types that are internal helpers remain private, not additional DI tags. In each contract below, the listed members are the entire member set; constructor dependencies become separate positional parameters. Each tag's shape is inline, consumers use `Tag['Service']`, and an implementing class uses `Context.Service.Shape<typeof Tag>`. The old tag ids remain neither aliases nor persisted keys: Effect service ids change with their tags at M1.

**Acceptance and boundaries.** A module opens its M1 only after every exposed tag below is declared at `tagma/<module>/<Tag>`, one owner is assigned to every live mutable resource below, the named symbol map has no same-scope collisions, and every persisted or wire carrier is checked against the carrier ledger below. Target filenames and migration order otherwise remain the cards'. The present code at `restructure` still declares the old tags, fields and files; this is a target, not a claim that it is already built. Reject the apparent expedient of adding `Faces`, `Owner`, `Deps`, `Live` or `Result` aliases: it creates two spellings for one subject. Build in the card's M1/M2/M3 order, moving each current member and consumer with its implementer; keep accepted §7.2.7 transitional bindings until their stated replacement. Claims/tasks in §7.5.9–17 retain their card's graph-work disposition; this amendment changes none. No independent store migration beyond the card's listed ones is authorized.

## Installation (§7.5.9)

**Contracts and consumers.** `InstallationPaths` (`tagma/installation/InstallationPaths`): `databasePath`, `installationRoot`, `launcherPath`, `seedDirectory`, `installationAnchor`; platform, workspace, change-record and composition take the needed paths at start, not the whole tag. `InstallationClosure` (`tagma/installation/InstallationClosure`): `read`, `verify`, `current`, `write`, `parts`; installation's cuts, builds and succession consume it. `MachineRegistry` (`tagma/installation/MachineRegistry`): `dump`, `restore`, `open`; projects/settings/graph supply three restore participants, installation drives export. `Succession` (`tagma/installation/Succession`): `current`, `restart`; current `http/succession.ts#Succession` class becomes private `ProcessSuccession` implementing that tag, and the HTTP operation and build-then-restart consume it. `CheckoutBuilds` (`tagma/installation/CheckoutBuilds`): `checkout`, `building`, `built`, `build`, `stop`; current `http/checkoutBuilds.ts#CheckoutBuilds` class becomes private `CheckoutBuildRunner` implementing that tag, and CLI/health consume it. These mechanism class names are distinct from their public subject tags. `FrozenBuilds` (`tagma/installation/FrozenBuilds`): `state`; HTTP serving consumes it. `SetupSteps` (`tagma/installation/SetupSteps`): `run`; external-harnesses fills the machine-CLI step. `SuccessionSteps` (`tagma/installation/SuccessionSteps`): `replaceHost`; executions fills it. `DowngradeSteps` (`tagma/installation/DowngradeSteps`): `close`, `drained`; enforcement fills the queue preflight step, while providers supplies a distinct `ConsoleKeyRollback` (`tagma/installation/ConsoleKeyRollback`: `copyToSnapshot`) after preflight. Steps are installation's start-bound slots, not a bag of services. No `InstallationProvenance` service: `measureProvenance` is a pure start-time producer whose value is passed to graph.

**State owners.** `installation/registry/file.ts` alone owns the registry rewrite counter and `registry.json`; its restore coordinator alone takes the machine transaction, and projects/settings/graph write their own rows inside it. The same registry driver subscribes to projects' `registryChanged`, settings' `settingsChanged` and graph's `projectPolicyChanged`; no graph feed retains a parallel dump. `installation/builds/checkout.ts` owns the one running-build slot, process group, stopping and finishing promises, `build.json` and its boot reap. `installation/process/succession.ts` owns the single restart permit and leaving receipt. `installation/process/claim.ts` owns the data-directory pid claim. `FrozenBuilds` measures once on construction, and `installation/closure` alone owns version publication. All downgrade steps are coordinated by installation, with enforcement solely owning the queue's admission/drain state.

**Renames and carrier decisions.** `install/closure.ts: InstallationOrigin → InstallationProvenance` (new relative to card §8(c)); `install/standing.ts: Standing → CurrentInstallation, readStanding → readCurrent`; `protocol/machineStanding.ts: MachineStanding → MachineState, StandingAct → MachineAct, serverStandingSchema → serverStateSchema, hostStandingSchema → hostStateSchema, CheckoutStanding → CheckoutBuildState` (the rename-map's generic `CheckoutState` would collide with workspace's checkout state); `http/succession.ts: RestartAsk → RestartInput`; `http/claim.ts: DataDirectoryHeldError → DataDirectoryConflict`; `http/sourceCut.ts: measureSource → measureProvenance`; `installationPaths.ts: databasePath → databasePath`; `install/launcher.ts: installationBin → binDirectory`; `http/FrozenBuilds.ts: FrozenFaces → remove, FrozenBuilds.layer → frozenBuildsLayer`; `http/succession.ts#Succession` implementation class → private `ProcessSuccession` beside the `Succession` tag; `http/checkoutBuilds.ts#CheckoutBuilds` implementation class → private `CheckoutBuildRunner` beside the `CheckoutBuilds` tag; `install/closure.ts: InstallationMismatch → InstallationInvalid` with `reason: 'mismatch'` (the existing invalid-document case becomes `reason: 'malformed'`), preserving `role,path,expected,found` on mismatch and `detail` on malformed; its local `refusalDetail` switch and callers change in the same M2 cut. No serialized arm bears this class tag: current health/CLI roads map it to text and fixed refusal codes. `install/cut/release.ts: NoPreviousVersion → PreviousVersionMissing` (new). `protocol/toolResult.ts#VacuumAnswer → VacuumAnswer` (new, installation-owned native tool answer; wire `status:'ok'` and `vacuum` field stay). `MachineRegistry` and `InstallationClosure` are new tags; their current functions are named above and their shapes are inline. Carrier reading now: `install/closure.ts` produces local `_tag` arms `InstallationMissing`, `InstallationInvalid`, `InstallationMismatch`, `InstallationUnreadable`; `refusalDetail` maps them to text for `http/main.ts`, `http/succession.ts`, `install/cut/build.ts` and CLI setup, and no current operation exposes those `_tag` arms. The class fold locally replaces `InstallationMismatch` with `InstallationInvalid(reason:'mismatch')`; the unchanged external codes are `installation-refused` and the health route's `no-successor`/`successor-left`. `http/claim.ts`'s actual old `_tag` is `DataDirectoryHeld` (class `DataDirectoryHeldError`), caught at startup/succession rather than serialized; both its `_tag` and diagnostic `Error.name` become `DataDirectoryConflict` in-process. `install/cut/release.ts#NoPreviousVersion` maps through `install/cut/build.ts#back` to CLI refusal code `no-previous`, which stays. These are local-only atomic producer/catcher renames, not a K5a answer migration. `InstallationRefusal` holds `Missing|Invalid|Unreadable` classes (formerly also `Mismatch`) and becomes `InstallationFailure` in `install/closure.ts`; its original `InstallationRefusal` name was not a code-only union. `InstallationOrigin`/`MachineStanding`/schema binding renames are TS only: JSON `origin.checkout`, `mode`, `state` and inner `_tag` values stay. `build.json`, `registry.json`, closure paths, `TAGMA_*` and standing-by IPC stay. **Card text replaced.** “`contract/service/… closure.ts` (`readInstallation`, `verifyInstallation`, the current installation)” becomes the `InstallationClosure` contract above, with every member placed. “`InstallationOrigin`” becomes `InstallationProvenance` in the TypeScript type only. “`Standing` → `CurrentInstallation`” stays, including its `readCurrent` function; it is not the `MachineState` snapshot. **State owners.** The `record/write.ts`/`record/holding.ts` implementation owns the `workspace_change*` rows, held-line arithmetic, original texts and author attribution; the `prepared/change.ts` implementation owns a prepared-change lease and private-index custody until release, never a second inventory maintained by enforcement or landing. `threadFiles/rows.ts` owns the per-thread/root subscription map, its one semaphore, detach callback and retained authorship cache; splitting the tag does not split those maps. `record/pending.ts` owns pending-op files and their boot replay; `record/discharge.ts` owns the HEAD-moved subscription and recovery sweep. `record/feed.ts` owns the change feed. Graph solely owns holder→task labels; change-record calls its port for rows even when the caller read another session.

**Renames and carriers.** `harness/WorkspaceChangeLog.ts: WorkspaceChangesOwner → ChangeRecord` (tag), `WorkspaceChangeLog → ChangeLog` (private implementation/port), `WorkspaceChangeRow → ChangeRow`; `protocol/evidence.ts#ChangeReadRow → ChangeReadRow = Omit<ChangeRow, 'id' | 'at'>` (the wire projection, not a second full stored row). These different shapes share one producer with an explicit projection; **the note map's `WorkspaceChanges` is rejected** because it conflates the plural kit interface with this server's single record. `harness/ThreadFiles.ts: ThreadFilesOwner → ThreadFiles` (tag), old `ThreadFiles` class → private `Files`; `protocol/checkoutStatus.ts: ThreadFileStanding → ThreadFileState`; `files/stripComments.ts: StripCommentsOwner → StripComments` (tag), `StripCommentsFace → remove`, former function shape becomes inline `strip`; `worktrees/CheckoutReads.ts: CommitStamps → CommitOverlay`; `harness/ThreadFiles.ts: PathUnread → PathUnreadable`, `PathOversized → PathRefused(reason:'oversized')` (both new condition-word classes; `path-unread` and `path-oversized` door codes stay); `harness/WorkspaceChangeLog.ts: WorkspaceChangeFact → ChangeFact` (new, private); `harness/ThreadFiles.ts: ReadingFailure` stays a failure union. `WorkspaceChangeRow` changes the TS name only; the row's `origin: edit|write|delete|shell`, `threadId`, `runId`, `tasks`, `at` and every stored `workspace_change*` table and column stay. `ThreadFileStanding` changes TS only, preserving the wire `state` and inner status strings. `ThreadFiles.ts#authorshipRefusal` maps local `PathUnread` and `PathOversized` to `GateRefusal('path-unread'|'path-oversized',…)` before an operation answers; the new `PathUnreadable` and `PathRefused` `_tag`s therefore stay in-process, with existing codes, fields and unblock unchanged. `http/handlers/files.ts` also hand-declares a distinct local `{_tag:'PathUnread',cause}`; that HTTP-owned wrapper becomes `HttpPathUnreadable` locally with its generic `files` refusal code unchanged, and never imports the change-record class. Pending-op filenames stay. `read_changes`, `read_authorship`, `strip_comments` stay operation ids; `record_write` is a new K2 id.

Card “Symbols renamed: none” becomes the five symbol renames above; `McpServersFaces` is removed, not carried into `contract/service/servers.ts`.
