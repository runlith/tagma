# Tagma architecture spec · Section 1. Modules — draft v10

**v8 redesigned section 1 from meaning; v9 and v10 keep that method.** Versions 1–7 laid files out by directory, measured imports and cut cycles; only the thread middle was designed top-down (decision [[3c5891f4]], `spec-01-modules.md`, `module-map-v6.md`, territory [[8553c5b9]]). Two independent meaning audits found 12 (`meaning-audit-arch-opus.md`) and 16 (`meaning-audit-arch-astra.md`) placements that follow imports rather than owners. v8 starts from the product's concepts, draws a module around each cohesive group of them, chooses every relation's pattern by what the relation means, and only then maps files and measures today's imports as the control that the code can reach the map.

**The operator's principle binds every sentence:** boundaries follow meaning — owners, logic, common sense. Where code imports from today is never an argument for where a thing belongs; imports only say what must be cut. **Harness is a core concept (the operator's word):** a harness is an agent runtime that runs threads; Tagma is the native harness; external harnesses (Claude Code, Codex, Grok, Devin, Cursor, Gemini, …) are integrated.

Measured at `98d8d3a216` over the 891 tracked non-test `.ts` files of `apps/tagma/server/src` — 871 production files and 20 fixtures — read from a snapshot of that commit, so a moving checkout does not change the figures. Beside this file: `spec-01v10-relations.mjs` (the relation registry and its checker, which exits non-zero on any problem; writes `spec-01v10-relations.json`), `spec-01v10-territory.mjs` (the file map and the import control; writes `spec-01v10-territory.json`), `spec-01v10-cutsites.md` (every import site of every cut edge) and `spec-01v8-v7map.json` (v7's file-to-module map the control starts from). Nothing in the repository or the graph was changed; no test or typecheck ran. The one figure read from a database — the count of external sessions in §1.13 — was read with `sqlite3 -readonly` from this machine's store and is a sample of this machine.

Section 1 draws boundaries only. Moving a module is a rebuild under sections 2–5 and its card in section 7, never a file move.

## 1.1 Outcome, problem, and what holds now

### Outcome
- **27 server modules**, each owning one meaning stated in one product sentence (§1.3).
- **The harness concept has one owner and two kinds of implementation, without overlap.** `threads` owns the concept, its contract (the `Harness` port and its registry, with the outcomes each face must keep) and everything a thread is whatever runs it — its mandate, its collaboration, its journal and rollout. `native-harness` is Tagma's own runtime. `external-harnesses` integrates external CLIs, one adapter per CLI. No harness module imports another; `threads` imports none and builds with no native run service.
- **Every relation has a pattern chosen for its meaning** (§1.4), and every place the product must grow has a named extension point and owner (§1.4.5).
- **The order is acyclic on the relation registry, checked by script** (§1.5): 27 modules, 152 relations, no non-trivial strongly connected component, no relation against the order.
- **The territory maps all 891 files** (§1.6, appendix A); the control over today's imports names the 92 domain edges and 47 door edges that must be cut, each with the relation that replaces it (appendix B) and every import site under it (`spec-01v10-cutsites.md`).

### Problem, with evidence
- **v7 placed by imports.** `check_rules` sat in `worktrees` because it borrowed `changeSubject`, `handoverOf` and `landingPlace` from `submit_work` (`harness/submitWork.ts:292`, `operations/projects.ts:69,84`). Both audits move the judgement to `enforcement` and the session's change to `change-record`; the port `ChangeSubjects` existed only because of the misplacement.
- **v7 had no harness concept.** Native and external runtimes share `threads`, and a low `clients` module holds the external CLIs' formats. Under this map the external session code imports native internals in 11 places (the kernel thread-store adapter, rollout, the kernel state type) and `threads` imports foreign formats and sessions 34 times (appendix B).
- **Knowledge holds what is not knowledge.** Setting rows and their resolution (`graph/core/Settings.ts`), project registration (`graph/projects/Projects.ts`) and each store's writer register (`graph/projects/Sessions.ts`) sit in `graph`, although MCP, power and executions read settings and every record names a project.
- **`worktrees` held three meanings:** the worktree lifecycle, landing work into git (landing, merge, PR), and reading any checkout (`worktrees/CheckoutReads.ts`), including the canonical one.
- **Doors and graph files host domain acts.** `submit_work` is declared in graph's operation file (`protocol/operations/graph.ts:1641`) with part of its body in `operations/projects.ts`; the hook transport of external CLIs (`cli/hooks.ts`, 821 lines) and most domain verbs sit in the `cli` door.

### What holds now, checked against the code
- **Birth already dispatches by harness:** `input.agentId === 'harness' ? deps.births.create(input, commit) : harness.createThread(input, commit)` (`harness/ThreadActs.ts:238`).
- **External sessions already use harness-neutral thread services:** the thread store, the inbox and scratch (`harness/HarnessSessions.ts:113-128`), and they report to a parent through the kernel's `deliver` (`harness/HarnessReports.ts:210,233`).
- **External CLIs share one adapter shape** — launch argv, hook surface, MCP surface, event readers, screen asks, keys (`protocol/harness/adapter.ts#HarnessAdapter`) — and one table of six (`protocol/harness/table.ts:10`). The native harness is the id `tagma` (`protocol/session.ts:5`).
- **The kernel takes its storage through ports a product fills** (`packages/agent/src/thread/ThreadPorts.ts`: `ThreadStore`, `ThreadEventJournal`, `ThreadInbox`, `ThreadDirectoryStore`, `ThreadResourceLedger`, `ThreadRunStoreFactory`, …), so different server modules can fill different ports.
- **An external thread already carries harness-neutral state in the native `thread` row:** its authority is written at adoption and inherited at spawn (`harness/HarnessBirths.ts:88,159`) and applied by the CLI's permission hook (`harness/HarnessPermissions.ts:61-79`); every table that holds shared thread state — inbox, delivery claims, resources, live spells, seen marks, target operations — has a cascading foreign key to `thread.id` (`db/thread.ts:243-255,320-361,482-495,539-564`).
- **An external thread already has a Tagma history of its own:** its birth ensures a rollout (`harness/HarnessBirths.ts:100-102,179`), and worktree notes are appended into it with no harness check (`harness/WorktreeNotes.ts:112-114`); a lost store is rebuilt from the rollout's `{thread, facet, session}` metadata line and its holdings (`files/ThreadRolloutSync.ts:504-537`).
- **Archiving a worktree commits its leftover work** before removing the directory (`working/WorktreeFinishing.ts:552-591`), drops its pending merge in the same unit as the archive (`:1083-1097`), and puts its threads away one by one with a kept or refused answer each (`:1100-1111`); `update_worktree` merges nothing — it hands the lead thread a task to merge the base (`:793-824`).
- **Two overlays are already injected:** `CommitStamps` into the checkout reader (`worktrees/CheckoutReads.ts:74`), and the commit hooks installed by the `create_worktree` body once the worktree is ready (`operations/worktrees.ts:189-190`).

### The harness concept
- **Harness-neutral** — `thread-record` and `threads`, whatever runs the thread.
  - `thread-record`: identity, project, lineage, principal, harness id, agent, birth provenance (`born_of`, `spawned_by_run_id`, `created_by`), title, archive, pin and the published phase.
  - `threads`: the thread's mandate — authority, rights, delegation, spawn budget, host binding — in a row of its own; the journal, the rollout file and its lane; notes about the thread (worktree created, set up, moved, merged); birth and placement; the inbox, envelopes, obligations and their delivery claims; collaboration; resources held and their release; targets and their change; archive, pin, move, delete; listing; the agent library; standing permission rules; doctrine.
- **The native harness's** — the kernel composed for Tagma: runs and their ledger, the admitted target of a run, the folds it projects from the journal, evidence of a native conversation; model, account and prompt selection per thread; instructions delivery; capabilities and tools; compaction; keep-warm; workflows. Its execution row (`thread`, now only execution columns) exists only for threads it runs.
- **An external harness's** — the session row (today's facet carried whole: CLI, session key, asked model, execution, observation, question, `held`, session state, retiring flag) and the facts of legacy runs; launch and adoption into a terminal; a session token before adoption; the hooks and the CLI verbs they call; observation of the CLI's files and screen; typing words and answers in; what Tagma installs into the CLI (hooks, MCP declaration, skill); one adapter per CLI. Tagma never controls a CLI: every reading is evidence and every typed delivery is one the CLI may or may not take (area [[6ca6b465]]).

#### The `Harness` contract
`threads` declares `Harness` in its `contract/service` and keeps the registry; each harness module implements it and registers through its manifest; `threads.start(harnesses)` binds them before admission (§1.4.4). `threads` owns envelopes, obligations, rights, the ask's record and the dispatch; a harness owns execution and the evidence of its result. Each face states its outcomes, because the existing lifecycles differ and the contract must keep every one of them:

| Face | When | Outcomes and guarantees |
|---|---|---|
| `born(unit, thread, ask)` | inside the birth unit (C2b) | the harness writes its own rows (native: `thread`, `thread_log`, seeds; external: its session row); a refusal rolls the whole birth back. `ask` carries what only this harness reads (native: model, profile, prompt) |
| `begin(thread, request)` | after the birth commits | native: admit the first run; external: a launch intent (C4) the pass drives. The stable request names a durable readiness obligation. Failure leaves accepted-but-not-ready evidence; retry does not silently delete or re-create the committed child |
| `deliver(thread, item)` | after threads committed the inbox item | `queued` (behind a standing run or session), `delivered` (to the standing run or typed into the CLI), `woken` (a new run or session opened), or `stored` (kept for the next turn). The item's kind decides the road: `task` opens or queues work; an interrupt `task` cuts a standing run first; an ordinary message never opens work while one stands; a transport signal (command notice) is delivered only to the addressed run or session. A repeat of the same envelope id answers the receipt it already has |
| `continue(thread)` | an interrupted thread is resumed, or an external session joined | native: a new run only when no run stands and the latest run was interrupted — an idle thread whose run completed refuses `ThreadRunNotInterruptedError`, as today; external: joins a session already open (`joined`) or opens a new one, a branch of its own; refuses `session-reporting` while an ended session still owes its report and `session-deleting` while the thread is retiring |
| `answer(thread, ask, value)`, `cancel(thread, ask)` | an ask threads recorded | native: the kernel's pending interaction; external: the CLI's screen question, typed; a stale ask refuses |
| `stop(thread)` | the operator or a parent stops | `stopped`, or the refusal `cli-standing` when an external CLI still stands after its quit keys — the session keeps running and the terminal is left open |
| `end(thread)` | the ending walk | admission closes; the harness releases or explicitly retains custody of its execution. External release runs through a durable intent outside store units. An ending that owes a report settles the report before a new opening; incomplete release/readiness/settlement remains pending or uncertain, never falsely complete |
| `quiet(thread, scope)` | a carrier handover or a guest read | a **scoped admission lease**: acquired atomically with a check that no run or session stands, released on every outcome, refused before start when one stands. While held, `begin`, `continue`, adoption and answer-resume refuse. It is never a way to pause an external CLI: if quiet cannot be proved, the lease refuses and so does the read that asked for it |
| `retract(unit, thread, signal)` | a command notice is taken back | inside the command's unit: withdraws the durable delivery addressed to the right run or session and acknowledges the inbox item; the in-memory queue is cleared after commit. Keys a CLI already accepted are not declared retracted; a lost or partly typed delivery keeps its doubt and is never repeated automatically |
| `folded(unit, events)` | threads appends to the journal | inside the append unit (C2b): the harness projects the new events into its own rows — native: its folds; external: nothing. The append and its projection commit together, whoever wrote the event |
| `record` | the lane's export, rest, wake and repair; lost-store import | the harness's part, inside the lane's own units: native — writes its folds into the export and evicts them in the rest unit, rehydrates them in the wake unit; external — its session row and legacy-run facts. A participant, never a second lane or a second coordinator |
| `evidence(thread, query)` | a read of what happened | native: the transcript; external: the CLI's files and screen, read as evidence |
| `current(thread)` | a target change, a seen mark, a list row | the run or session held now, or none |
| `row(thread)` | the list | a wire arm whose union composition derives |
| `models(asked)`, `titleContext(thread)` | a birth asks for a model; a title is generated | whether the harness can run on it; the text a title is made from |

#### Collaboration reads a thread catalog, not the native row
The kernel's collaboration kit (`packages/agent/src/collaboration`: envelopes, obligations, the spawn tree, rights, spawn access, budget) reads every thread through its `ThreadStore` port, which answers the native `ThreadRow` (`ThreadEnvelopes.ts:165`; also `ThreadSpawnTree`, `ThreadRights`, `ThreadObligations`, `ThreadSpawnAccess`, `collaborationBudget`), and delivers by default through the native run services, with declared participants as the exception (`ThreadEnvelopes.ts:154-167,245-269`). Under this map no external thread has that row, so:
- the kit declares the complete **thread catalog** contract it consumes — id, principal, name, spawn root, parent, agent, harness, phase/liveness, authority, rights, spawn budget, host binding and declared capabilities — and `threads` fills it from `thread_record_facts`, its mandate and the selected driver's truthful projection. Native history, checkpoint, model/provider/profile and native pending-question rows are not required of external threads; native birth parameters remain the native harness's `ask`;
- the kit's envelope and obligation logic consumes a mandatory **runtime** contract for start/wake/deliver, continue, stop, answer/cancel and current execution, with stable request identities, expected-execution fences and accepted/delivered/queued/refused/uncertain outcomes. Unsupported interaction controls refuse by capability. Common completion carries the selected driver's execution identity, outcome and report evidence, never an invented native transcript. `threads` dispatches to the selected harness with no native default; native commands remain behind `native-harness`'s implementation;
- the acceptance is that `threads` builds with no native run service in its layer at all, not only without importing `native-harness`. The workflow members keep today's behaviour by composing the kit with the native runner as their runtime. Section 6 versions the package's port change.

The kernel is still not the native harness: `packages/agent` is the agent runtime kit every agent of the monorepo runs on. `native-harness` composes its loop and run machine with Tagma's stores, models and tools; `threads` uses its collaboration kit as logic behind the two ports above; `external-harnesses` reaches thread semantics only through `threads`.

| `http`, `socket`, `cli` | Framing one transport into calls and feeds; `cli` also runs the verbs modules declare and serves MCP. | kept |
| `composition` | Assembling the modules: their layers, manifests, arguments and start bindings, and the process entry points. | kept |

### Where each boundary is most at risk
- `threads` runs nothing: its one model call is a title; it keeps no model history. Its journal orders events; what an event means to a model is its harness's fold.
- `threads` builds without any native run service: collaboration reaches runtimes only through the `Harness` dispatch.
- `native-harness` keeps no harness-neutral state: the inbox, lineage, authority, rights, resources and delegation are `threads`' or the record's.
- `external-harnesses` keeps no second inbox truth; it types what `threads`' inbox holds and records the claim there.
- `change-record` publishes nothing and judges nothing: it prepares the change; `landing` publishes it, `enforcement` judges it.
- `landing` selects no lines and judges nothing; it hands no work to a thread. `enforcement` owns no checkout and no landing.
- `workspace` owns no worktree lifecycle and no authorship; its commit history shows authorship through a hook `change-record` fills.
- `graph` stores no settings, registers no project and runs no generic git.
- `platform` names no domain: no harness list, page family, setting key, voice, or domain type moved there to escape an edge.
- `composition` decides nothing: no budget figure, no owner locator, no tool implementation.

## 1.4 Relations and extension points

### 1.4.1 Patterns, chosen by what a relation means

| Pattern | The relation means | What it guarantees, and its limit |
|---|---|---|
| **Service** | the consumer asks a lower owner for a fact or an act that is that owner's | the default; a direct call through the owner's `contract/service`, no mirror interface for one method |
| **Key reference, read model** | a row names another owner's row, or reads its facts | section 2 §2.4.2: a key reference grants no DML; a read model is the owner's contract |
| **Participant (C2)** | one atomic entity spans several owners' rows in one store | a named coordinator at or above every participant passes its unit to each participant's store method (section 2 §2.4.3) |
| **Port with two-phase start** | a lower owner's act needs a capability only a higher runtime has | declared by the lower in `contract/service`, implemented by the higher, bound by `start` before admission; before `start` the lower refuses explicitly; C2b when the answer must land in the lower's unit |
| **Hook (extension point)** | the owner of a scenario lets other owners insert a step or refuse at a named moment | order, scope and failure semantics are the owner's; contributors register through their manifests; a contributor above the owner is bound at `start`, like a port; zero contributors is a valid state |
| **Event (C3)** | an owner announces a committed fact; subscribers keep projections of it | data-free, after commit; a late or restarted subscriber recomputes from the read model; never where atomicity is owed |
| **Argument** | data decided by one owner is handed to another at build: paths, content, budgets, lists | the receiver knows nothing of the giver; not a service locator |
| **Manifest contribution** | a module declares its part of a list the product keeps: operations, feeds, endpoints, setting keys, capabilities, CLI verbs, page families, passes, doctrine sections, tables | the list's owner checks ids and shapes; composition collects; nothing imports composition |
| **Adapter** | one owner translates an outside format or protocol at its own boundary | vendor CLI formats (`external-harnesses`), the host wire (`packages/executions`), model wires (`packages/llm`), Docker (`sandbox`), MCP clients (`mcp`) |
| **Shared type** | a word every module uses and no module owns | only neutral vocabulary in `platform`; a domain type never moves there to escape an edge |

A pattern is never chosen to remove an edge. When the only defense of an edge is its direction, the thing sits with the wrong owner, and the owner is corrected instead.

### 1.4.4 Two-phase start
Layers build in the order of §1.5, each without the services of the modules above it. Then composition binds, before admission:

| Module | Bound at `start` |
|---|---|
| `power` | `PaceDoor` ← executions |
| `executions` | `NoticeTakeBack` ← threads; terminal adopters ← external-harnesses |
| `worktrees` | `PreservationCommit` ← landing; retirement settlement ← landing; placed threads ← threads |
| `change-record` | carrier admission ← threads |
| `sandbox` | `ReadStillness` ← threads |
| `landing` | `MergeNotice` ← threads |
| `workspace` | environment backends ← executions, sandbox; root-published ← enforcement; commit overlay ← change-record |
| `projects` | removal holds ← workspace, graph, threads |
| `settings` | managed writes ← graph |
| `graph` | gauges ← external-harnesses; the enforced-law contract's runtime part ← enforcement, where it needs services |
| `installation` | setup steps ← external-harnesses; succession steps ← executions |
| `threads` | `Harness` implementations, agent library entries and resource kinds ← native-harness, external-harnesses |
| the collaboration kit (inside `threads`' layer) | thread catalog and runtime ← threads, once the harnesses are bound |
| `native-harness` | `ThreadExecution` ← invocation |

Then event subscriptions register (or replay from the owner's read model), then admission opens. Before its `start` a module refuses what needs the binding, explicitly and at once — never a wait — and its background fibers admit no such work (v7 rule 9). Pure-data contributions — operation pairs, setting keys, capability declarations, doctrine sections, page families, CLI verbs, tables, the `lawEnforcement` codec and the enforced-law descriptor — are arguments at build, not start bindings. A contribution whose implementation needs services — a capability's tool factory or runtime rule, a provider, a hook body — has an owner and a scope and is bound at `start`; it is never counted as data. Two-phase start removes constructor dependence only because admission is refused until every binding stands; it is not a proof that no runtime wait cycle exists, and section 3's wait order, deadlines and reentrancy stay binding on the new owners.

## 1.5 Order

**Bottom-up:** `platform` < `projects` < `settings` < `providers` < `thread-record` < `workspace` < `graph` < `catalogs` < `installation` < `change-record` < `power` < `mcp` < `artifacts` < `executions` < `enforcement` < `performance` < `worktrees` < `landing` < `sandbox` < `threads` < `native-harness` < `external-harnesses` < `invocation` < `http` < `socket` < `cli` < `composition`.

**Checked, not assumed.** `node spec-01v10-relations.mjs` builds the adjacency from the 152 relations of the registry (26 of them composition's), refuses unknown or duplicate endpoints, runs Tarjan's algorithm, compares every relation with the order and exits non-zero on any problem: `{"nodes":27,"edges":152,"nontrivialScc":[],"backwards":[],"problems":[],"isolated":[]}`. A relation whose pattern is only an argument handed by composition is not in the registry, because it allows no import: v9 removed `change-record → graph` for that reason. The zero is a property of the target contract; today's code reaches it only through the cuts of appendix B.

**Where the order differs from v7, and why.**
- `workspace` below `graph`: a checkout does not need knowledge; the graph is served from a checkout. It was the other way only because registration sat in `graph`.
- `settings` below `providers`: providers reads its preferences from settings; settings imports no provider.
- `sandbox` below `threads`: a guest exists without a thread; binding one is a step of the thread's birth (Astra C11). `BirthBinding` goes.
- `landing` above `worktrees` and `enforcement`: a merge integrates a worktree and every publication is judged.
- The two harnesses above `threads`; `native-harness` before `external-harnesses` is only a linearization — no relation joins them.
- `clients` is gone; `projects` is new.

## 1.7 What stays from v7, and what changes in it

### Module form — kept
```
<module>/
  contract/wire/     browser-safe: operation declarations, schemas, events, read models, public types
  contract/service/  server services, ports and hooks other modules use or fill
  <module>.ts        assembly surface: ordered layers and the manifest of contributions
  cli.ts             verb descriptors, imported eagerly by the CLI entry (section 4)
  …                  internal
```
A port or hook lives in its declarer's `contract/service`; implementers and contributors import it from there. A module may expose several ordered layers (early stores, late facade).

### Rules — v7's nine restated, two added
1. **Consumer → entry:** a module reads a neighbor's `contract/`; the root reads `<module>.ts`; the app reads `contract/wire/`; tests read their own module, neighbors' `contract/` and declared test entries.
2. **Dependencies are an acyclic `depends-on` graph**, checked against the imports of assigned files.
3. **Relations follow meaning** (replaces v7's "breaking an upward dependency"): the pattern comes from §1.4.1; a pattern chosen only to remove an edge is a placement defect.
4. Floors inside a module and the module boundary are separate checks.
5. **Doors import only `invocation`'s `contract/service`, `platform`, and the transport kit of their own framing — the MCP server kit (`@runlith/mcp/server`) for `mcp-serve`** (section 4 §4.4.11; amended by section 6).
6. A scenario across modules has a named coordinator; it may hold one transaction when it declares its tables and all sit in one store file (section 2).
7. **Call context owners:** installation — a lifetime to which owners contribute their services, never the owner of accounts, host clients or performance (Astra C15); workspace, with graph's serving; run — `native-harness` for a live native run called with its own grant, `external-harnesses` for an adopted session; an act header of an ended run is provenance only, keeping its thread actor and giving no run scope (section 4 §4.4.2), and an external session token without an adopted thread resolves to an external principal with no run scope and the operator's standing permission rules as its policy (§4.4.3a); call — `invocation`. A mandatory unbound capability is an assembly error.
8. The root is one typed union of manifests; every central list and `exports` derives from it; the compiler proves declaration and body complete (section 4).
9. **Late binding between modules only by two-phase start**; a hook whose contributor sits above its owner binds at `start` too (§1.4.4).
10. **No harness module imports another, and `threads` imports no harness module and builds with no native run service** (new).
11. **`platform` holds only neutral vocabulary:** no domain list — harnesses, page families, setting keys, voices — and no domain type moved there to escape an edge (new; Astra C13).

### The `modules` rule and its engine needs — kept
- One `modules` rule at gate from day one; everything standing is debt owned by the module's wave task.
- The first snapshot comes from this territory, not from the graph (`#module` takes only `dir` today, F074): exactly one current physical owner per file — a mixed file's primary owner — with that file's debt. A named split enters the snapshot only when its wave has made the new files; the snapshot then records the new file territories and maps each earlier violation onto them. As directories become homogeneous, the snapshot materializes from `#module`.
- Entries are the whole module on day one and `contract/` after its wave (a tightening).
- Debt is `<consumer> → <target>` with its set of offending files; a new offending file is always refused; replacing an offender is refused.
- An unresolved in-project import refuses for runlith (`unresolved: refuse`); another project sets it.
- Floors inside a module are `direction` with `base` at the module's directory.
- Engine needs, neutral to any project and language: the snapshot in parameters through `enforce_rule`; tightening without a question (a removed edge, a narrower entry, a path nobody measured); node selection by role, not by the literal `#module`; parameters `entries`, `cycles`, `coverage`, `unresolved`, `files`, `reads`; nested territories where the deeper owns; debt with file sets; affected consumers of a changed export, entry or territory; a verdict that separates checked from unmeasured; debt that follows the same violation across a move only when the consumer, the allowed target and the kind survive under the snapshot; languages through the `code-facts` adapter. `package-boundary` stays for browser safety, SDK bans and packages' own floors.

### Waves and the floor rule [[f49f228f]] — one floor question instead of three
A new top-level entry is a tightening at any floor (`direction.ts#tightens:62-66`); reordering or removing an entry is a loosening. Every module that moves takes a directory of its own name — `platform/`, `projects/`, `providers/`, `thread-record/`, `workspace/`, `catalogs/`, `installation/`, `change-record/`, `executions/`, `performance/`, `landing/`, `sandbox/`, `threads/`, `native-harness/`, `external-harnesses/`, `invocation/`, `composition/` — and is placed on its target floor without a question. ## 1.8 Rejected alternatives
- **Keep `threads` as one module holding the native runtime and a separate `cli-sessions` (v7).** It has no place for the harness concept: external sessions import native internals (11 imports today) and a new runtime would have to copy one or the other. Rejected by the operator's word on harnesses.
- **One `harnesses` module holding native and external.** The two share no dependency law — the native runtime needs providers, MCP, instructions and tools; external CLIs need a terminal, the installed binary and hooks — and merging them would let one reach into the other. The concept already has its owner in `threads`.
- **A module per external CLI.** The six CLIs share one lifecycle machinery and one dependency law; each differs only in its format. A CLI is an adapter, added as one directory.
- **The model history in `threads`, harness-neutral.** The folds — entries, history items, the log, compaction checkpoints, pruned tool calls, cache observations — are the native runtime's projection of the journal: its model history, its compaction. An external CLI keeps its conversation in its own files. Putting them in `threads` would make the harness-neutral module own native-only projections. The journal they are projected from is not native: it orders every thread's events, Tagma's notes included.
- **The whole rollout lane in `native-harness`, `threads` owning only the file format and import coordination (Opus I4).** Taken from it: §2.4.7's guarantee must sit in one owner, and export must not write another owner's watermarks. Not taken: every thread has a journal and a rollout — an external thread's birth ensures one and Tagma's notes land in it — so a native-owned lane would need a native row, cursor and export ledger for threads native-harness does not run, or a second lane for external threads. The lane goes to the owner of the journal it exports, which is `threads`; native-harness joins its units as a participant for its folds (Astra R2).
- **Two lanes per thread, export in `threads` and rest in `native-harness` (v9).** It split §2.4.7's ordering — rest only after a synced export — across two owners, and left the cursor, refusal and export ledger under a native key that external threads cannot satisfy.
- **All of a thread's history in `native-harness` (v8).** An external thread has a Tagma history too — the rollout its birth ensures, the worktree notes Tagma appends, the metadata a lost store is rebuilt from. v8 would have left it without an owner.
- **`Harness.note` idempotent by id, each harness storing its own notes (v9).** A note changes under one id — setup goes from pending to done — so a no-op on repeat would freeze it at pending, and two stores would let the harnesses diverge. Notes are journal entries with revisions, written by `threads` for every thread (Astra R3).
- **The archive resumed from `worktree_operation.committing` (v9).** That table is the worktree's birth intent and `committing` is in-memory progress today; after a commit and a crash, a retry sees a clean tree and cannot know what was committed. A dedicated archive intent, resolved against landing's receipt, replaces it (Astra R4).
- **Authority, rights and host binding left on the native `thread` row (v8), or a `thread` row kept for every thread with native columns null.** The first strands what an external thread is allowed to do on a row it must not have; the second keeps a native-typed row in the life of every thread, so every kernel column change is a migration of external threads. Chosen: `thread_mandate` (Astra R1, Opus I1).
- **The collaboration kit moved into `threads` as it is.** Its envelopes default to the native runner (`ThreadEnvelopes.ts:245-269`); moving the layer would move the native runtime with it. Chosen: a thread catalog and a runtime port with no native default (Astra R3, Opus I1).
- **`quiet` as a way to pause a thread's runtime.** An external CLI cannot be paused: after its quit keys it may still stand (`HarnessSessions.ts:581-633`). The lease only refuses admission, and refuses itself when quiet cannot be proved.
- **A low `clients` module for the external CLIs' formats (v7).** Its lower readers need a neutral id (`HarnessId`), an argument (the variables a grant scrubs, a hook's budget) or a verb contract, not the formats; the formats have one owner.
- **`check_rules` in `worktrees` or `landing` (v7, section 4 §4.4.9).** Its question is what the rules say about a subject; landing is one subject among three. It kept `landing` owning a question of law and the change build inside landing.
- **One `registry` module holding projects and sessions (Opus #12).** A session is interned per store as that store's writer register — a store mechanism for neutral `(harness, key)` refs — while a project is a registration with its own holds and address. Chosen: `projects`, and the writer register in `platform` (Astra C07).
- **Commit stamps as an argument of the read (Astra C04).** The read belongs to `workspace`, below the stamps' owner; an argument would make the caller know both. The overlay is a hook `change-record` fills (Opus #8).
- **`worktrees` and `landing` as one module.** They change for different reasons and depend on different owners: landing and merging on `change-record` and `enforcement`, the lifecycle on `executions` for setup and on `threads` for the threads placed in it. Where the lifecycle needs a commit — archiving leftover work — it asks landing through a port it declares, and landing's pending merges settle inside the archive unit through a hook; neither makes them one owner.
- **`update_worktree` in `landing`, calling a handoff capability of `threads` (Astra R4).** The act merges nothing: it chooses the worktree's lead thread and hands it a task (`WorktreeFinishing.ts:793-824`). A `landing` operation whose only act is a `threads` act owns nothing of its own. Taken: Opus I2 — `update_worktree` is `threads`', reading the worktree through `worktrees`' service and taking its finishing gate there.
- **The archive's leftover commit as a plain git commit inside `worktrees`.** It publishes a thread's or the operator's work into the project's git, with the user's hooks and the commit lane, like a landing; one owner keeps every such publication, its lane use and its receipt (Astra R4). The graph's P3 commits of its own acts are not such a publication and stay the graph's.
- **The merged note rebuilt from the worktree record (v8).** The record keeps neither the commit, the mode, the after-act's outcome nor the addressees (`db/worktrees.ts:5-28`); it would lose the note after an archive or a restart, or address it to whoever stands there later. The merge receipt is its source.
- **The enforced-law type and strictness in `platform` to remove the `graph → enforcement` edge.** It would move a domain meaning into the neutral module (rule 11). Section 9's owner descriptor already carries behaviour across this boundary (Astra R5).
- **Every native world tool made a public operation, to reach triggers.** File and shell tools are the native runtime's, bound to a World; a public operation per tool would widen the contract for one wiring. The after-edit subject enters the trigger dispatcher through `ThreadExecution` (Astra R6).
- **`thread_owner_settings` kept as one table with three owners (v8).** One table has one owner (section 2 §2.4.2); a "row of its own" inside another owner's table is not ownership (Opus I3).
- **Installing commit hooks from `worktrees` into each new worktree.** It would make `worktrees` depend on `enforcement` and miss roots published any other way; every root workspace publishes carries them through the root-published hook.
- **A `doctrine` module.** Its sections describe each owner's contract and name its operations; a module of its own would import every module's operation ids and sit above all of them, while `graph`'s briefs need its law sections. Sections are contributions; audiences assemble them.
- **The watcher in `platform` (Opus #14).** Watching a checkout's tree, HEAD, index and refs is `workspace`'s meaning; only the filesystem primitive under it is a kit.
- **Figures derived by `composition` (section 3 v5).** The root decides nothing: installation reads the machine, platform computes, owners declare their envelopes (Astra C15).
- **Opus's order (`graph` below `workspace`, `providers` below `settings`).** Both followed from registration and settings sitting in `graph`; once they have their own owners, a checkout needs no knowledge and settings need no provider (Astra's order holds).
- **`vacuum_database` in `platform` (Astra).** `platform` performs no product act; compacting the installation's store is the installation's.
- **Task labels resolved inside the handover in `change-record` (Opus #3).** The tasks a landing names belong to its commit subject, which is `landing`'s; `change-record` answers which lines and carriers ride (Astra C02).

## 1.12 The remaining questions of rule [[8dab19b6]]
1–9 are §§1.1–1.11.
10. **Contract.** No operation id or answer changes because of this map; operations change owner only (§1.13, section 4). The `Harness` port, hooks and start bindings are server-internal, versioned with the build. The thread catalog and runtime ports change `packages/agent`'s surface, versioned by section 6. Harness ids stay open strings under the `HarnessId` brand; agent ids `harness:*` stay. The thread list's harness detail is a wire arm; the app decodes it through `arms` with its fallback (section 4 §4.4.1).
11. **Stored data.** Owners change for `project`, `setting`, `session`, `thread`, the folds, `target_snapshot`, `worktree_pending_merge` and `landing`; `thread_owner_settings` is cut into three tables; `thread_mandate` and `external_session` are new; the shared tables' foreign keys move to `thread_record`; the merge receipt gains the note's intent; the archive intent is new. Every move rides section 2's D4 and D6 migrations with an explicit result for every column (§1.13), whose rollback is §2.10.
12. **Who may do what.** The operator approves this map. `modules` refuses what it forbids; a loosening goes through `enforce_rule` in the open. A placement found wrong later is corrected here and in the snapshot, never by an exception in the code.
13. **Long-lived things.** Ports and start-bound hooks live for the process; the harness registry is fixed at `start`, so adding a harness is a new build. A quiet lease lives for its scope and is released on every outcome, including failure and interruption. Subscriptions live with their scope and replay from their read models at start. Debt entries retire with their violation.
14. **Bounded resources.** Nothing new is unbounded. `Harness.born` adds a harness's rows to the birth unit — a bounded set per thread. A merge receipt's addressees are the threads placed in one worktree. A synchronous hook runs under the caller's deadline and its own §3.12 ceiling; a contributor past it is named in the answer. Contributions are bounded by the number of modules.
15. **Rollout.** Work running during a wave keeps its rows; the D4 migration moves the mandate, facets and native rows, re-keys every thread's journal and lane to the record, keeps external threads' legacy-run facts, re-points the shared foreign keys and cuts legacy runs before admission. Every port and hook binds before admission, so no call meets an unbound one.
16. **Failures.** A harness refusing in `born` rolls back the whole birth. A restart after birth and before `begin` resumes `begin` from the birth's intent (a CLI launch follows the birth as a C4 intent). A restart during an archive resumes from its archive intent: the publication is resolved by landing's receipt key before anything else, so a commit is never made twice, and the tail finishes under the original caller's authority. A lost or partly typed delivery to a CLI keeps its doubt. A hook's failure follows its row in §1.4.3; none turns an act into a silent success.
17. **Observability.** `modules` verdicts and debt per module; refusals for an unbound port counted by port; quiet-lease refusals by thread; each `start` binding logged; the registry and control scripts rerun in every wave report.
