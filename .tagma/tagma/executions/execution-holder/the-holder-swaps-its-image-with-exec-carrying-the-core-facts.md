- **When.** Logic has left, `starting` is empty, and there is permission: an ACTIVATE frame or the `ACTIVATE_EXIT` exit status of logic whose channel is torn (then `bundle.next` taken by its `holder.entry`). Without permission — only if no logic of the standing bundle has reached ready, the restart pause is already longest, and `bundle.next` has its own `holder.entry`. The remembered PREPARE is not taken by that road: the server may replace or remove `bundle.next` without telling the holder, and the former candidate's argv would name an already-nonexistent load entry, leaving logic no exit. A candidate the holder already returned from or on which exec failed is not taken again without permission, and its PREPARE is refused: otherwise every cycle would open an uncovered window. PREPARE carries the `holder`-part path and the new bundle's logic argv — absolute runtime and host paths after the swap. Logic takes them from the `bundle.next` manifest: the holder does not read JSON but remembers the last accepted PREPARE in the table and after the swap launches logic by it, not by the argv it was raised with. Activation forgets PREPARE: it described the former `bundle.next`, and the next activation needs a new one. A new PREPARE immediately supersedes a former one, even if not itself accepted.
- **`holder.entry`** is the holder's declared contract inside a bundle: the only exit for logic that breaks at load and will never send PREPARE; otherwise it could only be fixed by killing the holder with all processes. It is a text file in the bundle root. First line `holder <part>`, other lines the logic argv in order: `bundle <path>` resolves to `<state>/bundle/<path>` after the swap, `state <path>` to `<state>/<path>`, `text <value>` as is. Paths relative, no `.`, `..` or NUL. The file names the load entry by its bundle's digest, so the digest does not cover it: the bundle build writes it after identity, and bundle verification checks it against the manifest output. PREPARE carries the same for permission activation. If the `bundle.next` holder file matches its own image, bundles swap without exec.
- **The table is core facts only** (`handover.rs`): generation, the logic argv the holder launches, the last accepted PREPARE, records and orphans. The departing holder writes the standing bundle's table, and the successor carries PREPARE into it itself: the same table serves a return to the former holder. Handles in it are opaque platform values. No shape marker: if the shape changes, the step translates the former. The platform carries its own: on macOS an unlinked table file in the state directory, the writer-claim fd (flock held on the same open file description), the soft child limit, and the holder part in argv `--successor`.
- **Exec on macOS** is `posix_spawn` with `SETEXEC | CLOEXEC_DEFAULT`. Before it FD_CLOEXEC is removed from carried fds: an inherit fd with CLOEXEC gives `EBADF` under SETEXEC (probe on macOS 26). On exec refusal CLOEXEC restored.
- **The successor** recreates kqueue (it does not survive exec), pins its own image (the trampoline of the same build as the holder) and adopts the claim and handles. Before launching logic it watches every held child: SIGCHLD arriving during exec is invisible to the new kqueue, but an unreaped child stays a zombie, and its status is not lost.
- **A successor that never started returns the former holder.** Any refusal after parsing its own argv and before the first launch of the new bundle's logic — directory, kqueue, table, adopt, logic itself — swaps bundles back and execs into the former image with `--returned`, the same claim, the same table file and the same fds. Otherwise the successor's exit would close all fds and every terminal would get a hang-up. So before that launch the successor neither closes the table file nor sets CLOEXEC on the claim, and adopt first verifies everything holding no resources and only then takes fds into ownership: a failed adopt closes nothing. The returned holder takes the table without PREPARE and does not return further. If bundles failed to swap back, the new bundle already stands: the successor that can still work stays and launches its logic, while the former holder that itself failed to swap bundles back launches the logic of the bundle that actually stands. Argv stays inconsistent in one case only: the successor never started at all (before kqueue and the table), and bundles did not swap back. Then the former holder returns from `bundle.prior` with its former argv.
- **The swap** goes through `renamex_np(RENAME_SWAP)`, so `bundle` exists at every moment; the former `bundle.prior` deleted in the gap. A failed exec swaps them back: the candidate lies in `bundle.next` again, and the standing bundle's logic launches without pause.
- **PREPARE** launches a new holder with `--verify` in the same argv shape as `--successor`, and it dry-runs the successor's whole start path: argv parsing, directory, standard fds, fd limit, session, event queue, table read and adopt with `fstat` and CLOEXEC of each handle. After that it exits, taking nothing: it does not lock the claim, does not pin the launch image. In its place each claim and handle has `/dev/null` open under the same number. A copy of the PTY master or of the stdin writer held in the verifier would hold the child's hang-up and EOF until its exit, i.e. up to 10 s. The holder keeps the check's deadline on its own timer: a verifier unanswered in 10 s is killed and removed, and PREPARE answers `timeout`. 10 s covers the first signature check of a fresh binary on a slow busy machine; a deadline miss costs only a refused prepare, and the former host keeps working.
- **Capability** `holder-replaces-itself`: without it the client answers PREPARE and ACTIVATE with `unsupported`. Windows will not declare it — no exec with the same pid there.
- **Emergency end of the successor before logic launch** (panic or SIGABRT, SIGSEGV, SIGBUS, SIGILL, SIGFPE, SIGTRAP signals) leads to the same return (`macos/rescue.rs`). The return plan — paths, both images' argv, claim, table and handle fds — prepared before any other start step. The signal handler and panic hook only swap bundles and exec: the calls are safe inside a signal handler. After logic launch the plan removed, and signals act as usual again.
- **Uncovered window:** the successor's SIGKILL, a fall before the plan installed, or a failed exec back — all fds closed. The check that dry-runs the successor's start narrows this window.
