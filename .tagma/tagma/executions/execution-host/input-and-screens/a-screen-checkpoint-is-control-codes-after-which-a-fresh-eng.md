A checkpoint is control-code text plus the record position whose parse it reflects: the screen has no cross-build format; any build's engine reads it. Buffer lines are written by its own writer; `@xterm/addon-serialize` is not used: the addon cannot tell an empty cell with a pen from an erased one, loses a zero-width cell after CSI and raises a false underline on a link.

- **Order is the invariant.** Content is written without margins, without origin mode and with ASCII charsets: otherwise LF scrolls only the region instead of moving lines into history, and text passes through DEC graphics. Tabs, the saved cursor and the buffer margins go after its content, the saved cursor before DECSTBM (otherwise DECSC in origin mode saves a position relative to the new margins). The saved cursor for alt when normal is active is set by entering alt with `?1047h` before the content; entering the active alt is also `?1047h`, not `?1049h`, which would overwrite the saved normal cursor. The cursor goes last, in origin mode relative to scrollTop.
- **Cells that cannot be printed directly.** An empty cell with a pen (left by a wide-character wrap, by erasing half a wide character, and by IRM) is reproduced with the engine's own mechanism: a wide character and printing into the neighbouring cell; a line tail of such cells is written right-to-left up to the line's content. Cells spoiled by this trick the writer then overwrites or erases with ECH. A wrap onto a continued line is taken by natural wrap or by a wide character overflowing in the last column, and a scroll at the bottom of the screen fills the new line with the current pen's background — which is why that too counts as spoiled.
- **Pen.** The engine's DECRC restores only fg and bg, while extended state (underline style and colour, link) stays current; the saved pen is therefore written by bits: underline is `4`, the extended flag without underline is a temporary link around DECSC. A live pen's underline colour is stored even without underline (`58` does not touch the flag) and is always written. DECSCA is `CSI 1/0 "q`. Shift (SI/SO/LS2/LS3) is always written: otherwise GL stays on the set the saved cursor assigned. There is no `charset` vs `charsets[glevel]` divergence in this engine: `CharsetService` changes them only together.
- **Links** are written as short `tagma-checkpoint-<nonce>-<n>` tokens shared by all cells of one link (a link without an id gets the token as its id, otherwise the writer would cut it across lines); the real ids and URIs sit in the file header and are substituted into the engine after replay. Otherwise a long URI would repeat on every line. The checkpoint's byte sum is capped by what the screen it describes holds, plus `parser.pendingBytes`; past that — `CheckpointUnwritable`, and the previous checkpoint stands.
- **Only at parser rest** (`parseState.rest`). If the parser stands right after printing (`parseState.printed` — REP and combining/ZWJ stitching across chunk borders depend on it) or the cursor is in pending wrap, the checkpoint's last act reprints the last cell through the current charset's reverse map; an EL-erased cell in pending wrap is reproduced with a space and `CSI 1K`, which does not clear isWrapped.
- **Cost.** Composition goes in 16384-cell chunks yielding to the event loop between them: taking a checkpoint on 320×100 with 5000 history lines holds the loop no longer than ~3 ms per chunk, and another terminal's echo delay on the same host is p99 4–6 ms against 53 ms for single-chunk composition (sample, macOS arm64, `checkpointPause.bench.ts`). It is taken at the first rest after half of `retainedBytes` since the previous checkpoint, and on preparation request.
- **Restore**: the checkpoint on a fresh engine, then record bytes from its position. Answers to queries in bytes before the frontier are dropped. Resize applies at the byte where the record grid put it: the live engine defers it until that byte parses (`regrid` answers the position), and record reading stops at the grid boundary, so replay and the live screen agree; a resize after the last output is taken from the grid at the record's end.
- **The window checkpoint** (`screenPoint`) is the same composition on window request: the live interpretation takes it at parser rest without moving the file checkpoint's due time, otherwise a window request would postpone the file one until its position falls out of retention. History is cut to the window's scroll. If the parser is not at rest, the standing file checkpoint replays in a temporary scoped interpretation with the window's history and the same dynamic-storage budget; the same serializer assembles it at the previous position without holding unneeded history. Tokens are expanded to real URIs from the checkpoint's table because the window engine does no relink and does not know the token format. Expansion and encoding go in chunks yielding to the event loop; the frame cap is checked as UTF-8 is produced, before the total result is assembled; past it the window gets `budget`. The window drops the output queue and writes the checkpoint straight past the queue cap: the queue already held the checkpoint or reading from its position will deliver it again, and a cap cutting it would leave a partial screen. Before the checkpoint go RIS and what RIS does not reset in xterm — hidden cursor, LNM, OSC colours and the title — so even an engine already carrying a screen continues from it as fresh.
- **Files in the record folder**: `screen-<position>.checkpoint` (a JSON header line, then text; draft and rename), the newest position stands — the earlier ones are deleted by publishing, and a late old one deletes itself against the newer. `screen.abandoned` holds an interpretation refusal; restore opens it with the same refusal. At stream end `screen.retired` is written and checkpoints are deleted; a checkpoint published after it deletes itself. No checkpoint means the checkpoint at 0 while the record keeps byte 0, otherwise the screen is unavailable with a `checkpoint` reason.
