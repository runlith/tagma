An independent config-lane fixture reported a current green seed slowing from 26.4 s file wall to 190.1 s, with SQLite writer/git-index hold warnings and 31.2 s uncovered test wall; that report is another waiting/contention candidate, not a proved server-CPU effect. Retained load queries for that execution and the machine returned no rows, which is missing coverage rather than zero load. A causal fix still needs an isolated current workload and identified resource/producer; disabling shared runtime work or raising limits would not supply that proof.

The `tagBuffers` cost is Bun's `serialization: 'advanced'` IPC encoding, and it grows faster than linearly with the number of values in one message, not with its bytes. Measured on Bun 1.4.4 (best of a few `child.send` calls from a bare `Bun.spawn` parent, one machine, one sample): 10k short strings 5.9 ms, 100k 152 ms, 200k 328 ms, 400k 1151 ms; 10k row objects of 10 fields 37 ms; one 16 MiB string 22–44 ms; one 16 MiB `Uint8Array` 6–9 ms. The same messages with `serialization: 'json'` take 0.25 / 2.3 / 6.3 / 11.9 / 4.1 / 18 ms, but JSON encodes a `Uint8Array` as an index object (1 MiB took 1093 ms) and has no bigint, so neither built-in mode fits the channel's values. That superlinearity is real but lies above what the channel sends. Measured through the public `sqliteProcessLayer`, `Programs` and `ProcessPool` on `childHosting` with a timing wrapper around `Host.send` (scratch bench, loaded machine, two samples): a one-value `Run` sends in a p50 of 0.01 ms; a 10-value insert 0.02 ms; an 8,000-value page, the `binds.ts` ceiling, 1.6–5.3 ms; a batch of 64 programs × 10 statements 0.2–0.35 ms; one program of 3,000 statements (30k values) 1.0–3.3 ms. On the reply side the parent loop's worst gap was 5.4 ms over 5,000-row reads and 87 ms over 50,000-row reads (500k values), decoded natively, with the encoding cost paid in the child. `bun:jsc` `serialize` before `send` is 3× cheaper for 100k–400k strings but slower for a 16 MiB blob (43 vs 6 ms) or string (31 vs 23 ms), and itself superlinear (100k 30 ms, 400k 171 ms). No codec change is warranted: no current sender reaches the sizes where encoding costs a loop-visible amount, and none would have removed this stall.
