A list many features fill is a point its lower owner declares, and each feature contributes from its own `layer.ts`. Surfaces (`Surfaces`, workspace), section columns (`Columns`, workspace), palette actions (`PaletteActions`, workspace), tab kinds (`Panes`, shared panes), link kinds and link menu items (`LinkKinds`, `LinkMenuItems`, opening), settings sections and their contributions (`SettingSections`, `SectionContributions`, settings). The owner stands below every feature that contributes to it. If it loaded their files itself, every importer of addresses would pull all features up the module order. A root outside the core merges its own feature layer beside them, and its items join the same points.

Each registry (`SurfaceRegistry`, `ColumnRegistry`, `ActionRegistry`, `PaneRegistry`, `LinkRegistry`, `SectionRegistry`) is a service over its point. It reads the point's current items when asked and rebuilds its index only when the items array changes, never snapshotting them at build. A contribution may join after the registry was built: members are eager and build in manifest order, or later under a condition or from a chunk. Invariants between items are claims the point refuses at admission: a route, a former name, the home surface, a setting key held by a section, a tab kind's link. A reference to something this build lacks degrades instead of refusing: a column, a parent surface, or a section a contribution names. A core alone, or an extra root without the feature that declares it, still opens. Run-time sources register into the same points (`point.register`), so names and routes have one claims ledger whichever arrives first. A surface that carries its page (`payload`: a component, or a Tagma App view) stands under the one contributed route `p/…`, which `app/SurfacePage.svelte` renders from the registry; core surfaces keep their own route files. App sections are such surfaces with `within`: they stay out of `declared` and are not portable. App launchers and section actions are `PaletteActions` sets, and the point claims every listed action id. Single-item validity is `admits` (a refusal reason, `RegistryRefusal`), and exclusive names are `claims` (`RegistryClash`). Each registry builds its index through `point.derive(build)`, rebuilt when the items array changes. A registry that caches per item keys the cache by the declaration object rather than its id, so a contribution that left and came back under the same id is built anew (`ColumnRegistry`). A consumer that copies a registry answer into its own state derives it from the registry instead (`SettingsCatalog` files each entry under the current `sectionOf`).

Addresses that need the registry are built by the `Addresses` service (from `Router` and `SurfaceRegistry`). Components take it via `.use()`, services by injection, and helpers outside the graph (`markdown.ts`, `blockRefView`, `commitAnchors`) receive it as a parameter. `address.ts` keeps pure functions that need no registry: project, branch, diff and route parameters from `Router`, and diff-range parsing. A test that needs a realistic set of the core's surfaces or links takes it through composition test doors (`testSurfaces`, `testAddresses`, `testAddressing`, `testLinks` in `app/testing.ts`), whose lists are fixture data, or builds a registry over `makePoint` with the declarations it needs. Completeness of the production wiring is proved only by `app/routes.test.ts`. It mounts the real `appLayers` and checks routes against surfaces, every `under`, `column` and contribution section, and that no core contribution clashes. Workspace declares the "Go to …" actions as a function of the app, because their list depends on the registry.
