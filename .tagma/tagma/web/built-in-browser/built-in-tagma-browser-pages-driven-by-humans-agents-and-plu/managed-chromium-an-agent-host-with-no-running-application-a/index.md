Managed Chromium is the second host of the `PageHost` and `ProfileHost` ports ([[39241ecf|browser module]]): the server itself launches Chromium with a profile and talks CDP to it. Agents work on it when the Tagma application is not running, and engine system tests get a real target from the first step. Fingerprint-spoofing profiles stand on it next. Screencast lets the desktop panel, the web, and the phone see and drive pages held by a different desktop.

**Host.**
- The adapter is `managed` — the server's own module; composition connects it to the ports.
- The browser process is a child of the server, one per profile, supervised by the adapter like a plugin process under the plugin module. It ends with the server; after a restart profile pages become `dormant` and restore to the record's current URL (CDP does not restore back-forward history). A process with no pages ends after idle; a long-undriven and unshown page unloads to `dormant`, as on desktop.
- CDP is `--remote-debugging-pipe`: no port. Pipe messages split on `\0`, the adapter reads a narrow header, and large results go to the engine worker as opaque text. The 2026-10-17 experiment (Bun 1.4.3, Chrome for Testing 151.0.7922.71, macOS arm64, one sample): the pipe holds both through `Bun.spawn` with extra fds and through `node:child_process` (used by the Effect `ChildProcessSpawner` with `additionalFds`) — a 5 MB result, about 1,200–1,450 exchanges per second, a clean exit on `Browser.close`; Chromium itself exits when the pipe closes.
- User-data-dir is `browser/profiles/<profile id>` in the server data directory, 0700; the name derives only from the profile id.
- Windowless: `--headless=new`; the viewport is the 1280×800 build window until agent emulation or a screencast viewer with layout sets it (below). On macOS the build explicitly sets Keychain behaviour. Chrome for Testing 149.0.7827.55 on the experiment machine launched and wrote persistent cookies with no window prompt both with and without `--use-mock-keychain`; that does not prove the first launch on a clean account. `--use-mock-keychain` is verified for unattended launch; its price is cookies under a mock key in the 0700 profile directory. The installed-Chrome identity and policy are not established by that sample.
- Page life: opening and closing targets comes from `Target.setDiscoverTargets`; on each page the host keeps its own service session with only `Page` — favicon, downloads, history, dialogs — no `Runtime`. Otherwise an unhandled `alert()` on a windowless page would block it invisibly. Navigation goes through CDP: without it Chromium never navigates.
- "Unresponsive": the host counts a page unresponsive when a light request to its renderer stays unanswered past the deadline; a renderer is someone else's process, and a deadline is fair here. Reloading an unresponsive page does not wait for its renderer: a same-site `Page.reload` never settles while the busy renderer is not freed, so the host replaces the target — opens a new one at the current URL under the same page id, closes the old one, and reports `swapped`.
- One agent profile for all agents: two agents signing into different accounts on one site disturb each other. Stage 1 accepts that; per-thread ephemeral contexts are stage 2, and the port already carries a context.
- The managed-host agent profile gets its sign-ins by import — from the user's Chrome or from the desktop agent profile, with no Google, like any import ([[eae10179|import]]). Signing into Google and passkey sign-in need a window and a human — those are windowed managed profiles, stage 2.

**Builds.** The build contract is internal to the `managed` adapter: find the executable and install it when missing; launch arguments for the profile; the schema of the profile's document part holding the build id and window mode (windowless at stage 1; a build window is stage 2). The core knows nothing of builds. Stage 1 builds:
- `chrome-for-testing` — the server downloads the right version from the official Chrome for Testing JSON addresses into the data directory and verifies it; while downloading, `open_page` waits and the feed shows progress; when it never downloads or is corrupt — a `host-refused` refusal whose reason and unblock name the build (the adapter adds no own refusal codes to the core: operations declare refusals statically, and the core never lists adapters). Step 1.1 installs exactly this — the minimal host without a screencast for engine system tests;
- `installed-chrome` — the user's installed Google Chrome with its own Tagma user-data-dir: Google branding, Widevine. The user's main profile is untouched: Chrome never lets a default profile be debugged. With no Chrome — `host-refused` with a reason.
A build answers for a coherent windowless identity: UA and client-hint brands with no `HeadlessChrome`. Headless=new changes only the UA token (`HeadlessChrome/<major>`), its brands match the windowed ones, so the build sets the whole process UA with a `--user-agent` flag carrying its `Chrome/<major>` — pages, frames, workers of every kind and their requests speak as one, like Orca's process UA ([[447be62e|research]]). The price is empty high-entropy client hints, as in any Chrome with `--user-agent`. Overriding `Emulation.setUserAgentOverride` on every target was rejected by measurement: it never changes a shared worker's `navigator.userAgent`, and waiting for the debugger at target start holds service-worker registration. Proof is a wire-level system-test measurement. PDF goes through the single `PageHost` action; this adapter performs it via `Page.printToPDF`. PDF support in stage-2 windowed managed profiles is verified on their own build; a native Electron API result never proves it.

**Screencast.**
- The engine runs one `Page.startScreencast` flow per page through its session multiplexer while the page has at least one viewer, and distributes frames to viewers over the `browser.screencast` feed; while a viewer exists the engine holds the port's `paint` on the page, and the host draws it with no background throttling. It works on any host: a desktop page is watched from the phone the same way.
- The budget belongs to the producer: a viewer declares its CSS size and pixel-density limit; the one flow per page follows the weakest viewer (smallest quality and size, largest interval), and a frame reaches viewers as is, with no server-side parsing or re-encoding.
- Each frame is acknowledged with `Page.screencastFrameAck`: without ACKs Chromium stops sending.
- A viewer that stops taking arriving frames for the set time after at least one received frame is evicted.
- A static page sends no frames: with no frame inside the interval the engine takes a screenshot.
- **Page size.** A natively viewed page takes its size from the view bounds: a phone viewer picks only the frame size and density and never changes the layout under the human at the Mac. Whether a host's pages have a native view is declared by the host in `Host.native`. A page with no native view takes its size from the first viewer asking for layout: the engine sets `Emulation.setDeviceMetricsOverride` on it, yielding to agent emulation; mobile emulation runs only on an explicit "mobile view" (`emulate_page`).
- **Viewer input** is one ordered flow per (viewer, page) pair over a live socket: the live socket's `browser.input` calls with `seq`, applied by the engine strictly in order, in event batches per animation frame; not an HTTP call per event. A viewer gets its own id from the first `browser.screencast` event. Mouse, wheel (one event per animation frame), control keys go as `Input.dispatchKeyEvent`; typed text after composition ends goes as `Input.insertText`, so Cyrillic and IME work past the US-layout table. Coordinates arrive as frame fractions and convert to CSS viewport by the last frame's size. A viewer-area change travels the same flow and rebuilds the flow and layout with no new subscription.
- **Clipboard.** A viewer's ⌘V pastes its clipboard text through `Input.insertText`: a windowless browser's clipboard is not the human's clipboard. Copying from the page is a `copy` event on the same flow: the answer carries the selected text, and the viewer puts it in its own clipboard.
- **Files.** While a page has a viewer, page file picking is intercepted (`Page.setInterceptFileChooserDialog`): viewers get pick events, bytes travel to the server with a `browser.files` call into the page directory, and the engine hands them to the field via `DOM.setFileInputFiles`. Windowless-page downloads go to `browser/downloads/<profile id>` (`Browser.setDownloadBehavior` sets the directory for the whole profile browser; the event's `frameId` assigns the download to the page) and are removed with the profile, land in the page record, and a human downloads them from the panel while an agent reads `read_page_downloads`.
- The client screencast view ([[e3064958|panel]]) is a `PageView` adapter for pages held by another desktop. On the phone it is a page screen with a tab list and touches.
- A managed-host page popup (OAuth during an agent run) is a screencast tab a human can carry through.

**What the performer proves.** Engine scenarios pass on a managed host with both builds; an instance restart restores pages by URL; a windowless-identity measurement finds no `HeadlessChrome` in UA or brands; an `alert()` on a windowless page becomes a dialog in its state; a missing build refuses with `host-refused` naming the build. Screencast: a viewer gets frames; a second viewer with a smaller budget lowers the shared one; one that stops acknowledging is evicted; a static page yields a frame; a viewer click lands in the element under the converted coordinates; reordered input messages apply by `seq`; a natively viewed page's viewer never changes its size; viewer file picking reaches the field; a windowless page's download appears in the record. Measurement (one sample): the server event-loop lag with one and three screencast pages.

**What the operator checks.** An agent walks a scenario and a human watches it in the panel; from the phone the page shows and drives with touches, text insertion and file upload work.
